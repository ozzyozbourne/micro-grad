CHAPTER 11Fusion & splitting into kernels

Chapter 10 ended with a graph full of STAGE (BUFFERIZE) candidates. This chapter answers the question you actually care about: how many kernels, and which ops go into which one? You'll see the cost function that throws cheap candidates away (pm_remove_bufferize), the per-kernel buffer limit (pm_limit_bufs), how survivors become ALLOC + STORE (bufferize_to_store), and how split_kernels cuts the graph into SINKs wrapped in CALLs. Then a catalogue of 13 real programs with their kernels and C code, a game, and a graph you can cut yourself.

11.1 Intuition: a kernel is a loop nest that ends in a store

After rangeify, the graph is "one giant loop program": every value is written in terms of loop variables. A kernel is a piece of it that a GPU can launch on its own: one loop nest whose body ends by writing to memory. So the cut points are exactly the places where a value is written to a buffer and later read back:

  • every STORE (your outputs, contiguous(), assign, copies) — always;
  • every STAGE that survives — a candidate from the realize map that wasn't cheaper to recompute.

Everything between two cut points is fused: it runs inside the loop of the kernel that reads it, possibly more than once (recomputation is the price of fusion).

AnalogyA kitchen. Each kernel is a cook at a station who produces one tray (a buffer). A cook may prepare intermediate ingredients herself, right when she needs them (fusion) — even if the cook next to her prepares the same ingredient again (recomputation). Only when an intermediate is expensive (it involves a long reduction), or needed whole before anyone can use a bit of it (a row max before subtracting it), does it go on its own tray in the fridge (a buffer) — and that costs a fridge trip (a memory round-trip) and a new cook (a kernel launch).
The key ideaKernels = STOREs + surviving STAGEs. Chapter 10 proposes candidates conservatively; pm_remove_bufferize removes the ones that are cheap to recompute; the survivors are turned into stores into fresh ALLOC buffers; finally every STORE/END that closes all its loops is cut out as one kernel. Count the stores, you've counted the kernels.

11.3 pm_remove_bufferize: when is recomputing cheaper than storing?

The pattern is INDEX(STAGE(src, *ranges), *idx) — "a consumer reads a candidate buffer at position idx". Removing the STAGE means: substitute the consumer's idx for the STAGE's own ranges inside src, i.e. compute src right there, at the position the consumer needs. The decision is remove_bufferize:

def remove_bufferize(src:UOp, buf:UOp, idx:UOp):
  # if it's user contiguous, we never remove it
  if not buf.arg.removable: return None

  # *** here is where we compute the cost ***
  # if we return None, the bufferize is kept
  accessed_buffers: list[UOp] = []
  reduces: list[UOp] = []
  def red_gate(x:UOp):
    if x.op is Ops.AFTER:
      accessed_buffers.append(x.buf_uop); return False
    if (x.op is Ops.STAGE and x.arg.addrspace == AddrSpace.GLOBAL) or x.op is Ops.MSTACK:
      accessed_buffers.append(x); return False
    if x.op is Ops.STORE: return False          # don't look inside stores
    if x.op is Ops.PARAM: accessed_buffers.append(x)
    if x.op is Ops.REDUCE: reduces.append(x)
    return True
  src.toposort(gate=red_gate)
  accessed_buffers = dedup(accessed_buffers)

  # if this is generated from multiple buffers, don't remove this buffer
  if len(accessed_buffers) > 3: return None

  # if any reduces access a buffer, don't remove this buffer
  buffer_in_reduce = False
  def buf_gate(x:UOp):
    nonlocal buffer_in_reduce
    if x.op in {Ops.PARAM, Ops.STAGE, Ops.AFTER}: buffer_in_reduce = True
    return not buffer_in_reduce
  UOp.sink(*[x.src[0] for x in reduces]).toposort(gate=buf_gate)
  if buffer_in_reduce: return None

  # if it makes it here, the bufferize is removed
  replaced = {k:v for k,v in zip(buf.src[1:], idx.src[1:]) if k.op is not Ops.CONST and not (v.op is Ops.CONST and v.val is Invalid)}
  return src.substitute(replaced, extra_pm=pm_gate_substitute)

So the cost model is three crisp rules, not a FLOP estimate:

  1. Never remove a user's contiguous() (removable=False). (In practice .contiguous() already became a STORE in prepare_rangeify, and STOREs are never STAGEs, so they never even reach this rule; removable=False covers ALWAYS_CONTIGUOUS sources and non_removable custom-kernel inputs.)
  2. Keep if the value reads more than 3 buffers. Recomputing means re-reading every buffer at every use; past 3 inputs the memory traffic of recomputation is likely worse than one store + one load.
  3. Keep if any REDUCE inside it reads a buffer. A reduce costs a whole loop per element; recomputing it per consumer element would multiply the work by the size of the consumer's loop. Reductions over pure index math (e.g. arange's cumsum trick) are fine to recompute.

Otherwise the STAGE is removed. Note the costs it does not count: how many ALU ops src has (elementwise is considered free next to memory), and how many consumers read it.

11.5 pm_limit_bufs: a cap on buffers per kernel

  
Some backends limit the number of buffer arguments a kernel may take (WebGPU: 8 bindings). _limit_bufs
  runs on every binary/ternary op, counts the set of buffers (STAGE, AFTER, PARAM, MSELECT, MSTACK) reachable below it
  (memoized in LimitBufsContext.buf_cache), and if it exceeds MAX_BUFS - 1 (one slot is reserved for the output) it inserts a fresh
  STAGE on each elementwise source via stage(), with new WEAK ranges. The limit is MAX_KERNEL_BUFFERS or
  DEVICE_MAX_BUFS = {"WEBGPU": 8}; on CPU it is 0 = off.


def _limit_bufs(ctx:LimitBufsContext, root:UOp):
  if (device:=root.device) is None: return None # no device, index related calculations
  device = device if isinstance(device, str) else device[0].split(":")[0]
  if not (MAX_BUFS:=MAX_KERNEL_BUFFERS.value or DEVICE_MAX_BUFS.get(device, 0)): return None
  ...
  if len(bufs) > MAX_BUFS - 1: # NOTE: this -1 is for the output buffer
    return root.replace(src=tuple(stage(ctx, s) if s.op in GroupOp.Elementwise and s.device is not None else s for s in root.src))

  
The same matcher has a second job: fix_store_hazard. If a STORE into buffer B
  has a value that loads from B at a different index than the one being written, the value is staged into a temporary first, so the
  kernel never reads an element it already overwrote. (The realize-map rule realize_store_after_src from Chapter 10 catches the
  same problem earlier for whole assigns.)


  
  
11.6 bufferize_to_store: STAGE becomes ALLOC + STORE

  
A surviving STAGE is still an abstract "materialize this". bufferize_to_store
  (pass stage to store, bottom-up) makes it concrete:


def bufferize_to_store(ctx:itertools.count, x:UOp, idx:UOp):
  size = prod(x.shape)
  dtype = x.commit_dtype()   # a BUFFER is never weak
  rngs = sorted(idx.ranges, key=lambda x: x.arg)
  ...
  if x.arg.addrspace == AddrSpace.GLOBAL:
    buf = UOp.alloc((size,), dtype, slot=next(ctx), device=x.arg.device)
    do_store = buf.index(idx).store(x.src[0].cast(dtype)).end(*rngs)
    return buf.after(do_store).cast(x.dtype)

  
Before it runs, pm_flatten_bufferize collapses a multi-range STAGE into a single flat index (a RESHAPE in reverse), so
  idx is one expression. The result: a fresh ALLOC (a call-local, not-yet-real buffer with a slot number), an
  INDEX+STORE of the value, an END that closes the STAGE's ranges, and an AFTER that
  says "readers see the ALLOC only after that store". The consumer's existing INDEX now indexes the AFTER. If the STAGE wraps an
  existing AFTER (an assign), no new buffer is made: the existing stores just get their ENDs.

11.7 split_kernels: cutting out SINKs and wrapping them in CALLs


def split_store(x:UOp) -> UOp|None:
  # if we have any open ranges here, we don't split. open DEVICE ranges are fine, they are bound per device at launch
  if any(r.axis_type is not AxisType.DEVICE for r in x.ranges): return None

  # local kernel rewrite
  lctx = LocalAddBufferContext()
  ret = graph_rewrite(x, to_define_global+pm_flatten_range, ctx=lctx, name="kernel split", bottom_up=True)
  ret = ret.substitute({b:debuf(i, b) for i,b in enumerate(lctx.map)}, walk=True)
  ret = graph_rewrite(ret, pm_renumber_range, ctx={a:i for i,a in enumerate(lctx.ranges)}, walk=True)

  # create the Kernel. NOTE: buffers can be on different devices here now, they are compiled to SDMA copies later by schedule
  return ret.sink(arg=KernelInfo()).call(*lctx.map.values())

split_kernels = PatternMatcher([
  (UPat((Ops.STORE, Ops.END), name="x"), split_store),
])

  
split_store fires on every STORE/END
  whose .ranges (the open ranges below it) is empty — i.e. a complete loop nest. Bottom-up order means inner kernels are cut first;
  the outer kernel then sees them only as AFTER(buffer, CALL) leaves. Inside:

  
    
    
  • "kernel split" (to_define_global): walks the kernel body; every BUFFER/ALLOC/PARAM/MSTACK/MSELECT
    becomes an entry of lctx.map (and the walk stops there — BottomUpGate); an AFTER is replaced by its buffer, remembering
    the AFTER as the CALL argument (that's how the dependency on the producing kernel is kept); check_buf_states raises
    "cycle detected while indexing" if one kernel would read two different states of the same buffer.
    • 
    
  • debuf: buffer number i becomes PARAM(i) reshaped to its shape — kernel-local, positional. Slot 0 is whatever
    was found first, usually the output.
    • 
    
  • pm_renumber_range (the unnamed rewrite in the pass list): ranges renumbered from 0 in order of appearance, so two identical
    kernels anywhere in any program have identical ASTs → same compile-cache key.
    • 
    
  • The body becomes SINK(arg=KernelInfo()) — the kernel AST of Chapter 13 — and is
    .call(*buffers)'d.
    • 
  

  
Finally pm_no_views strips RESHAPE/SHRINK sitting directly on buffers: in the kernel graph, a buffer is just storage.


  
Why CALL? A CALL(body, *args) is the same op used for @function calls and the whole
  schedule (CALL(LINEAR(...)), Chapter 12). A kernel is a function from buffers to buffers; making it a CALL means the scheduler,
  the JIT and the runtime handle "a kernel", "a copy" and "a nested schedule" uniformly.

11.10 The price of fusion: recomputation

  
Fusion saves memory round-trips and kernel launches, but not for free. x - x.mean() is a single kernel because the mean is a
  scalar. On a CPU that's great: the codegen notices the reduce loop doesn't depend on the output loop and emits it once, before. On a GPU, the
  output loop is spread across work-groups — and each work-group has to compute the mean for itself:

11.12 Hammer it again: one program, three ways

  
Take softmax on (4, 8) and say why it is 3 kernels three times over.

  
    
    
  1. As math. \(\text{out}_{ij} = e^{x_{ij}-m_i} / s_i\) with \(m_i = \max_j x_{ij}\) and \(s_i = \sum_j e^{x_{ij}-m_i}\). To produce
    any \(\text{out}_{ij}\) you need the full \(s_i\), which needs the full \(m_i\). Two complete reductions per row must finish before the
    output loop, and each one feeds a broadcast. (The third kernel is the output.)
    2. 
    
  2. As rangeify. Both REDUCEs collect ending ranges from the broadcasting MUL/ADD → candidates. EXP2 has two consumers at different
    ranges → candidate. The input RESHAPE has two consumers → candidate.
    3. 
    
  3. As remove_bufferize. The two REDUCE candidates contain a reduce that reads a buffer → kept. EXP2 and RESHAPE read ≤ 3 buffers, no
    reduce → removed (EXP2 is recomputed in kernels 1 and 2: open the softmax case above and hover the pink nodes).
    4. 
  

  
And the C code confirms it: kernel 0 is a max over 8, kernel 1 an exp-sum over 8 that reads kernel 0's buffer, kernel 2 recomputes
  exp2((x - max)*log2(e)) and multiplies by the reciprocal of the sum.


  

    
Why is x.sum(1).sum() one kernel, while x / x.sum(1, keepdim=True) is two?

    
    
    
    
Ending ranges come from broadcasting consumers. A reduce feeding a reduce has no broadcast in between, so it fuses into one loop nest (r_8_4).

  


  

    
After split kernels, how does the output kernel's CALL know it must run after the kernel that computes the row means?

    
    
    
    
Dependencies live in the graph as AFTERs. Chapter 12's create_schedule turns them into an order.

  


  

    
What turns a surviving STAGE into something a kernel can write to?

    
    
    
    
    
ALLOC is "storage to be allocated later". It only becomes a real BUFFER in Chapter 12 (resolve_linear_call → create_new_buffer).

  


  

    
You have 6 input tensors added together on WebGPU (8 bindings max). What happens?

    
    
    
    
The check is len(bufs) > MAX_BUFS - 1. On CPU you can simulate a smaller limit with MAX_KERNEL_BUFFERS=4, as in the catalogue.

  


  
Chapter summary
    
    
  • Input: the rangeified graph with candidate STAGEs. Output: a kernel graph — CALL(SINK(KernelInfo), *buffers) nodes linked by AFTER(buffer, CALL).
    • 
    
  • pm_remove_bufferize keeps a candidate iff it's non-removable, reads > 3 buffers, or contains a reduce that reads a buffer. Everything else is recomputed at each use.
    • 
    
  • pm_limit_bufs caps buffers per kernel (WebGPU / MAX_KERNEL_BUFFERS) and fixes store hazards.
    • 
    
  • bufferize_to_store: STAGE → AFTER(ALLOC, END(STORE(INDEX(ALLOC, idx), value), ranges)).
    • 
    
  • split_kernels cuts each fully-closed STORE/END into a kernel: buffers → positional PARAMs, ranges renumbered, SINK(KernelInfo).call(*buffers).
    • 
    
  • Kernel count = STOREs (outputs, contiguous, assign, copies, split reduces) + surviving STAGEs (broadcast-back reduces, expensive multi-use values, hazards, buffer limits).
    •
