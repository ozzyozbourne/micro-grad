CHAPTER 07Movement ops

A movement op never moves a byte. It is a promise about where to look. After this chapter you will be able to read any chain of RESHAPE · PERMUTE · EXPAND · PAD · SHRINK UOps as a single function from an output position to an input position (plus a validity mask), know exactly which primitive ops each friendly Tensor method turns into — including the surprising ones, like flip — and see why this version of tinygrad treats the index expressions built during rangeify as the source of truth.

7.1Intuition: a view is a recipe for where to look

Take a buffer of six floats in memory, [0 1 2 3 4 5]. "Reshape it to 2×3", "transpose it", "flip it", "pad it with zeros" — none of these needs to touch the six floats. Each one only changes the answer to one question:

The one question "If somebody asks for element out[i, j] of the result, which element of the buffer do I read — or is it padding?"
A movement op is nothing but a function \( f : \text{output index} \mapsto \text{input index} \cup \{\text{invalid}\} \). Compose a chain of them and you get one bigger function. That function is what eventually appears as the address arithmetic inside a kernel's load.
Analogy: a concert hall seating chart The audience (the bytes) sits still. A movement op is a new seating chart printed for the ushers: "row 2, seat 1 on the new chart means row 1, seat 2 in the hall". PERMUTE relabels rows as seats, RESHAPE renumbers the seats as if the hall had a different width, EXPAND tells several ushers to send people to the same seat, SHRINK hands out a chart for just the balcony, and PAD adds imaginary seats along the walls that are always empty (zero). Printing a new chart is free. Only when someone actually reads the chart (a kernel loads data) does work happen.

7.2The five primitives (and what is not one)

In this checkout the tensor graph has exactly five movement ops. The Ops enum says it in a comment:

tinygrad/uop/__init__.py:92

UNSHARD = auto()  # UNSHARD is really a movement op

plus SHRINK, which is declared higher up next to INDEX () because it survives into codegen as a pointer-window op, and the set used by the scheduler is GroupOp.Movement = {RESHAPE, EXPAND, PERMUTE, PAD, SHRINK} (). UNSHARD is "really a movement op" for multi-device tensors (it concatenates per-device shards along an axis); we leave it to Chapter 19.

Three things your memory of older tinygrad (or PyTorch) will get wrong
  1. There is no FLIP op. Ops.FLIP does not exist; Tensor.flip is built from PAD/RESHAPE/PERMUTE/SHRINK (§7.4 — it is a beautiful trick).
  2. EXPAND only adds dimensions on the left. Its arg is the tuple of new leading sizes and the output shape is arg + src.shape. To broadcast a size-1 axis in the middle, the high-level expand squeezes it out, expands on the left, and permutes back.
  3. PAD and SHRINK store (offset, size), not (before, after) or (start, end). x.pad(((1,1),(0,2))) on a 2×3 tensor is stored as PAD((1,4),(0,5)): offset 1 into a new size of 4, offset 0 into a new size of 5.
A UOp is EXPAND with marg = (4,) applied to a source of shape (2, 3). What is its shape?
In this version _shape for EXPAND is literally tuple(self.marg) + ps (ops.py:392): new axes are prepended. The index function just drops the leading indices, which is why the same input element is read for every value of the new axis.

7.3How a movement op is stored: args are UOps

You might expect UOp(Ops.RESHAPE, arg=(3,2)). That is not how it looks. The shape argument is itself part of the graph: src[1:] holds UOps — a STACK of CONSTs (or a single CONST for a 1-tuple) — and .arg is None. Here is the real thing, printed by examples/07_movement_basics.py:

Read the output carefully, it is dense with design decisions:

  • Buffers are flat. Tensor([[0,1,2],[3,4,5]]) is a 1-D BUFFER of 6 floats wrapped in RESHAPE(2,3). Every tensor shape you ever see is already a movement op on top of flat storage.
  • Args are UOps, built by shape_to_shape_arg and attached by UOp._mop. That is what lets a shape contain a symbolic Variable (Chapter 6) — a shape is just an integer-valued UOp expression — and it means args are hash-consed like everything else: the two STACKs inside PAD reuse the very same CONST nodes as other shapes in the graph.
  • marg decodes them back. For PAD/SHRINK there are two arg srcs (offsets, sizes) zipped into pairs.

def _mop(self, op:Ops, arg) -> UOp:
  # early NOOP
  if op is Ops.EXPAND and len(arg) == 0: return self
  if op in {Ops.SHRINK, Ops.PAD} and len(arg) == 0:
    assert len(self.shape) == 0, "0 len arg only valid on zero length shape"
    return self
  match op:
    case Ops.RESHAPE | Ops.EXPAND: src_args = [arg]
    case Ops.PAD | Ops.SHRINK: src_args = list(zip(*arg))
    case Ops.PERMUTE: src_args = [arg]
    case Ops.STACK:
      srcs = (self,)+tuple(arg)
      dtype = dtype_from_uop(Ops.STACK, srcs, None)
      return UOp(Ops.STACK, src=tuple(u if u.base.is_invalid else u.ccast(dtype) for u in srcs))
    case _: raise RuntimeError(f"{op} is not a MovementOp")
  usrcs = [shape_to_shape_arg(arg) for arg in src_args]
  return UOp(op, src=(self,)+UOp.sink(*usrcs).simplify().src)

Shape inference. UOp._shape () is a recursive_property: every UOp computes its shape from its sources the moment it is built, and invalid ops raise immediately — a bad reshape fails at the Python line that wrote it, not deep inside the scheduler. Note the subtle resolve(prod(ps) != prod(self.marg), False): with symbolic shapes the product equality might be true at runtime but unprovable now, so only provably unequal products are rejected.

Where did broadcasting go? Elementwise ops broadcast implicitly: the comment at ops.py:424 says "broadcasting lives in _shape property now". MUL of a (2,1,3) and a (1,4,3) source simply has shape (2,4,3); no EXPAND is inserted. Rangeify later gives the broadcast axes a constant-0 index (broadcast_rngs, ). You will see this in matmul in Chapter 8. (Set DISALLOW_BROADCAST=1 to make implicit broadcasting an error.)

Some lessons hiding in that table:

  • view, flatten, unflatten, squeeze, unsqueeze and x[:, None] are all just RESHAPE. transpose and .T are PERMUTE.
  • Integer indexing x[1] is a SHRINK to size 1 followed by a RESHAPE that drops the axis.
  • Strided slicing x[1:3, ::2] has no stride op: _apply_view_ops pads to a multiple of the stride, reshapes each axis into (n/stride, stride), and SHRINKs the inner axis to 1 — "take every 2nd" becomes "take column 0 of a 2-wide reshape".
  • expand of a middle axis is RESHAPE (squeeze) → EXPAND (left) → PERMUTE (move it back): see _broadcast_to below.
  • repeat = reshape-to-insert-1s → EXPAND → reshape-to-merge. roll = repeat(2) along the axis, then a SHRINK window that starts at the right offset.
  • flip takes 12–14 primitive ops. Read on.

def _broadcast_to(self, new_shape: tuple[sint, ...]) -> Self:
  if self.shape == new_shape:
    return self
  if self.ndim > len(new_shape):
    raise ValueError(f"cannot broadcast tensor to fewer dimensions. shape={self.shape} to {new_shape=}")
  # first unsqueeze left with 1s https://data-apis.org/array-api/latest/API_specification/broadcasting.html
  shape, _ = _align_left(self.shape, new_shape)
  # for each dimension, check either dim is 1, or it does not change
  if not all(s == ns or s == 1 for s, ns in zip(shape, new_shape)):
    raise ValueError(f"cannot broadcast {self.shape} to {new_shape=}")
  # EXPAND only adds dims on the left. squeeze 1s that need expanding, EXPAND on left, permute back.
  n_left = len(new_shape) - len(self.shape)
  expand_at = tuple(i-n_left for i in broadcast_axes(self.shape, new_shape) if i >= n_left)
  kept = tuple(i for i in range(len(self.shape)) if i not in expand_at)
  squeezed = self.reshape(tuple(self.shape[i] for i in kept))
  expanded = squeezed._mop(Ops.EXPAND, arg=new_shape[:n_left] + tuple(new_shape[n_left+i] for i in expand_at))
  # expanded shape = [left] + [expand_at dims] + [kept dims], permute to new_shape
  perm = tuple(range(n_left)) + tuple(
    n_left + (expand_at.index(i) if i in expand_at else len(expand_at) + kept.index(i)) for i in range(len(self.shape)))
  return expanded.permute(perm)

def _apply_view_ops(self, mops:list) -> Self:
  # applies shrink + flip + stride from a list of parsed view indices
  # flip negative strides
  x = self.shrink(tuple(m["boundary"] for m in mops)).flip(tuple(i for i, m in enumerate(mops) if m["stride"] < 0))
  strides = tuple(abs(m["stride"]) for m in mops)
  # apply stride
  if any(st != 1 for st in strides):
    if not all_int(x.shape): raise RuntimeError("symbolic shape not supported")
    x = x.pad_to(tuple(round_up(s, st) for s, st in zip(x.shape, strides)))
    x = x.reshape(tuple(flatten((s // st, st) for s, st in zip(x.shape, strides))))
    x = x.shrink_to(tuple(flatten((s, 1) for s in x.shape[::2]))).reshape(x.shape[::2])
  return x

The flip trick, in words

To reverse an axis of length \(n\) without a reverse primitive: pad each element into its own row of width \(n-1\) (it sits in column 0 of an \(n\times(n-1)\) grid), flatten — element \(i\) is now at position \(i(n-1)\) — and pad \(n-1\) zeros at the front, so element \(i\) is at \((i+1)(n-1) = in + (n-1-i)\). Read that in a grid of width \(n\): row \(i\), column \(n-1-i\) — the elements lie on the anti-diagonal of an \(n\times n\) square. Transpose the square: element \(i\) moves to row \(n-1-i\), column \(i\), i.e. flat position \((n-1-i)n + i\). Shrink off the first \(n-1\) positions and reshape to width \(n-1\): that is row \(n-1-i\), column 0. Take column 0 — the elements come out reversed. Every step is a pure index function, and once the whole chain is composed, symbolic simplification collapses the twelve ops to \(\text{buf}[5 - r_0]\) (for \(n=6\)). The chain animator in §7.6 replays this with real data.

cat and stack: STACK is a data op, too

The STACK op you met as a shape container also appears as a data op: stack stacks UOps along a new leading axis, and cat of equal-sized pieces is stack(...).flatten(dim, dim+1). Unequal pieces are padded into place and summed (usum) — padding contributes zeros, so the sum is a select. During rangeify a data STACK becomes a tree of WHEREs on the leading range (convert_stack_to_where, ).

Which primitive ops does x[::2] on a 1-D tensor of length 6 use?
Strides are not a primitive. _apply_view_ops pads to a multiple of the stride (unneeded here), reshapes to (3, 2), shrinks to (3, 1) and reshapes to (3,). The composed index is buf[r0*2] (see §7.6).

7.5The mental model: every movement op is an index function

The single most important function for this chapter is apply_movement_op in schedule/indexing.py. Its comment reads "this is the definition of the movement ops" — and it really is: the scheduler never "executes" a movement op, it only ever calls this function to translate the loop variables (RANGE UOps) of a consumer into index expressions for the producer.

tinygrad/schedule/indexing.py:147 — _apply_reshape and apply_movement_op
@functools.cache
def _apply_reshape(in_shape:tuple[sint,...], out_shape:tuple[sint, ...], urngs:UOp) -> UOp:
  acc:sint = 1
  axes_in:list[UOp] = []
  for s,src in list(zip(out_shape, urngs.src))[::-1]:
    axes_in.append(acc*src)
    acc *= s
  combined_axes = UOp.const(0).usum(axes_in)
  axes_out:list[UOp] = []
  for s in in_shape[::-1]:
    axes_out.append(combined_axes % s)
    combined_axes //= s
  # this simplify is doing a lot of heavy lifting. this is the replacement for the reshape view merging code
  return graph_rewrite(UOp.sink(*axes_out[::-1]), symbolic+pm_simplify_valid+pm_drop_and_clauses, name="reshape")

# this is the definition of the movement ops
@functools.cache
def apply_movement_op(op:Ops, in_shape:tuple[sint,...], arg:tuple, rngs:tuple[UOp, ...]) -> tuple[UOp, ...]:
  match op:
    case Ops.SHRINK:  rngs = tuple(a if off == 0 else a+off for a,(off,_) in zip(rngs, arg))
    case Ops.PERMUTE: rngs = tuple(rngs[p] for p in argsort(arg))
    case Ops.EXPAND:  rngs = rngs[len(arg):]
    case Ops.PAD:
      # NOTE: the .where(r-s, i) is not inside the graph_rewrite so that `convert_pad_to_where_to_keep_behavior_local`
      #       wraps the pad with only the newly added valid
      rngs = tuple(r if (sz == sh and off == 0) else (r-off).valid(graph_rewrite((r >= off) & (r < (sh+off)),
        symbolic+pm_simplify_valid, name="pad")) for r,sh,(off,sz) in zip(rngs, in_shape, arg))
    case Ops.RESHAPE:
      sink = UOp.sink(*rngs).simplify() # NOTE: this applies any commutative flips to the rngs early
      sub_array = {r:r.replace(arg=(AxisType.PLACEHOLDER, i)) for i,r in enumerate(sink.ranges)}
      rngs = _apply_reshape(in_shape, arg, sink.substitute(sub_array)).substitute({v:k for k,v in sub_array.items()}).src
    case _: raise RuntimeError(f"{op} is not a MovementOp")
  return rngs

Inputs → transformation → outputs, precisely:

input
the op, the input shape, the decoded marg, and one index UOp per output axis (usually RANGEs r0, r1, …)
output
one index UOp per input axis — integer expressions of the output ranges, possibly wrapped as idx.valid(cond) (a WHERE(cond, idx, Invalid)) by PAD
direction
backwards: from consumer to producer. You do not push data forward through a view; you pull indices backward through it.

7.6Composition: a whole chain is one index expression

Because each op is a function from output index to input index, a chain is function composition, applied top-down: start with one RANGE per axis of the final view, feed them into the topmost op's index function, feed the result into the next one, … until you reach the buffer. That is exactly the loop in run_rangeify (indexing.py:282: if x.op in GroupOp.Movement: rngs = apply_movement_op(x.op, x.src[0].shape, x.marg, rngs)). Part 2 of the example does the same walk by hand:

  u = t.uop

7.7PAD and the validity mask

PAD is the only primitive whose index function is partial: outside the original window there is nothing to read. tinygrad expresses that with the special constant Invalid: (r - off).valid(cond) is WHERE(cond, r - off, Invalid) (UOp.valid, ). Where does the zero come from? Not from the index: during rangeify the PAD node itself is rewritten into a WHERE on the data:

tinygrad/schedule/indexing.py:98 — PAD → WHERE
def convert_pad_to_where_to_keep_behavior_local(ctx:IndexingContext, x:UOp):
  if x not in ctx.range_map: return None
  if x.op is Ops.INDEX and len(ctx.range_map[x][0]) == len(ctx.range_map[x][1]): return None
  if (bx:=create_bufferize_and_index_based_on_ranges(ctx, x)).src[0] is x: return None
  valid: UOp = UOp.const(True).uprod([r.get_valid() for r in ctx.range_map[x][0]])
  return valid.where(bx.src[0], UOp.const(x.dtype.const(0)))

So a padded load becomes valid ? load(buf[idx]) : 0 right at the PAD, using only the validity that PAD introduced (that is what the NOTE inside apply_movement_op is about). In C you saw it already: ((Lidx1<1)?val0:0.0f). Two consequences worth remembering:

  • PAD always pads with 0. x.pad(…, value=v) with \(v \ne 0\) is built as PAD(ones_mask).where(PAD(x), v) (_pad_constant, ) — a second PAD of a boolean True plus a WHERE.
  • Negative padding is a SHRINK. _pad_constant shrinks first for negative pads, then pads with the non-negative remainder.
  • reflect / replicate / circular are compositions. circular is repeat + SHRINK; reflect and replicate build edge slices (negative-stride slices, i.e. flips; or SHRINK+EXPAND) and cat them.

7.8Cleaning up chains before rangeify: mop_cleanup and pm_mops

Composition via index expressions makes most structural "view merging" unnecessary, but a few cheap rewrites still run on the tensor graph so it stays small. They live in tinygrad/uop/movement.py:

mop_cleanup = PatternMatcher([
  # merge adjacent SHRINKs
  (UPat(Ops.SHRINK, name="x").f(Ops.SHRINK, allow_any_len=True, name="s"),
   lambda s,x: x.src[0]._mop(Ops.SHRINK, tuple((o+p, n) for (o,_),(p,n) in zip(x.marg, s.marg)))),
  # merge adjacent RESHAPES
  (UPat(Ops.RESHAPE, src=(UPat(Ops.RESHAPE, name="x2"), UPat()), name="x"), lambda x,x2: x.replace(src=(x2.src[0], x.src[1]))),
  # remove noop RESHAPEs
  (UPat(Ops.RESHAPE, src=(UPat(name="x2"), UPat()), name="x"), lambda x,x2: x2 if x2._shape is not None and x2.shape == x.shape else None),
  # merge PERMUTEs
  (UPat(Ops.PERMUTE, src=(UPat(Ops.PERMUTE, name="x2"), UPat()), name="x"),
   lambda x,x2: x2.src[0].permute(tuple(x2.marg[i] for i in x.marg))),

7.9Views are free until realized; contiguous()

A movement op costs nothing until some kernel reads through it, and then it costs nothing extra: the index expression is folded into that kernel's load address. Part 3 of the example prints the C code for m.T.flip(0) + 1:

  Returns a contiguous tensor.

Even contiguous() is lazy and smart: when the chain over a real BUFFER collapses to a contiguous range of it, the scheduler (contiguous_mops_to_view, , using UOp.contiguous_view) replaces it by a sub-buffer view with an offset — zero kernels. Only a genuinely non-contiguous order (the transpose) produces a copy kernel. And when you use a view as an input to a computation (m.T + 1), the view fuses into that kernel's loads.

When should you call contiguous() yourself? When one expensive view is read many times by different kernels with different access patterns, or when an index expression has become so tangled (pads inside reshapes inside pads) that it blocks optimizations. Most of the time, let the scheduler decide what to materialize — that is Chapter 11's topic.

7.10History note: from ShapeTracker to index expressions — and why

Historical note (older tinygrad, not this checkout) Older versions represented a view as a ShapeTracker: a stack of Views, each with a shape, strides, an offset and an optional mask, and a large amount of code tried to merge views (e.g. "is this reshape of this permuted view still expressible with strides?"). When merging failed, the stack grew, and the final index came from walking the stack. Strides are a lossy, closed-form summary: they can express PERMUTE, EXPAND (stride 0), SHRINK (offset) and simple RESHAPEs, but not every reshape of a permuted or padded view, nor flip without negative strides.

In this version there are no strides anywhere. The graph keeps the literal chain of movement ops, and the meaning of a view is the index expression rangeify builds from it. The trade-offs:

  • One mechanism for everything. Composition is function composition; "can these two views be merged?" becomes "how small does symbolic make this expression?" — and every improvement to the symbolic engine (Chapter 6) improves views for free.
  • Fewer primitives. Without strides there is no reason to have FLIP or a strided SHRINK; they are compositions that simplify.
  • Symbolic shapes just work, because shapes and offsets are UOps (the STACK-of-CONST args).
  • The cost is that the simplifier must be strong (div/mod folding with range analysis, valid simplification) — otherwise the kernel would literally compute twelve ops' worth of index math for a flip.

The rest of this story — how a RANGE is created per axis, how ranges flow through reduces and multiple consumers, and what gets materialized — is Chapter 10: Rangeify. When you get there, remember: every movement op you met here is consumed by one call to apply_movement_op, and then removed (remove_movement_op_after_rangeify, ).

Chapter summary

  • Five primitive movement ops: RESHAPE, PERMUTE, EXPAND, PAD, SHRINK (+ UNSHARD for multi-device). No FLIP, no strides. EXPAND prepends dims; PAD/SHRINK store (offset, size).
  • Args are UOps in src[1:] (STACKs of CONSTs, decoded by marg); shapes are inferred eagerly by UOp._shape; buffers are flat and every shape is a RESHAPE on top.
  • Every Tensor movement method (view/reshape, T, flatten, squeeze, slicing, expand, repeat, roll, flip, pad modes, cat/stack) reduces to those primitives — sometimes via clever tricks (flip's anti-diagonal, strided slicing by reshape+shrink).
  • A movement op is an index function: apply_movement_op maps output ranges to input indices; PAD adds a validity mask that rangeify turns into WHERE(valid, load, 0).
  • Chains compose by function composition and are collapsed by symbolic simplification (flip: 12 ops → 5 - r0); mop_cleanup merges trivial neighbours early.
  • Views are free until a kernel reads them, and then they are just address arithmetic in that kernel. contiguous() = STAGE; a contiguous range of a buffer becomes a sub-buffer view with 0 kernels.
  • Next: Chapter 8 builds matmul and conv out of these pieces; Chapter 10 shows the full rangeify that consumes them.
