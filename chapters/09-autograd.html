CHAPTER 09Autograd as graph rewriting

In tinygrad, backward() does not compute anything. It walks the lazy UOp graph of your loss in reverse, applies one small rewrite rule per op, and returns more lazy UOps. The gradient graph is made of the same bricks as the forward graph (Chapter 8), it is scheduled together with the forward graph, and it fuses with it into the same kernels. This chapter shows the whole engine — about 130 lines in tinygrad/mixin/gradient.py — rule by rule, on real graphs with real numbers.

9.1Intuition: walk the graph backwards, multiplying local slopes

Analogy: a river delta, in reverse The forward graph is a set of streams merging into one river (the scalar loss). Pour one bucket of "sensitivity" into the river mouth (\(\partial L/\partial L = 1\)) and walk upstream. At every junction the flow is split according to a local rule (an ADD sends the full flow up both branches; a MUL sends each branch the flow times the other branch's value; a reshape just reshapes the water). Where two streams came from the same spring, their flows add up. What arrives at each spring is \(\partial L/\partial\,\text{spring}\).

That is reverse-mode automatic differentiation: the chain rule \( \frac{\partial L}{\partial x} = \sum_{u \in \text{consumers}(x)} \frac{\partial L}{\partial u}\frac{\partial u}{\partial x} \) evaluated from the output back to the inputs. The two things that make tinygrad's version special:

  • The local rules are a PatternMatcher (pm_gradient, Chapter 5) — one UPat per op, each returning the gradients of the op's sources as UOp expressions.
  • The result is a graph, not numbers. \(\partial L/\partial u\) is a UOp built from the forward UOps; nothing runs until you realize it.

9.3The engine: compute_gradient

tinygrad/mixin/gradient.py:107 — _deepwalk and compute_gradient
def _deepwalk(root:UOp, targets:set[UOp]) -> tuple[list[UOp], dict[UOp, bool]]:
  # compute the target path (top down)
  in_target_path: dict[UOp, bool] = {}
  root.topovisit(lambda u: any(in_target_path[x] or x in targets for x in u.src), in_target_path)
  # don't flow through DETACH or anything not in target path
  return [node for node in in_target_path if node.op is not Ops.DETACH and in_target_path[node]], in_target_path

def compute_gradient(root:UOp, root_grad:UOp, targets:set[UOp]) -> dict[UOp, UOp]:
  walk, in_target_path = _deepwalk(root, targets)
  grads: dict[UOp, UOp] = {root: root_grad}
  for t0 in reversed(walk):
    if t0 not in grads or grads[t0].op is Ops.NOOP: continue
    # CALL: pass needed param set so backward only computes required gradients
    if t0.op is Ops.CALL:
      needed = {i for i, arg in enumerate(t0.src[1:]) if arg in targets or in_target_path.get(arg, False)}
      lgrads:tuple[UOp|None, ...]|None = call_gradient(grads[t0], t0, needed)
    else:
      lgrads = cast(tuple[UOp|None, ...]|None, pm_gradient.rewrite(t0, ctx=grads[t0]))
    if lgrads is None: raise RuntimeError(f"failed to compute gradient for {t0.op}\n\nin {str(t0)[0:1000]}...")
    assert len(lgrads) == len(t0.src), f"got {len(lgrads)} gradient, expected {len(t0.src)}"
    for k,v in zip(t0.src, lgrads):
      if v is None: continue
      # a shaped edge's gradient is summed to its source's shape
      if k._shape is not None and v._shape is not None and k._shape != v._shape:
        v = v.cast(sum_acc_dtype(v.dtype))._rop(Ops.ADD, broadcast_axes(k.shape, v.shape)).reshape(k.shape).cast(v.dtype)
      if k in grads and grads[k].op is not Ops.NOOP:
        if v.op is Ops.SINK and grads[k].op is Ops.SINK:
          grads[k] = UOp.sink(*[p + n if (p.op is not Ops.NOOP and n.op is not Ops.NOOP) else
                                 n if p.op is Ops.NOOP else p for p, n in zip(grads[k].src, v.src)])
        else: grads[k] = grads[k] + v
      else: grads[k] = v
  return grads

Step by step:

  1. _deepwalk marks every node that lies on a path from the root down to some target (topovisit computes, bottom-up, "does any of my sources lead to a target?"). Nodes off the path — constants, other parameters you did not ask about — are never visited. DETACH nodes are dropped from the walk, which is all it takes to stop gradient flow.
  2. The walk is a toposort (sources before consumers); iterating it reversed visits every consumer before its sources — exactly what reverse mode needs: by the time we reach x, all of x's consumers have contributed to grads[x].
  3. For each node with a gradient, pm_gradient.rewrite(t0, ctx=grads[t0]) returns a tuple with one entry per source (or None for "no gradient", e.g. the condition of a WHERE or the shape-argument sources of a movement op).
  4. Broadcast summing: if an entry's shape differs from its source's shape — because elementwise ops broadcast implicitly (Chapter 7) — it is summed over broadcast_axes and reshaped. This one line is the gradient of every implicit broadcast and of EXPAND.
  5. Accumulation: a source reached through several consumers gets grads[k] + v: the "sum over consumers" of the chain rule.
Why does iterating reversed(walk) guarantee that grads[x] is complete before x's own rule runs?
Toposort order means sources come first. Reversed, consumers come first. Each consumer adds its contribution to grads[x], so when the loop reaches x the sum over all consumers is done.

9.5Watching it run: reverse mode on real graphs

Back to sum(x*x). Its forward graph is REDUCE(ADD)(MUL(x, x)). The walk visits REDUCE, then MUL:

  • REDUCE (ADD) rule: ctx._broadcast_to(src.shape) — the scalar 1 becomes EXPAND(3,) of a constant 1.
  • MUL rule: (src1 * ctx, src0 * ctx) = (x * 1⃗, x * 1⃗). Both entries are for the same source x — and thanks to hash-consing both are literally the same UOp. compute_gradient accumulates: grads[x] = x·1⃗ + x·1⃗. That is the printed gradient ADD(MUL(x, expand…), MUL(x, expand…)), and \(2x = [2,4,6]\).

Things to notice while stepping:

  • neuron: relu is WHERE(0 < h, h, 0). The WHERE rule gives None to the condition, so the CMPLT node never receives a gradient and is skipped. The constant 0.0 branch does receive a (useless) gradient — compute_gradient records it but never walks the CONST, and since nobody asks for it, it is never computed. The bias b has shape (1,) while the ADD has shape (3,): the gradient is summed over the broadcast axis (broadcast_summed).
  • matmul: the walk passes REDUCE → REDUCE → PERMUTE → MUL → (PERMUTE, RESHAPE) → RESHAPE; each movement op inverts itself. See §9.7.
  • sigmoid: no sigmoid rule exists. The walk goes through RECIP, ADD, EXP2 and MUL — and the numbers come out as \(\sigma(z)(1-\sigma(z))\): 0.235 and 0.1966 for \(z = 0.5, -1\).

9.6Movement ops: the gradient is the inverse movement

A movement op is a pure re-indexing, so its Jacobian is a 0/1 matrix and the gradient just routes values back through the inverse re-indexing:

Read the rows: pad((1,1)) drops the first and last upstream values; shrink puts zeros where nothing was read; expand(3,6) sums the three rows (1+7+13 = 21); and flip — 12 primitive ops in the forward graph — produces the reversed upstream gradient, because each of its PADs, SHRINKs, RESHAPEs and PERMUTEs is inverted in turn.

The reduce ↔ expand duality In this IR EXPAND adds leading axes and REDUCE removes leading axes (Chapter 7 and 8). Their gradients are each other: \[ \text{REDUCE}_{\text{ADD}}:\ \frac{\partial L}{\partial x} = \text{EXPAND}\Big(\frac{\partial L}{\partial \text{ret}}\Big) \qquad \text{EXPAND}:\ \frac{\partial L}{\partial x} = \text{REDUCE}_{\text{ADD}}\Big(\frac{\partial L}{\partial \text{ret}}\Big) \] The REDUCE rule calls reduce_gradient → ctx._broadcast_to(src.shape); the EXPAND rule returns ctx unchanged and the generic shape check in compute_gradient calls _rop(Ops.ADD, broadcast_axes(...)). Summation and copying are adjoint linear maps — the gradient of "read once, use many times" is "add up all the uses".

9.7MAX, WHERE, and the matmul transpose that nobody wrote

tinygrad/mixin/gradient.py:8 — reduce_gradient
def reduce_gradient(ctx:UOp, ret:UOp, op:Ops):
  if op == Ops.ADD: return (ctx._broadcast_to(ret.src[0].shape),)
  if op == Ops.MAX:
    # count the ties in the acc dtype, the count can overflow the gradient dtype
    mask = ret.src[0].eq(ret).cast(sum_acc_dtype(ctx.dtype))
    return ((mask/mask._rop(Ops.ADD, tuple(range(ret.arg[1])))).cast(ctx.dtype) * ctx,)
  if op == Ops.MUL:
    # d(prod x)/dx_j = prod_{i!=j} x_i: ret/x_j whenever x_j != 0 (any zero makes ret 0), else the product of the others
    safe_x, axes = (is_zero:=(x:=ret.src[0]).eq(0)).where(1, x), tuple(range(ret.arg[1]))
    zero_count = is_zero.cast(sum_acc_dtype(is_zero.dtype))._rop(Ops.ADD, axes)
    return (ctx * is_zero.where(zero_count.eq(1).where(safe_x._rop(Ops.MUL, axes), 0), ret/safe_x),)
  • Elementwise MAX sends the gradient to the larger input and splits ties 50/50 (x.eq(y).where(ctx * 0.5, 0)) — the reason relu is not written with maximum (Chapter 8).
  • REDUCE MAX builds a mask of the positions equal to the max, divides by the number of ties (counted in the accumulation dtype so it cannot overflow), and multiplies by ctx: \( \partial \max / \partial x_i = [x_i = m] / \#\{j: x_j = m\} \).
  • REDUCE MUL handles zeros carefully: \(\partial \prod x / \partial x_j = \prod_{i\ne j} x_i\), computed as ret/x_j when \(x_j \ne 0\) and as the product of the others when exactly one zero exists.
  • WHERE: (None, c.where(ctx, 0), c.where(0, ctx)) — each branch gets the gradient only where it was selected; the condition gets none.

Now matmul. Nobody wrote "the gradient of A@B with respect to A is G @ Bᵀ" — it falls out of MUL + REDUCE + movement rules:

=== 3. matmul: dL/dA = G @ B.T and dL/dB = A.T @ G fall out of the MUL + REDUCE + movement rules
forward : REDUCE<ADD,2>(REDUCE<ADD,1>(permute(2, 0, 1)(MUL(A, B))))
dL/dA   : reshape(2, 3)(reshape(2, 1, 3)(REDUCE<ADD,1>(permute(1, 0, 2)(MUL(B, permute(1, 2, 0)(expand(3,)(expand(2, 2)(cast<f32>(1.0)))))))))
dL/dA   = [[1.0, 1.0, 2.0], [1.0, 1.0, 2.0]]    expected ones(2,2) @ B.T = [[1.0, 1.0, 2.0], [1.0, 1.0, 2.0]]
dL/dB   = [[5.0, 5.0], [7.0, 7.0], [9.0, 9.0]]    expected A.T @ ones(2,2) = [[5.0, 5.0], [7.0, 7.0], [9.0, 9.0]]

Read dL/dA from the inside out: the two REDUCEs' gradients are EXPANDs of the constant 1 (expand(2,2) then expand(3,) — a new leading axis, exactly undoing a REDUCE that removed a leading axis); the PERMUTE's gradient is the inverse permutation (1,2,0); the MUL's gradient for A is "the other source", B, times that; and because A was (2,1,3) but the product is (2,2,3), compute_gradient sums over the broadcast axis (permute(1,0,2) + REDUCE); finally two RESHAPEs undo A's reshapes. That sum over the N axis of \(B_{kj}G_{ij}\) is precisely \((G B^\top)_{ik}\).

What is the gradient of x.max() for x = [1, 3, 3] (upstream 1)?
reduce_gradient for MAX: mask = [0,1,1], divided by the tie count 2. The captured worked example "REDUCE (MAX)" in the rule explorer shows exactly [0.0, 0.5, 0.5], and the finite difference agrees.

9.8DETACH, CONTIGUOUS_BACKWARD and STAGE

Three ops exist mainly to talk to the autograd and the scheduler:

  • DETACH (x.detach(), ): identity in the forward pass. _deepwalk removes it from the walk, so no gradient flows through it. softmax and logsumexp detach the max they subtract (it cancels mathematically, so differentiating through it would only add work).
  • CONTIGUOUS_BACKWARD (x.contiguous_backward(), ): identity in the forward pass; its gradient rule is ctx.contiguous() — "materialize the gradient here". A way to cut a huge fused backward kernel without touching the forward.
  • STAGE (contiguous()): gradient passes straight through ((ctx,)).

Before scheduling, both DETACH and CONTIGUOUS_BACKWARD are simply deleted (earliest_rewrites, prepare.py:196) — by then the gradient graph has been built and they have done their job.

=== 6. DETACH stops the gradient; the graph walk skips it
d/dz (z * z.detach()).sum() = [2.0, 3.0]  (only one branch contributes)
d/dz (z * z).sum()          = [4.0, 6.0]

9.9Gradients are lazy UOps: forward and backward fuse

Because a gradient is just a UOp graph that reuses the forward UOps (MUL's rule mentions ret.src[1], EXP2's rule mentions ret itself), the scheduler sees one big DAG containing loss and gradients. It decides once what to materialize and what to fuse (Chapter 11). Realize them separately and it cannot share:

The pitfall that line 5 shows realize() replaces a tensor's UOp with its buffer (the scheduler rewrites all live tensors through becomes_map). If you realize the loss and then ask for its gradient, the loss is a BUFFER with no path to the weights, and you silently get zeros. Build the gradients first (or call backward()) and realize everything together — which is also the fastest option.
Why is "forward + backward at once" (10 kernels) cheaper than forward then backward (5 + 8 = 13)?
The backward-only schedule starts with r_16_32_8, r_16_4_32, r_16_4, r_16_4 — the same forward kernels again — because the gradient UOps reference forward UOps that were not kept as buffers.

Different angle: forget the rules and check the result against the definition of a derivative. A 3→5→3 MLP with relu and cross-entropy:


print("\n=== 5. MLP: gradients of a real loss, checked against finite differences")
Tensor.manual_seed(1)
X = Tensor.randn(4, 3).realize(); Y = Tensor([0, 2, 1, 2]).realize()
W1, b1 = Tensor.randn(3, 5).realize(), Tensor.zeros(5).contiguous().realize()
W2, b2 = Tensor.randn(5, 3).realize(), Tensor.zeros(3).contiguous().realize()
def loss_fn(W1, b1, W2, b2): return ((X @ W1 + b1).relu() @ W2 + b2).sparse_categorical_crossentropy(Y)
loss = loss_fn(W1, b1, W2, b2)
grads = loss.gradient(W1, b1, W2, b2)
print("loss =", round(loss.item(), 5), " gradient shapes:", [g.shape for g in grads])
eps = 1e-3
W1l, gW1 = W1.tolist(), grads[0].tolist()
for (i, j) in [(0, 0), (1, 3), (2, 4)]:
  plus = [row[:] for row in W1l]; plus[i][j] += eps
  minus = [row[:] for row in W1l]; minus[i][j] -= eps
  fd = (loss_fn(Tensor(plus), b1, W2, b2).item() - loss_fn(Tensor(minus), b1, W2, b2).item()) / (2 * eps)
  print(f"dL/dW1[{i},{j}]  autograd {gW1[i][j]: .5f}   finite-diff {fd: .5f}")

What breaks, and other edges

  • Non-scalar loss without gradient=: assertion "backward must be called on a scalar tensor". Pass an upstream gradient of the same shape (as section 4 of the example does).
  • Integer tensors: "only float Tensors have gradient"; weak (Python-constant) tensors cannot be targets either.
  • Ops with no rule (e.g. BITCAST returns None; comparisons return None): gradient simply stops there.
  • Custom kernels / CALLs: call_gradient () either uses a user-supplied grad_fxn (e.g. nn.Embedding's backward) or differentiates the call's body and wraps the result in a new backward CALL — functions (Chapter 18) are differentiable too.
  • Assign/in-place: the AFTER/STORE rules route gradients through assignments, including partial stores through a view (partial_store_gradient).

Chapter summary

  • Tensor.gradient(*targets) → compute_gradient(root, root_grad, targets); backward() targets every live float tensor in the graph (no requires_grad) and accumulates into .grad.
  • _deepwalk keeps only nodes on a path to a target (DETACH excluded); iterating the toposort in reverse processes consumers before sources.
  • pm_gradient has one rule per primitive; composites (sub, div, exp, sigmoid, softmax, matmul, conv) get gradients for free by chaining.
  • Movement gradients are inverse movements; REDUCE and EXPAND are each other's gradient; implicit broadcasts are summed by one generic line.
  • MAX splits ties, WHERE routes by condition, REDUCE MAX/MUL are handled in reduce_gradient; DETACH / CONTIGUOUS_BACKWARD steer autograd and are removed before scheduling.
  • Gradients are lazy UOps that reuse forward UOps, so forward+backward schedule and fuse together (10 kernels vs 5+8). Never realize the loss before building its gradients.
