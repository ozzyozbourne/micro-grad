CHAPTER 02Tensors are lazy

A tinygrad Tensor is a thin handle around one UOp. Every method you call — +, .exp(), .T, .sum() — builds a new UOp out of the old ones and wraps it in a new Tensor. Nothing is computed. This chapter opens up the handle, watches the graph grow node by node, and then finds out exactly which calls make tinygrad finally do the work, and what happens to every other live Tensor when it does.

All outputs are from tinygrad commit 6a404871 on DEV=CPU. If you remember older tinygrad, the LazyBuffer class is gone. The .lazydata attribute became .uop, and the "lazy buffer" is now simply the tensor's UOp graph. requires_grad no longer exists as a slot either (see 2.2).

2.1The idea: a Tensor is a promise

In NumPy or eager PyTorch, c = a * b allocates memory for c and fills it before the line returns. In tinygrad, c = a * b returns in microseconds no matter how big a and b are, because all it does is make a node MUL(a.uop, b.uop). The tensor c is a promise: "if anyone ever asks, my value is a times b".

Analogy: a spreadsheet formula Typing =A1*B1+1 into a cell stores the formula, not a number. tinygrad Tensors are cells holding formulas that refer to other cells. The twist: tinygrad doesn't recompute on every keystroke. It waits until you read a cell (.tolist(), .item(), .numpy()) or explicitly say .realize(). Then it compiles all the formulas you need into as few kernels as possible. Afterwards it replaces the formula in that cell, and every reference to it, with the number it computed.

That gives three questions, and this chapter answers each one with real code and real output:

  1. What does the promise look like? It is a .uop graph: what each op adds, how creation works, how broadcasting is represented (2.2–2.6).
  2. When is it kept? The calls that trigger realization, and the many that don't (2.8).
  3. What happens when it is kept? realize() → linear_with_vars → run_linear. After that, every live tensor that referenced the computed value is rewritten to read the buffer instead (2.7, 2.11).

2.3Every op builds a UOp, nothing is computed

Every Tensor method ends in Tensor._apply_uop. It unwraps the input tensors to their UOps, calls a UOp-level function, and wraps the result in a brand-new Tensor. The constructor is skipped (Tensor.__new__). The inputs are never modified:

tinygrad/tensor.py:103
  def _apply_uop(self, fxn:Callable[..., UOp], *x:Tensor, **kwargs) -> Tensor:
    srcs = (self,)+x
    new_uop: UOp = fxn(*[t.uop for t in srcs], **kwargs)
    # directly create the Tensor
    ret = Tensor.__new__(Tensor)
    ret.uop, ret.grad, ret.is_param = new_uop, None, True
    # add to all_tensors after construction succeeds
    all_tensors[weakref.ref(ret)] = None
    return ret

  # alu, _uop, _wrap_uop and const are used by the mixins
  def alu(self, op: Ops, *src: Tensor) -> Tensor: return self._apply_uop(lambda *u: u[0].alu(op, *u[1:]), *src)

So d = (a*b + 1).exp().sum() is four _apply_uop calls, and the kernel counter stays at zero. The printout below is a compact one-line-per-node view of d.uop (op, dtype, shape, arg). Notice that exp is not a primitive. It became EXP2(x * 1/ln 2), the first sign that the Tensor API is sugar over a small set of UOps.

  • x + 1 adds a CONST 1.0 with dtype weakfloat. Python literals stay weak (Chapter 3), and the CONST has shape (). It is broadcast by the ADD's shape rule without an EXPAND (2.6).
  • relu is WHERE(CMPLT(0.0, x), x, 0.0): one CONST used twice. -x is x * -1.
  • Movement ops carry their argument as UOps: x.T is PERMUTE(X, STACK(1, 0)), and reshape takes a CONST/STACK shape. Shapes are data in the graph, which is how symbolic shapes work (Chapter 6).
  • sum(axis=-1) = REDUCE(PERMUTE(X, (1,0))) with arg (Ops.ADD, 1). UOp._rop permutes the reduced axes to the front, and the arg says "reduce the first 1 axis" (Chapter 9).

2.4The mixins: one API, two classes

Where are exp, sum, reshape and relu defined? Not in tensor.py. They live in tinygrad/mixin/, and both Tensor and UOp inherit them. A mixin method calls a handful of hooks (alu, _mop, _rop, const, _wrap_uop). The Tensor implements each hook with _apply_uop, and the UOp implements it by building the node directly. The same Python code therefore builds the same graph in both classes:

### 3. Tensor and UOp share the same mixins: the Tensor graph IS the UOp graph

UOp MRO also contains: ['RandMixin', 'OpMixin', 'ElementwiseMixin', 'CreationMixin', 'ReduceMixin', 'DTypeMixin', 'MovementMixin']

(a*b+1).uop is (a.uop*b.uop+1) prints True, so it is the same object, thanks to hash-consing. The Tensor graph is the UOp graph. Click a class in the method-resolution order to see what it owns:

Why share the mixins? The scheduler and codegen also need to write x.reshape(...), x + 1 or x.where(a, b) on raw UOps while rewriting graphs. Sharing one implementation means a pattern written in the compiler and a line written by a user produce identical nodes. It also means hash-consing dedups them, and there is no separate "Tensor op" layer to keep in sync. The old LazyBuffer layer existed only to bridge that gap, and it is gone.

UOp._frompy packs the list with struct.pack into a BUFFER on the PYTHON device (host memory), already allocated and filled. Then __init__ calls copy_to_device("CPU"), which adds a COPY. The data does not reach the CPU device until a copy kernel runs. That copy is the one kernel Tensor([1., 2.]).realize() runs (2.8). With device="PYTHON" there is no COPY. dtype comes from dtypes.from_py: ints → int32, floats → float32 (DEFAULT_INT/DEFAULT_FLOAT). bfloat16/fp8 have no struct format, so they are packed as float32 and given a CAST.

Tensor(3.5) is just UOp.const(3.5): a CONST with no device (device=None) and the weak dtype weakfloat. It has no storage and never will on its own. To read it (.item()), _buffer first clones it to CPU (x.clone("CPU")), and that clone commits the weak dtype to float32.

ones/zeros/full are EXPAND(CONST), a broadcast scalar that costs nothing. By default (buffer=True) it is stored into a fresh ALLOC: AFTER(ALLOC, STORE(ALLOC, EXPAND(CONST))), which means "this allocation, after the store into it". That is why Tensor.ones(4).realize() runs one kernel. With buffer=False you get the bare EXPAND(CONST), still weak and deviceless.

Tensor.rand(3) builds a 101-UOp graph: a threefry counter-based PRNG written in UOps (RandMixin.rand). The key and counter live in per-device state buffers, so realizing it runs 5 kernels (counter update + the random bits + conversion to float). Random numbers are just more lazy graph (Chapter 8).

What is the graph of Tensor([1, 2, 3]) on a default DEV=CPU machine, and what dtype does it have?
Lists go through _frompy into a host buffer on the PYTHON device. The tensor's device is CPU, so __init__ adds a COPY. dtypes.from_py of a list of ints is DEFAULT_INT = int32. Only scalars become CONSTs, and only they stay weak.

2.6Broadcasting: a shape rule, not an op

Broadcasting in tinygrad uses two separate mechanisms, and confusing them is a common source of misreading graphs:

  1. ALU ops broadcast implicitly. x + y with shapes (3,1) and (4,) produces an ADD whose srcs have their original shapes. No EXPAND is inserted. The UOp._shape property computes the output shape with _broadcast_shape. "Broadcasting lives in _shape property now", as the source puts it. Set DISALLOW_BROADCAST=1 to turn this into an error and find accidental broadcasts.
  2. Explicit expand (and _broadcast_to, used by assign and friends) emits real movement ops: RESHAPE to squeeze away the size-1 dims being stretched, EXPAND which only adds dims on the left, and a PERMUTE to put the new dims where they belong.
tinygrad/uop/ops.py:76 — the rule
def _align_left(*shapes:tuple[sint, ...]) -> tuple[tuple[sint, ...], ...]:
  max_dim = max(len(s) for s in shapes)
  return tuple((1,)*(max_dim-len(s))+s for s in shapes)
def _broadcast_shape(*shapes:tuple[sint, ...]) -> tuple[sint, ...]:
  if all_same(shapes): return shapes[0]
  # per right-aligned dim: sizes of 1 broadcast to the others, which must all agree
  ret = []
  for sizes in zip(*_align_left(*shapes)):
    if len(rest:=dedup([s for s in sizes if isinstance(s, UOp) or s != 1])) > 1:
      raise IndexError(f"shape mismatch: objects cannot be broadcast to a single shape {shapes}")
    ret.append(rest[0] if rest else 1)
  return tuple(ret)

    kept = tuple(i for i in range(len(self.shape)) if i not in expand_at)

    expanded = squeezed._mop(Ops.EXPAND, arg=new_shape[:n_left] + tuple(new_shape[n_left+i] for i in expand_at))

    perm = tuple(range(n_left)) + tuple(

    return expanded.permute(perm)

2.7realize(): keeping the promise

tinygrad/tensor.py:217
  @disable_gc()
  def realize(self, *lst:Tensor, do_update_stats=True) -> Tensor:
    """Triggers the computation needed to create these Tensor(s)."""
    to_realize = [x for x in (self,)+lst if x.uop.base.needs_storage()]
    if len(to_realize):
      linear, var_vals = Tensor.linear_with_vars(*to_realize)
      run_linear(linear, var_vals, update_stats=do_update_stats)
    return self

Three lines carry the weight:

  • needs_storage() filters out tensors that are already buffers (or views of one), which is why a.realize() on a realized tensor runs 0 kernels.
  • linear_with_vars is the whole scheduler entry point (Chapters 10–12). The part that belongs to this chapter is the start and the end of it:
    1. It refuses to realize a weak dtype that lives on a device ("weakness ends where storage begins").
    2. For each output that needs storage, it builds buf = UOp.new_buffer(device, size, dtype) and replaces the compute by buf.after(buf.store(compute)). A pending ALLOC with bind_on_realize becomes a real BUFFER.
    3. It drops the AFTERs (pm_drop_after) to get becomes_map: compute UOp → its storage.
    4. It calls _apply_map_to_tensors(becomes_map | tensor_map, name="bufferize") before anything runs, so every live tensor already points at the buffer that is about to be filled.
    5. It returns create_linear_with_vars(sink): the LINEAR of CALLs.
  • run_linear executes the CALLs and fills the buffers (Chapter 17).
tinygrad/tensor.py:18 — the rewrite that reaches every live tensor

    new_sink = sink.substitute(applied_map, name=f"substitute {name}", walk=True)

    for t,ns in zip(scope_tensors, new_sink.src):

The visitor marks a node "in scope" if it is a key of the map or has an in-scope source. Only tensors whose graph touches a replaced node get rewritten. numpy() takes the same _buffer() path. The subtle part is the line x = self.contiguous(). What gets realized is a new tensor x (a STAGE of self), not self. The result is copied out and x dies, but self.uop still holds the lazy graph. Reading an unrealized tensor twice therefore computes it twice:

Each tolist() ran 3 kernels: the two COPYs of a and b from the PYTHON device (still pending, since they were never realized) plus the ADD. After an explicit g.realize() the tensor is a BUFFER and reads are free. Rule of thumb: realize() a tensor you will read more than once. bool() is deliberately undefined, so if t: can't hide a sync.

2.9contiguous(): a STAGE marker

tinygrad/mixin/elementwise.py:59
  def contiguous(self) -> Self:
    uop = self._uop
    if self.dtype in dtypes.weaks or uop.op is Ops.STAGE or self.device is None or uop.has_buffer_identity(): return self
    return self._wrap_uop(uop.alu(Ops.STAGE))

contiguous() computes nothing. It wraps the graph in STAGE, which tells the scheduler "materialize this value into its own buffer here; don't fuse it into consumers as index math". It is a no-op if the tensor already is a buffer (has_buffer_identity), is weak, or has no device.

  • STORE(buf, value) has dtype void. It is a pure effect.
  • AFTER(buf, STORE) has buf's dtype and shape. It is the value "buf, but only after the store happened". That gives the scheduler an explicit ordering edge. Anything reading w afterwards reads the AFTER, so it cannot be scheduled before the write.
  • The value ADD(BUFFER, 1) reads the same buffer it writes (shared node). The scheduler handles that read-before-write (WAR hazard) in Chapter 12.
  • Assigning to a view (w[1:].assign(...)) takes the other branch. The STORE goes into the view and every live tensor sharing the base storage is rewritten to read target.after(store).

2.11all_tensors: weak references to every live tensor

all_tensors is a module-level dict[weakref.ref[Tensor], None], used as an ordered set. Both __init__ and _apply_uop add the new tensor, and __del__ removes it. Weak references mean the registry never keeps a tensor alive. As soon as Python drops your last reference, the tensor leaves the registry and _apply_map_to_tensors stops considering it:

### 10. weak references: dead tensors leave all_tensors
after creating tmp: 1 new live tensors
after del tmp: weakref is dead -> True | net new live tensors: 0

Why the registry exists at all: graph rewrites happen on UOps, but users hold Tensors. Without it, realizing e could not reach the f you are holding (2.7). The same mechanism serves assign on views, multi-device sharding and gradient bookkeeping. Every "rewrite the world" step goes through _apply_map_to_tensors. Running VIZ=1 shows these steps as substitute bufferize entries.

Deep dive: why realize is decorated with @disable_gc()

_apply_map_to_tensors iterates over list(all_tensors) and dereferences each weakref. If Python's cyclic GC ran in the middle of a realize, tensors could vanish between the scope scan and the assignment, and __del__ would mutate all_tensors while it is being walked. disable_gc() (helpers.py) turns off the cyclic collector for the duration, which also avoids random GC pauses inside the scheduler. Reference-count frees still happen, which is why the dict is copied with list(...) first.

You hold only f = (a*b) + 1; the tensor for a*b was a temporary and is gone. You call f.realize(). Which tensors does _apply_map_to_tensors rewrite?
The visitor only selects tensors whose graph reaches a key of applied_map. Dead tensors were removed from all_tensors by __del__, and their weakrefs would be None anyway.

Chapter summary

  • A Tensor has three slots: uop, grad, is_param. Shape, dtype and device are read from the UOp.
  • Every method goes through _apply_uop and builds a new UOp. The methods are shared mixins (tinygrad/mixin/) used by both Tensor and UOp, so the Tensor graph is the UOp graph (hash-consed, identical objects).
  • Creation fingerprints: list → COPY(BUFFER@PYTHON); scalar → weak deviceless CONST; empty → RESHAPE(ALLOC); ones/full → AFTER(ALLOC, STORE(ALLOC, EXPAND(CONST))); rand → a ~100-UOp threefry graph.
  • ALU broadcasting is implicit in UOp._shape (_broadcast_shape). Explicit expand is RESHAPE → EXPAND(left) → PERMUTE.
  • realize() = linear_with_vars (bufferize + _apply_map_to_tensors + schedule) + run_linear. Realization rewrites every live tensor that depended on the result.
  • tolist/item/numpy/data realize a contiguous() copy via _buffer, not the tensor itself. contiguous() = STAGE, assign() = AFTER(STORE). all_tensors holds weak references to every live tensor.
