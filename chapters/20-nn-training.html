20.1Intuition: a training step is just a bigger lazy graph

In PyTorch a training step is three phases that run one after the other: forward runs kernels, backward() runs more kernels, and optimizer.step() runs yet more kernels, each one as soon as Python reaches the line. In tinygrad none of those three lines computes anything:

  • model(X) and .sparse_categorical_crossentropy(Y) add UOps to a graph (Chapter 2).
  • .backward() adds the gradient UOps to the same graph and hangs a lazy Tensor on each parameter's .grad (Chapter 9).
  • opt.schedule_step() adds the optimizer math and turns each parameter into AFTER(BUFFER, STORE(BUFFER, new_value)): a promise that this buffer will be overwritten.

Only loss.realize(*opt.schedule_step()) hands the whole thing (forward, backward and update, one DAG) to the scheduler. The scheduler is free to fuse across what PyTorch would call phase boundaries and to order kernels in any way the data dependencies allow, and the result is a single LINEAR that can be captured and replayed (Chapter 18).

AnalogyA PyTorch training step is a cook who follows a recipe line by line. A tinygrad training step is a recipe card handed to a kitchen manager. The manager reads the whole card (including "afterwards, put the new seasoning back in the jar"), plans the stations, and only then lights the stoves. Because the plan is written down, it can be photocopied and reused tomorrow: that is TinyJit.
The key ideaThe optimizer update is not an eager in-place mutation. It is expressed with Tensor.assign, which builds STORE + AFTER UOps. The step is therefore itself a lazy, schedulable, cacheable, JIT-able graph, and the same scheduler that fuses x*2+1 also plans "read w, compute w − lr·update, write w".

20.2nn layers: plain objects holding Tensors

tinygrad/nn/__init__.py is 417 lines. There is no Module base class, no parameter registration, no hooks, no .to(device). A layer is a Python class whose __init__ creates Tensors as attributes and whose __call__ calls Tensor methods. Here is Linear in full:

tinygrad/nn/__init__.py — class Linear
class Linear:
  def __init__(self, in_features:int, out_features:int, bias=True):
    bound = 1 / math.sqrt(in_features)
    self.weight = Tensor.uniform(out_features, in_features, low=-bound, high=bound)
    self.bias = Tensor.uniform(out_features, low=-bound, high=bound) if bias else None

  def __call__(self, x:Tensor) -> Tensor: return x.linear(self.weight.transpose(), self.bias)

The work happens in Tensor methods defined in the mixins: Tensor.linear calls Tensor.dot, which reshapes both operands so they broadcast, multiplies, and sums over the shared axis:

# mixin/op.py, dot() (abridged)

return (x*w).sum(-1, dtype=dtype).cast(least_upper_dtype(x.dtype, w.dtype) if dtype is None else dtype)

There is no "matmul op" in tinygrad. A matrix multiply is MUL of two broadcast views, followed by REDUCE(ADD) (Chapter 8). Even the weight initialization (Tensor.uniform) is lazy: it is a threefry RNG graph until something realizes it.

20.3nn.state: state dicts are a walk over __dict__

With no Module class, how does tinygrad find the parameters? get_state_dict walks the object recursively: Tensors are leaves; objects are expanded through __dict__; lists, tuples and dicts are expanded with index or key prefixes; namedtuples through _asdict. get_parameters is just list(get_state_dict(obj).values()).

def get_state_dict(obj, prefix:str='', tensor_type=Tensor) -> dict[str, Tensor]:
  if isinstance(obj, tensor_type): return {prefix.strip('.'):obj}
  if hasattr(obj, '_asdict'): return get_state_dict(obj._asdict(), prefix, tensor_type)  # namedtuple
  if isinstance(obj, OrderedDict): return get_state_dict(dict(obj), prefix, tensor_type)
  if hasattr(obj, '__dict__'): return get_state_dict(obj.__dict__, prefix, tensor_type)
  ...  # lists/tuples -> "prefix.i.", dicts -> "prefix.key."
Because get_parameters returns every Tensor it finds, BatchNorm's running_mean is in the list too. The optimizer separates the two kinds with the Tensor.is_param flag: BatchNorm marks its statistics with .is_param_(False) (nn/__init__.py:38), and Optimizer.__init__ splits its input into self.params (updated) and self.buffers (only realized alongside the step).

Checkpoints are lazy too

safe_save writes the safetensors format: an 8-byte little-endian header length, a JSON header (dtype, shape, data_offsets), then the raw bytes. Nothing is read until you realize, and load_state_dict does exactly that by calling v.replace(state_dict[k].to(v.device)), then realize().

20.4nn.optim: an update rule written with assign

nn/optim.py is 179 lines and contains every optimizer. There are only two real classes. LARS covers SGD (trust coefficient 0), momentum, Nesterov and Muon (Newton–Schulz). LAMB covers Adam and AdamW (trust ratio fixed at 1). SGD, Adam, AdamW and Muon are functions that return a configured LARS or LAMB:

def Adam(params, lr=0.001, b1=0.9, b2=0.999, eps=1e-8, device=None, fused=FUSE_OPTIM):
  return LAMB(params, lr, b1, b2, eps, 0.0, adam=True, device=device, fused=fused)

The base class does the bookkeeping and the parameter write-back:

tinygrad/nn/optim.py — Optimizer.schedule_step
def step(self):
  Tensor.realize(*self.schedule_step())

def schedule_step(self) -> list[Tensor]:
  if not TRAINING: raise RuntimeError(...)          # TRAINING must be enabled to use the optimizer
  ...
  updates, extra = self._step(self.params, [unwrap(t.grad) for t in self.params])

\[ m \leftarrow \beta_1 m + (1-\beta_1) g,\qquad v \leftarrow \beta_2 v + (1-\beta_2) g^2,\qquad w \leftarrow w - \eta\,\frac{m/(1-\beta_1^t)}{\sqrt{v/(1-\beta_2^t)}+\epsilon} \]

What assign builds

Tensor.assign handles several cases (disk, views, initializing a still-pending value). For a realized parameter it takes the simple path at the end:

self.uop = self.uop.after(self.uop.store(x.uop))   # AFTER(BUFFER, STORE(BUFFER, value))

The Tensor object stays the same Python object, so the model still points at it, but its .uop now means "this buffer, read after the store has happened". Anything built from the parameter later (for example the next step's forward pass, if you do not realize in between) reads the new value. That is the read-after-write ordering the scheduler enforces (Chapter 12). Note t.detach() in _apply_update: the update must not be differentiated through.

After opt.schedule_step() returns, what has happened to the parameter buffers?
schedule_step only builds graphs. assign mutates the Tensor's .uop in place, so the same Python object (the one your model holds) now denotes "the buffer after the store". The scheduler turns that STORE into a kernel when you realize.

The 30 kernels

Phases are not something tinygrad knows about. The script derives them from the dataflow: forward means "the loss kernel depends on it", update means "touches optimizer state or writes a parameter", and the rest is backward. Things to notice:

  • The schedule is a toposort, not program order. Kernels 1–2 (b1_t *= 0.9, b2_t *= 0.999) are "update" kernels but run second and third: they depend on nothing, and create_schedule emits ready kernels in BFS order.
  • Kernel 0 fuses all of Linear 1 (MUL + REDUCE + bias) into one r_32_8_4_4_2 that writes the pre-ReLU hidden layer (128×32 = 4096 floats). ReLU is not a kernel of its own: it is fused into kernel 3, the consumer (r_128_2_32 = Linear 2).
  • log_softmax + the loss is 3 kernels (4, 5, 6): max over classes, sum of exp, then the masked mean. Kernel 6's C (below) contains a whole polynomial: on CPU, LOG2 is decomposed by the transcendental rewrites (Chapter 15).
  • Backward is 7 kernels (7–13): softmax − one-hot gradient, then for each Linear one reduce for the weight gradient (Xᵀ·δ), one for the bias gradient (Σδ), and one to propagate δ back through Linear 2 and the ReLU mask.
  • The update is 16 kernels: one each for m and v of each of the 4 parameters (14–21), then a new value per parameter into a temporary (22–25), then a copy back (26–29). Why the temporary? The value stored into w reads w. realize_store_after_src materializes the source of a STORE whenever it reads its own destination, which is how the scheduler avoids a write-after-read hazard in general. In this purely elementwise case each element reads only itself, so the copy is conservative.

The kernel-0 C shows the optimizer from Chapter 14 at work: the 128×32 output was split into loops of 32 and 8, with two axes upcast by 4 (hence the float4 loads and four float4 stores per iteration). The 2-element reduce (the input dimension) was unrolled away completely.

Why does the step have 4 kernels that only copy a temporary into a parameter (26–29)?
realize_store_after_src in schedule/indexing.py: if dest.base in src.toposort(): realize src. The update w.detach() - lr*up contains w, so it goes to a temporary buffer, and the STORE becomes a copy kernel. The rule is general (it is needed when, say, a transpose of w is assigned into w); here it happens to be stricter than necessary.

  • Step 1 is a new graph (everything is now a BUFFER), so it is a cache miss again. Scheduling takes about 100 ms.
  • From step 2 on it is a cache hit, and scheduling takes about 3 ms. The key is the hash of the graph after pm_replace_buf has replaced every concrete buffer with a numbered PARAM (transform_to_call). New weight values do not change the key; a new graph shape does.

The schedule cache removes scheduling, but Python still rebuilds the whole graph every step (forward, backward, optimizer: hundreds of UOp constructions) and still walks the LINEAR. TinyJit removes that as well: call 0 runs normally, call 1 records every LINEAR that is run (capturing in engine/realize.py), merges them, memory-plans and compiles them, and calls 2+ only replay the captured LINEAR with the new input buffers (Chapter 18).

# Part 2: train to convergence on the spiral and record, every few steps, the loss and the model's predictions on a
#         32x32 grid of the input plane -> data/ch20_train.json (replayed by the chapter's decision-boundary demo).
import json, math, os, random, time
from tinygrad import Tensor, nn, Context, TinyJit, GlobalCounters
DATA = os.path.join(os.path.dirname(os.path.abspath(__file__)), "..", "data")

def spiral(n_per_class=64, seed=0):   # identical to examples/20_train_step.py
  rnd = random.Random(seed)
  pts, labels = [], []
  for c in range(2):
    for i in range(n_per_class):
      r = 0.15 + 0.85 * i / n_per_class
      t = 1.6 * math.pi * i / n_per_class + c * math.pi + rnd.gauss(0, 0.12)
      pts.append([r * math.cos(t), r * math.sin(t)]); labels.append(c)
  return pts, labels

class MLP:
  def __init__(self, hidden=32): self.l1, self.l2 = nn.Linear(2, hidden), nn.Linear(hidden, 2)
  def __call__(self, x:Tensor) -> Tensor: return self.l2(self.l1(x).relu())

def make(seed=0):
  Tensor.manual_seed(seed)
  model = MLP()
  opt = nn.optim.Adam(nn.state.get_parameters(model), lr=0.02)
  return model, opt

pts, labels = spiral()
X, Y = Tensor(pts).realize(), Tensor(labels).realize()

def step(model, opt):
  with Context(TRAINING=1):
    opt.zero_grad()
    loss = model(X).sparse_categorical_crossentropy(Y).backward()
    return loss.realize(*opt.schedule_step())

    GlobalCounters.reset()
    st = time.perf_counter(); out = fn(); out.item(); ts.append((time.perf_counter() - st) * 1e3)
  return ts, GlobalCounters.kernel_count

20.9A real model from the same pieces: tinygrad/llm

python -m tinygrad.llm (cli.py main) downloads a GGUF model (Llama 3.2, Qwen3/3.5/3.6, OLMoE, GLM, …), parses it with gguf_parse, builds a Transformer and chats, or serves an OpenAI-compatible API with --serve. The model file is about 770 lines and is built from what you have seen:

  • nn.Embedding for token_embd, nn.RMSNorm for every norm, and Linear, a subclass of nn.Linear in llm/kernels/amd.py that can also hold packed quantized GGUF weights.
  • Each block's body is a @function(precompile=True) (FFNBlock.__call__), so every layer with the same shapes shares one schedule.
  • The KV cache is updated with a raw STORE + AFTER, the same UOps assign builds: store = self.cache_kv[...].uop.store(...); Tensor(self.cache_kv.uop.after(store)).
  • forward is wrapped in two TinyJits, one for prefill and one for single-token decode, and sampling is the Gumbel-max trick done with Tensor ops (argmax(logits/T − log(−log u))).

Chapter summary

  • tinygrad/nn layers are plain classes holding Tensors. Linear is reshape · MUL · REDUCE · ADD and fuses into one kernel.
  • nn.state.get_state_dict walks __dict__/lists/dicts. safetensors, torch and gguf loading are lazy views of a DISK buffer, read on realize.
  • Optimizers are two classes (LARS, LAMB). The update is Tensor math plus assign, which turns each parameter's .uop into AFTER(BUFFER, STORE(...)). schedule_step() runs nothing, and the TRAINING ContextVar gates it.
  • One step of a 2-32-2 MLP with Adam is one LINEAR of 30 kernels: 5 forward, 7 backward, 18 update. The order is a toposort, so independent update kernels run early. Self-reading stores go through a temporary.
  • The schedule cache keys on the graph with buffers replaced by PARAMs, so a steady-state step skips scheduling. TinyJit also skips graph building: about 40 ms down to about 3 ms per step here.
  • tinygrad/llm is a full LLM runner built from the same nn layers, @function, STORE/AFTER KV caches and TinyJit.
