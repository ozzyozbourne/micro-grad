CHAPTER 01The 10,000-foot view

One page, the whole machine. We take two real programs — (a*b+1).sum() and a small (x @ w).relu() — and follow them from the line of Python you type all the way to the machine code that runs, printing the actual artifact at every stage. By the end you will know the name of every stage, which function owns it, what goes in, what comes out, and which later chapter zooms into it.

Everything on this page was produced by tinygrad commit 6a404871 (v0.14.0, October 2026) running on DEV=CPU (clang). If you remember older tinygrad: LazyBuffer, ShapeTracker, ScheduleItem, the Kernel/Linearizer classes and DEFINE_GLOBAL are gone. Today a tensor holds a UOp, a schedule is a LINEAR UOp of CALLs, and kernel arguments are PARAMs.

1.1The one-sentence version

tinygrad is a lazy compiler. Calling a * b does not multiply anything: it appends a node to a graph. Only when you ask for a value (.tolist(), .item(), .numpy(), .realize()) does tinygrad look at the whole graph, decide which parts become separate GPU/CPU kernels, generate source code for each kernel, compile it, and run it.

Analogy: a restaurant that cooks only when you pay Each Tensor operation is a line on an order ticket ("multiply these, add one, sum"). Nothing is cooked while you write. When you say "I'd like to eat now" (.item()), the head chef reads the whole ticket, notices that three lines can be done in one pan (fusion), assigns pans and burners (scheduling), writes a precise recipe card for each pan (codegen), and only then do the cooks start (run). Because the chef sees the whole ticket first, they can do things a cook following lines one by one never could.

The five big boxes above are the five layers you will meet over and over. Their boundaries are real functions:

1.2Everything is a UOp

The single most important fact about modern tinygrad: there is exactly one data structure for programs, from the first Tensor op down to the compiled binary. It is class UOp, and it has three fields:

tinygrad/uop/ops.py — the whole UOp dataclass header (dtype is a derived property, see Chapter 3)
@dataclass(eq=False, slots=True)
class UOp(RandMixin, metaclass=UOpMetaClass):
  op:Ops                       # what kind of node: ADD, RESHAPE, BUFFER, RANGE, CALL, PROGRAM, ...
  src:tuple[UOp, ...] = tuple()  # the inputs: other UOps
  arg:Any = None               # op-specific payload: a constant, a device name, a KernelInfo, C source, bytes ...
  @recursive_property
  def dtype(self) -> DType: return dtype_from_uop(self.op, self.src, self.arg)

A UOp is immutable and hash-consed: UOpMetaClass.__call__ looks up (op, src, arg) in a weak-value cache, so building the same node twice returns the same Python object. That makes graph equality an is check, makes common sub-expressions automatically shared, and makes every compiler pass a pure function "UOp in, UOp out". Every pass is a graph_rewrite with a PatternMatcher (Chapter 5).

What changes from stage to stage is which Ops appear. The Ops enum is literally organised by altitude:

tinygrad/uop/__init__.py — excerpt of class Ops (comments are the source's own)
class Ops(FastEnum):
  # ** 1 -- defines/special **
  SPECIAL = auto()
  # BUFFER references bound storage; ALLOC declares unbound global storage
  BUFFER = auto(); ALLOC = auto()
  # ** 2 -- non op uops **
  NOOP = auto(); REWRITE_ERROR = auto()
  # CALL is a kernel invocation; value-producing calls write to ALLOC arguments
  PARAM = auto(); CALL = auto()
  # LINEAR is a list of UOps, SOURCE has a str arg that's human readable, BINARY has bytes arg that's compiled
  PROGRAM = auto(); LINEAR = auto(); SOURCE = auto(); BINARY = auto()
  # AFTER passes src[0] through and promises in the toposort that any consumers of the AFTER run after src[1:]
  SINK = auto(); AFTER = auto()
  ...
  # ** 3 -- load/store **
  INDEX = auto(); SHRINK = auto()
  LOAD = auto(); STORE = auto()
  # ** 4 -- math **
  WMMA = auto()
  CAST = auto(); BITCAST = auto(); EXP2 = auto(); LOG2 = auto(); SIN = auto(); SQRT = auto(); RECIP = auto(); NEG = auto(); TRUNC = auto()
  ADD = auto(); MUL = auto(); ...; CMPLT = auto(); CMPNE = auto(); CMPEQ = auto(); ...
  WHERE = auto(); MULACC = auto()
  # ** 5 -- control flow / consts / custom **
  BARRIER = auto(); RANGE = auto(); IF = auto(); END = auto(); ENDIF = auto()
  CONST = auto()
  ...
  # ** 6 -- ops that don't exist in programs **
  CONTIGUOUS_BACKWARD = auto(); DETACH = auto()
  STAGE = auto(); COPY = auto(); MSELECT = auto(); MSTACK = auto(); CUSTOM_FUNCTION = auto()
  # the core 5 movement ops! these only exist in the tensor graph
  RESHAPE = auto(); PERMUTE = auto(); EXPAND = auto(); PAD = auto()
  ...
  REDUCE = auto(); ALLREDUCE = auto()
The thesis in one line A Tensor program, a schedule, a kernel, a list of instructions and a compiled program are all just graphs of UOps that use different subsets of Ops. Compiling = rewriting the graph until only "low" ops remain. One IR, one rewrite engine, one set of tools (printing, VIZ, hashing, caching) for every stage.

def spy(module, name):
  """replace module.name with a wrapper that records (args, result) and then returns the real result"""

  def wrapper(*args, **kwargs):

1.4Stage 1 — the lazy tensor graph

Input: Python calls. Output: a UOp DAG that describes the computation. Who: every Tensor method ends in Tensor._apply_uop, which calls a UOp-building function on the input UOps and wraps the result in a new Tensor. No kernel runs.

Read it bottom-up. Each Python list became a BUFFER on the PYTHON device (the data is already there, in host memory) followed by a COPY to CPU. a*b is a MUL, +1 is an ADD with a CONST 1.0, and .sum() is a REDUCE whose arg (Ops.ADD, 1) means "reduce the leading 1 axis with ADD". The CONST 4 under both buffers is the buffer's size — sizes and shapes are UOps too, which is how symbolic shapes work (Chapter 6). Notice it appears once (x4:=) and is reused: hash-consing at work.

Chapter 2 is entirely about this stage: what the Tensor object holds, how the mixins build UOps, how creation functions differ, and what forces realization.

1.5Stage 2 — scheduling: from a tensor graph to a list of kernels

Input: the tensor graphs of the tensors you realize. Output: a LINEAR UOp whose sources are CALLs, in execution order. Who: Tensor.linear_with_vars → create_linear_with_vars. This is the biggest conceptual stage, so let us take it in five sub-steps.

2a. Bufferize the outputs (still in linear_with_vars)

tinygrad/tensor.py — linear_with_vars (abridged)

  """Creates the LINEAR UOp needed to realize these Tensor(s), with Variables."""

  # weakness ends where storage begins
  if any(u.dtype in dtypes.weaks and u.device is not None for u in sink.src):
    raise RuntimeError("cannot realize a weak dtype; cast to a concrete dtype first")
  ...
  for x in sink.toposort():
    u = x.replace(src=tuple(tensor_map.get(s, s) for s in x.src))
    ...
    elif x in bases and u.needs_storage():
      ...
      else:  # allocate fresh storage and store the compute into it
        buf = UOp.new_buffer(src.device, prod(src.max_shard_shape), src.dtype).reshape(src.max_shard_shape).shrink_to(src.shard_shape)

  return create_linear_with_vars(sink)

Every output that needs storage gets a fresh BUFFER, and the computation is wrapped as AFTER(buffer, STORE(buffer, compute)): "this buffer, after the compute has been stored into it". Then — before anything has run — _apply_map_to_tensors re-points every live Tensor at that buffer. This is the input of the next step:

2b. Callify: buffers become parameters

transform_to_call collects the stores, replaces every concrete BUFFER by a positional PARAM (slot 0, 1, 2 …) and wraps everything into one CALL whose extra sources are the actual buffers.

-- output: one CALL; its body is a SINK where every BUFFER became a PARAM slot:
CALL body ops: CONST:3, PARAM:3, COPY:2, STACK:1, RESHAPE:1, MUL:1, ADD:1, REDUCE:1, STORE:1, AFTER:1, SINK:1
CALL args    : ['BUFFER(CPU, slot=2)', 'BUFFER(PYTHON, slot=0)', 'BUFFER(PYTHON, slot=1)']
Why turn buffers into PARAMs? So that the CALL body no longer mentions which memory it runs on. Two runs of the same program on different data produce the identical body UOp — identical hash — and hit the schedule_cache. Section 1.9 shows the cache hit happen.

2c. Prepare + rangeify: shapes become loops

lower_sink_to_linear is the pattern that fires on that CALL and runs create_schedule(get_kernel_graph(prepare_rangeify(function))). prepare_rangeify resolves multi-device ops, inlines calls and turns each COPY into an anonymous ALLOC + STORE + AFTER. Then run_rangeify performs the key transformation of the whole scheduler: every value is now addressed by index expressions built from RANGE UOps (loop variables), and all movement ops (RESHAPE, PERMUTE, EXPAND, PAD, SHRINK) disappear into those indices.

-- after prepare_rangeify: COPY became ALLOC + STORE + AFTER
ops: CONST:3, PARAM:3, STORE:3, AFTER:3, ALLOC:2, STACK:1, RESHAPE:1, MUL:1, ADD:1, REDUCE:1, SINK:1

-- after run_rangeify: movement ops are gone, every access is an INDEX by RANGEs
ops: INDEX:7, CONST:4, PARAM:3, RANGE:3, STORE:3, AFTER:3, ALLOC:2, END:2, MUL:1, ADD:1, REDUCE:1, SINK:1

Read the op counts: RESHAPE/STACK are gone; there are now 3 RANGEs (one loop for each copy, one for the reduction), 7 INDEXes and 2 ENDs (closing the copy loops). Chapter 10 is dedicated to how ranges are created and propagated.

2d. Kernel split

get_kernel_graph cleans up (symbolic simplification, removing unnecessary buffers), turns staged values into stores, and finally split_store cuts the graph at every STORE/END with no open ranges: each piece becomes SINK(…).call(*buffers) — one CALL per kernel.

-- after get_kernel_graph: the graph is cut into CALLs, one per kernel
3 CALLs: ['PARAM:2, INDEX:2, CONST:1, RANGE:1, STORE:1, END:1, SINK:1', 'PARAM:2, INDEX:2, CONST:1, RANGE:1, STORE:1, END:1, SINK:1', 'CONST:4, PARAM:3, INDEX:3, RANGE:1, MUL:1, ADD:1, REDUCE:1, STORE:1, SINK:1']

Three kernels: two copy loops (STORE(INDEX(dst, r), INDEX(src, r))) and the compute kernel that fused MUL, ADD and REDUCE into one. Fusion is not a separate pass you can point at; it is the absence of a cut. Chapter 11 explains when tinygrad cuts and when it fuses.

2e. Order, lower copies, plan memory

create_schedule builds the kernel dependency graph from the AFTER edges (read-after-write and write-after-read) and toposorts it into a LINEAR. Back in create_linear_with_vars, PARAMs are resolved to real buffers, copy kernels are lowered to bulk STORE calls (pm_copy_from_store), and memory_plan_rewrite packs temporary buffers into shared arenas:

============ STAGE 3: the schedule (LINEAR of CALLs, after memory planning) 
  0: CALL  body=STORE -> copy (STORE call)  args=['BITCAST', 'BUFFER[PYTHON]']
  1: CALL  body=STORE -> copy (STORE call)  args=['BITCAST', 'BUFFER[PYTHON]']
  2: CALL  body=SINK  -> kernel             args=['BUFFER[CPU]', 'BITCAST', 'BITCAST']

Look at the args: the two intermediate CPU copies of a and b are not separate allocations; they are BITCAST(SHRINK(BUFFER(i8, 512))) views at byte offsets 0 and 256 of a single 512-byte arena (open the "Schedule" stage in the map above and hover them). Only the output buffer (BUFFER[CPU], held by c) is a standalone allocation. Chapter 12 covers this.

After linear, _ = c.linear_with_vars() but before running linear, what does c.uop look like?
_apply_map_to_tensors(becomes_map | tensor_map, "bufferize") runs inside linear_with_vars. That is why examples/01_matmul_relu.py must call run_linear(linear) after y.schedule_linear(): otherwise y.tolist() reads uninitialized memory (we hit exactly that bug while writing the example and it printed zeros).

1.7Stage 4 — codegen: AST → optimized, lowered, linearized, rendered

Who: to_program (cached) → do_to_program. It first calls full_rewrite_to_sink — about 30 named graph_rewrite passes that optimize (choose loop splits/upcasts: apply_opts) and lower the AST — and wraps the result in a PROGRAM. Then the PROGRAM itself is grown by a small pattern matcher, one source at a time:

tinygrad/codegen/__init__.py — pm_to_program: each rule appends one stage's output to the PROGRAM's src
pm_to_program = PatternMatcher([
  (UPat(Ops.PROGRAM, src=(UPat(Ops.SINK, name="sink"),), name="prg"), do_linearize),       # SINK            -> + LINEAR
  (UPat(Ops.PROGRAM, src=(UPat(Ops.SINK, name="sink"), UPat(Ops.LINEAR, name="lin")), name="prg"), do_estimates),
  (UPat(Ops.PROGRAM, src=(UPat(), UPat(Ops.LINEAR, src=UPat(Ops.INS), name="lin")), name="prg"), do_assemble),  # ISA backends
  (UPat(Ops.PROGRAM, src=(UPat(), UPat(Ops.LINEAR, name="lin")), name="prg"), do_render),   # LINEAR          -> + SOURCE
  (UPat(Ops.PROGRAM, src=(UPat(), UPat(Ops.LINEAR), UPat(Ops.SOURCE, name="source")), name="prg"), do_compile),  # -> + BINARY
])
Even "the compiled program" is a UOp PROGRAM(SINK, LINEAR, SOURCE, BINARY): the lowered graph, the ordered instruction list, the C source string (in a SOURCE's arg) and the machine-code bytes (in a BINARY's arg). The pipeline never leaves the IR.

Things to notice, each one a later chapter:

  • The optimizer applied Opt(op=OptOps.SPLIT, axis=0, arg=(0, AxisType.UPCAST)): the 4-long reduce loop was fully upcast (unrolled into vector lanes), so the C has no loop at all and loads a float4 (Chapter 14).
  • The kernel was renamed test → r_4: r = has a reduce (E = elementwise), then the loop sizes.
  • Symbolic simplification hoisted the four +1.0s out of the sum into a single +4.0f (Chapter 6).
  • The LINEAR is a flat, topologically ordered list where loads come early and stores late (linearize, Chapter 16). The renderer (ClangRenderer) walks this list and prints one line per value.

  def __init__(self, cachekey:str|None=None): self.cachekey = cachekey if CCACHE else None
  def compile(self, src:str) -> bytes: return src.encode()   # NOTE: empty compiler is the default
  def compile_cached(self, src:str) -> bytes:

      assert not getenv("ASSERT_COMPILE"), f"tried to compile with ASSERT_COMPILE set\n{src}"

    1.13Why is it built like this?

    • Laziness buys whole-program knowledge. An eager framework must decide what to do with a*b before it knows that a +1 and a .sum() follow. tinygrad sees the whole graph at realize(), so it can fuse three ops into one kernel, fold +1s into +4.0f, and never allocate the intermediate a*b.
    • One IR means one toolbox. Because tensors, schedules, kernels and programs are all UOps, one rewrite engine (PatternMatcher + graph_rewrite), one printer, one visualizer and one hashing scheme serve every stage. New passes are a list of patterns, not a new data structure.
    • Hash-consing makes it cheap. Identical sub-graphs are shared, equality is identity, and every stage can be cached by UOp.key.
    • The price: errors surface late (a shape bug in your model may appear only when you call .item()), the first run pays scheduling+compile time (hence the caches and TinyJit), and reading the internals requires knowing which Ops are legal at which altitude — which is what spec.py checks and what this guide is for.

    1.14Reading roadmap

    The remaining chapters follow the pipeline. Foundations first (the IR and the rewrite engine every later stage is built from), then the stages left to right.

    Which statement about a PROGRAM UOp produced by to_program is true?
    The example printed PROGRAM srcs: ['SINK', 'LINEAR', 'SOURCE', 'BINARY']. Loading the binary into an executable function happens later, at run time, in get_runtime.
    In which stage do RESHAPE/PERMUTE/EXPAND disappear from the graph?
    The op counts printed after run_rangeify contain no movement ops, and the heat-map shows the teal rows end at the rangeify column. "Movement ops are free" is literally true: they cost nothing at run time because they only change index math.

    Chapter summary

    • tinygrad is a lazy compiler: Tensor ops build a UOp graph; realize() (or anything that needs data) compiles and runs it.
    • Everything is a UOp (op, src, arg), immutable and hash-consed. Stages differ only in which Ops appear.
    • Schedule (Tensor.linear_with_vars): bufferize outputs → transform_to_call (buffers→PARAMs) → prepare_rangeify → run_rangeify (movement ops → RANGE indexing) → get_kernel_graph (cut into CALLs) → create_schedule → copies lowered, memory planned.
    • Codegen (do_to_program): full_rewrite_to_sink (optimize + ~30 lowering passes) → linearize → render, producing PROGRAM(SINK, LINEAR, SOURCE, BINARY); compile_cached makes the binary.
    • Run (run_linear): dispatch each CALL by its body (STORE = copy, PROGRAM = kernel) via pm_exec.
    • Use DEBUG=2/4/5, NOOPT=1, VIZ=-1 + tinygrad.viz.cli to watch it; four caches make repeated structures cheap.
