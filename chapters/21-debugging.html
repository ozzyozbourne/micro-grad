CHAPTER 21Debugging & introspection

tinygrad is small enough to read, and it comes with tools to watch itself: environment variables that print every stage (DEBUG), a trace of every graph rewrite and every pattern match (VIZ, TRACK_MATCH_STATS), a type system for the IR (SPEC), knobs that switch the optimizer off or turn it into a search (NOOPT, BEAM), and a regression system that proves a refactor did not change any generated kernel (process replay). This chapter runs each one on the same small program and shows the real output. It ends with a playbook for answering any "why does tinygrad do X?" question yourself.

21.1The specimen, and how the switches work

Every tool in this chapter is pointed at this three-line program: a 2×4 Python list, x*2+1, a row sum. It is small enough to read the whole output and still goes through every stage: a host-to-device copy, a fused elementwise+reduce kernel, an optimization, C codegen and clang.

examples/21_debug_target.py — run with DEV=CPU python3 examples/21_debug_target.py
# Chapter 21 — the tiny program every introspection tool in this chapter is pointed at
# Run: DEV=CPU DEBUG=2 python3 examples/21_debug_target.py     (try DEBUG=1..7, VIZ=-1, NOOPT=1, BEAM=2 ...)
from tinygrad import Tensor
x = Tensor([[1., 2., 3., 4.], [5., 6., 7., 8.]])   # python list -> a PYTHON-device buffer, copied to CPU
y = (x * 2 + 1).sum(axis=1)                          # one fused elementwise+reduce kernel
print(y.tolist())                                    # .tolist() realizes: schedule -> codegen -> run

All the switches are ContextVars in helpers.py, read from the environment once at import: DEBUG, BEAM, NOOPT (helpers.py:237), VIZ and PROFILE (272–276), SPEC (277), CAPTURE_PROCESS_REPLAY (257). Because they are ContextVars, you can also change most of them for a region of code with with Context(DEBUG=4): ... or @Context(BEAM=2). sz.py counts them: 53 flags in this version (21.9). docs/env_vars.md lists the public ones.

Some flags only take effect at import time: VIZ/TRACK_MATCH_STATS decide whether PatternMatcher is replaced by TrackedPatternMatcher when uop/ops.py is imported (ops.py:1690). Set those in the environment, not with Context.

21.3VIZ: every graph rewrite, recorded

Every compiler pass in tinygrad is a graph_rewrite with a PatternMatcher (Chapter 5). That makes one generic tracer enough for the whole compiler. With VIZ set, TRACK_MATCH_STATS defaults to 2 (ops.py:1572) and three things change:

  • PatternMatcher becomes TrackedPatternMatcher, which records every successful match as (uop_before, uop_after, upat_location, seconds).
  • Every function decorated with @rewrite_group (for example linear_with_vars → "Schedule 1 -> 2 n1", or do_to_program → the kernel name) opens a group. Every graph_rewrite(..., name=...) inside it appends a TrackedGraphRewrite (location, input sink, matches, name, depth).
  • At exit, an atexit hook pickles all of this to $TMPDIR/rewrites.pkl.<user> (UOps are stored as integer trace numbers plus a uop_fields table so they can be rebuilt), and PROFILE (implied by VIZ) writes profile.pkl.<user>.

VIZ=1 then execs into tinygrad/viz/serve.py if stdout is a terminal, a web UI on port 8000. VIZ=-1 only saves the files and prints saved viz files, view using: python -m tinygrad.viz.cli. Here is the real web UI on the specimen, with group r_2_4 → rewrite postopt symbolic → match 1 selected:

viz/cli.py reads the same pickles. With no arguments it prints the whole timeline: every USER Tensor method call (PROFILE wraps them, tensor.py _profile_wrapper), every TINY compiler span and every kernel run. -s NAME selects a source (or a kernel inside it, and then a rewrite inside that), -q REGEX searches event and rewrite names and prints the matching graphs, -t [N] aggregates, and --json emits one JSON object per line. PROFILE: the timeline without the rewrites

PROFILE defaults to abs(VIZ) (helpers.py:276), and you can also set it on its own. It records three kinds of events into profile.pkl: every public Tensor method call (via _profile_wrapper; the USER source in the --list tab), compiler spans (TINY), and device kernel runs with real timestamps (CPU). Call profile_marker("name") in your program to drop named markers. viz.cli --interval START [END] then restricts -t or the timeline to events between two markers. That is how you time "step 10 to step 20 of training" while excluding warm-up.

Replaying the trace yourself

The pickle is not a black box. The next script captures it (TRACK_MATCH_STATS=2 without the server) and decodes it with the viz server's own load_rewrites and get_full_rewrite, in a fresh process, as the server does. It writes every step that had matches to JSON for the browser below.

21.4TRACK_MATCH_STATS / PRINT_MATCH_STATS: which rules fire, and what they cost

TRACK_MATCH_STATS=1 gives you the tracking pattern matcher without the per-match graph log. 21.5SPEC and type_verify: the IR has a type system

A UOp is just (op, dtype, src, arg), and nothing in the constructor stops you from building nonsense. The spec is what does. uop/spec.py defines it as PatternMatchers whose rules return True (valid), False (invalid) or None (no opinion), the same machinery as everything else:

spec_sharedrules valid everywhere: SINK, CONST, ALU dtype agreement, comparisons, WHERE, CAST(included in the others)

def type_verify(ast:UOp|list[UOp], check_spec:PatternMatcher, enter_calls=False):
  lst = list(ast.toposort(enter_calls=enter_calls)) if isinstance(ast, UOp) else ast
  with Context(TRACK_MATCH_STATS=0):
    for i,u in enumerate(lst):
      ret: bool|None = check_spec.rewrite(u)
      if ret is not True:
        if DEBUG >= 3: print(render_uir(lst))
        raise RuntimeError(f"UOp verification failed at {i} on {u.op} {u.dtype} {len(u.src)} {[(x.op, x.dtype, x.arg) for x in u.src]} {u.arg}")

21.6NOOPT and BEAM: switch the optimizer off, or make it search

The kernel AST is the same either way. Only the optimization stage between the AST and lowering changes (Chapter 14). NOOPT=1 applies no OptOps, so the C is the plain loop nest the AST describes. This is the first thing to try when a kernel is wrong, because it tells you whether the bug is in an optimization. The default runs hand_coded_optimizations. BEAM=n runs beam_search: it compiles and times candidate OptOp sequences on the real device and keeps the best n at each level. Results are cached in the disk cache, so IGNORE_BEAM_CACHE=1 forces a fresh search.

21.7Process replay: refactors must not change generated code

tinygrad gets refactored constantly, and most PRs say "no behavior change". Process replay checks that claim mechanically:

  1. Capture. CI runs the test suite on your branch with CAPTURE_PROCESS_REPLAY=1. Every function decorated @rewrite_group(..., replay="process_replay") pickles its inputs, the values of every ContextVar, the test location (get_process_replay_loc, which finds the unittest frame) and its return value into the sqlite CACHEDB (ops.py:1651). In this version that is do_to_program: AST + renderer → PROGRAM (with source).
  2. Replay. Check out master, run process_replay.py. For each captured row it restores the ContextVars, calls master's to_program on the same AST, and unified-diffs master's source against your branch's.
  3. Judge. Diffs are printed. If the PR title contains [pr] (a refactor/speedup claim), any diff fails CI (ASSERT_DIFF). Replay stops early when more than 20% of kernels change. [skip_process_replay] opts out.

The CI step is .github/actions/process-replay; the local recipe is local.sh. The idea fits in a few lines, which is the last part of 21_noopt_beam.py: lower the same AST twice. A pure refactor gives 0 diff lines. A change that alters codegen (simulated with NOOPT) gives a diff that names exactly what changed:

  • The IR has a spec written as PatternMatchers. type_verify runs it at checkpoints (SPEC=1) and SPEC=2 runs it on every UOp at construction.
