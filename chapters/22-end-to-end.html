CHAPTER 22Capstone: the end-to-end explorer

Type a tinygrad program and follow it all the way down: the lazy UOp graph, every scheduling rewrite and the rules that fired, the schedule of kernels, each kernel's AST, optimizations and lowering passes, the linearized program, the C source clang compiles, and the timings and values it produces. Everything shown comes from a real run of the pinned tinygrad checkout, recorded by tinygrad's own rewrite tracker.

22.1One program, eight snapshots

The earlier chapters each took one stage of the compiler apart. This chapter connects them. You give the explorer a snippet; it runs the snippet in a fresh subprocess with DEV=CPU and records the program at eight points:

① Tensor graph

The lazy UOp DAG behind out.uop. Nothing has run. ch 2 · ch 4

② Schedule passes

Every graph_rewrite inside Tensor.linear_with_vars: bufferize, callify, rangeify, kernel split. ch 10 · ch 11

③ Schedule

A LINEAR UOp: an ordered list of CALLs (kernels and copies) with their buffers. ch 12

④ Kernel AST

One kernel's SINK: PARAMs, RANGEs, INDEX, REDUCE, STORE, END. ch 13

⑤ Codegen passes

do_to_program → full_rewrite_to_sink: opts (UPCAST…), expander, devectorize, decompositions… ch 14 · ch 15

⑥ Linearized

The DAG ordered into a flat list of UOps, one per line of the program. ch 16

⑦ C source

What ClangRenderer emits from that list, then compiled to a BINARY. ch 16

⑧ Run

run_linear executes each CALL; per-kernel time, estimated ops/bytes, the output values. ch 17
AnalogyA factory floor with eight inspection windows. The snippet is raw material. At each window you see the part as it is at that moment, and between windows you see which machines (pattern rules) touched it and how often. Purple windows are per kernel: once the scheduler has cut the work into kernels, each kernel goes through its own codegen line.
The key ideaEvery arrow in this pipeline is a graph_rewrite over UOps, apart from a few plain Python steps (toposorting the schedule, linearizing, rendering strings, calling clang). Because UOps are hash-consed, a node that a pass leaves alone is the same object before and after. The explorer gives each UOp one stable id for the whole trace, so the graph morphs between stages: nodes that survive stay where they are, new nodes fade in, and the ones that were rewritten away disappear.

The snippet convention

  • Tensor, dtypes, nn, UOp, Ops, Device are already imported.
  • Assign the result to out: a Tensor, or a list, tuple or dict of Tensors. If you don't, and the last line is an expression, that expression becomes out.
  • Whatever the snippet realizes while it runs (for example x = Tensor([...]).realize()) is the prelude. The trace then focuses on the single realize of out. The presets realize their inputs first, so the traced graph starts from real BUFFERs instead of copies from the PYTHON device.

22.2How the trace is captured: tinygrad tracks itself

The tracer re-implements nothing. tinygrad already has a tracker for every rewrite; it is the data source for VIZ=1. Setting TRACK_MATCH_STATS=2 turns it on (that is what VIZ=1 sets underneath). At import time, tinygrad/uop/ops.py then replaces PatternMatcher with TrackedPatternMatcher, and every function wrapped in @rewrite_group starts recording:

tinygrad/uop/ops.py — TRACK_MATCH_STATS TrackedGraphRewrite rewrite_group TrackedPatternMatcher
TRACK_MATCH_STATS = ContextVar("TRACK_MATCH_STATS", 2 if VIZ else 0)

@dataclass(frozen=True)
class TrackedGraphRewrite:
  loc:tuple[str, int]                           # location that called graph_rewrite
  sink:int                                      # the sink input to graph_rewrite
  matches:list[tuple[int, int, tuple, float]]   # before/after UOp, UPat location and time
  name:str                                      # name of the rewrite
  depth:int                                     # depth if it's a subrewrite
  bottom_up:bool
  walk:bool
  enter_calls:bool

tracked_keys:list[TracingKey] = []
tracked_ctxs:list[list[TrackedGraphRewrite]] = []

# graph_rewrite itself is decorated:
@rewrite_group(new_ctx=False)
def graph_rewrite(sink:UOp, pm:PatternMatcher, ctx=None, bottom_up=False, name=None, ...) -> UOp: ...

There are two kinds of @rewrite_group. A new-context group, such as the scheduler or do_to_program for one kernel, appends a new entry to tracked_keys. A new_ctx=False function, such as graph_rewrite, prepare_rangeify or get_kernel_graph, appends one TrackedGraphRewrite to the current group. Its depth is the length of the active_rewrites stack, which is why rewrites nested inside a pattern's callback appear indented. TrackedPatternMatcher.rewrite then adds (before.trace_num, after.trace_num, upat.location, seconds) to active_rewrites[-1].matches every time a rule returns a new UOp.

For one realize on CPU, the groups look like this (names are real):

tools/trace.py (in this guide's repo, not tinygrad) adds three small hooks on top of that machinery:

  1. Output graphs. TrackedGraphRewrite stores only the input sink, as a trace_num. VIZ rebuilds outputs by replaying the matches. The tracer wraps RewriteContext.unified_rewrite / .walk_rewrite and records (input, output) for the TrackedGraphRewrite that is active_rewrites[-1] when the call starts. Only the outermost call per context counts: substitute() and simplify() without a name run untracked (TRACK_MATCH_STATS=0) but still go through RewriteContext while an outer rewrite is active.
  2. Timings. It wraps track_stats (the function that prints the DEBUG=2 lines) to record each call's kernel time and estimates, and runs run_linear(..., wait=True) so kernel times are measured.
  3. Compiled programs. After the run it reads each kernel's PROGRAM UOp (SINK, LINEAR, SOURCE, BINARY) from to_program_cache, using to_program_key(ast, renderer).

The worker also sets PARALLEL=0, because the compile worker pool's initializer runs Context(TRACK_MATCH_STATS=0) and would hide kernel lowering. It unregisters the atexit hook that would otherwise write rewrites.pkl. Realization is split the way Tensor.realize splits it internally: Tensor.linear_with_vars(*outs) (scheduling), then run_linear (compile and execute). That gives a clean boundary between stages ② and ⑤.

Serialization keeps the JSON small: there is one node table per trace (id → {op, dtype, arg, shape, src ids}, with args formatted by tinygrad's own _render_arg), and every graph is stored as just a root id. Because of hash-consing, a node's id fixes its sources, so the browser rebuilds any graph by walking src from the root. Limits: at most 1500 nodes per graph (the ones nearest the root, as in uop2json), 25k nodes per trace, 160 passes per group.

22.3How to read each stage

For every stage: what goes in, what transformation happens, what comes out, and what to look for in the explorer.

① Tensor graph: UOp.sink(*[t.uop for t in outs])

In: your Python. Out: a DAG of tensor-level UOps: BUFFER (realized inputs), movement ops (RESHAPE, PERMUTE, EXPAND, PAD, SHRINK, FLIP), ALU ops, REDUCE. Shapes live on the nodes. Look for: how a single high-level call (@, softmax, conv2d) expanded into primitives (ch 8), and the extra backward UOps after .backward() (ch 9).

② Schedule passes: Tensor.linear_with_vars

In: the tensor graph. Out: a LINEAR. In order: realized outputs get buf.after(buf.store(compute)) (drop after / substitute bufferize). Then transform_to_call turns buffers into PARAMs and wraps everything in a CALL (replace bufs). Then lower_sink_to_linear runs prepare_rangeify → get_kernel_graph (apply rangeify replaces movement ops with index expressions, stage to store, split kernels) → create_schedule. Finally resolve linear call binds the PARAMs back to buffers, and memory_plan_rewrite packs intermediate buffers into an arena. Look for: the pass where movement ops disappear (apply rangeify) and the pass where the graph splits into CALLs (split kernels). The heat strip above the pass list shows where the matches concentrate.

③ Schedule: the LINEAR

Out: LINEAR(CALL(SINK, buf0, buf1, …), CALL(…), …), in execution order (a Kahn toposort over read-after-write and write-after-read dependencies). A kernel CALL's body is a SINK with KernelInfo. A copy's body is a STORE. The arguments are the buffers, with output first. Look for: how many kernels the preset turned into, and which buffers connect them.

④ Kernel AST

In to codegen: SINK(END(STORE(INDEX(PARAM, idx), value), ranges…)). Every loop is a RANGE; a reduction is REDUCE(value, range). Look for: the index expressions (range*4 + range) that replaced the movement ops.

⑤ Codegen passes: full_rewrite_to_sink

The named passes run in order. simplify ranges merges loops. apply_opts applies the heuristic's OptOps: a pass named shift (0,) 4 upcast is one OptOp being applied. expander turns upcast ranges into vectors. remove reduces rewrites REDUCE into an accumulator register and a loop. expand broadcast / add loads, devectorize2 and memory coalescing regroup loads into float4. lower all index dtypes turns weakint indices into i32. late decompositions rewrites ops the renderer lacks (for example exp2 becomes a polynomial on CPU). add control flow orders the loops. Then linearize/render calls do_linearize, do_estimates, do_render and do_compile.

⑥ Linearized, ⑦ C source, ⑧ Run

linearize orders the DAG into a list (the LINEAR in the PROGRAM). ClangRenderer walks that list and emits one C statement per non-inlined UOp. run_linear then executes the CALLs. In the explorer, click a row in the linearized table to highlight that UOp and its sources in the graph.

22.6Hammer it again: same program, different knobs and shapes

NOOPT=1: what the optimizer contributed

The same matmul with NOOPT=1. Every codegen pass still runs; only hand_coded_optimizations inside apply_opts is skipped (elif not NOOPT and …), so no shift … upcast pass appears. With nothing upcast, remove reduces produces a real accumulator. float buf0[1] is the REG-space ALLOC that lower_reduce creates, and the k-loop survives. Estimated FLOPs go from 112 to 128, because the accumulator also adds into the initial 0.0f:

The scheduler fuses as much as it can. It only materializes a buffer where an elementwise consumer needs a reduce's result broadcast back over the reduced axis, as in softmax and the fused chain, or where several outputs are requested (the MLP's loss and two gradients). Softmax: three kernels, and exp2 written out as a polynomial

softmax = x - max, exp, divide by the sum. tinygrad computes exp(x) as exp2(x·log₂e). The first kernel is the max-reduce; here it is, with the 8-wide reduce upcast into two float4 loads and a chain of compare-selects:

22.8The API contract

22.9Check yourself

The explorer's graph morphs smoothly from "before" to "after" a rewrite. What makes stable node ids possible?
UOpMetaClass caches every UOp by (op, src, arg, type(arg)). A rewrite rebuilds only the path from changed nodes up to the root; everything else is literally the same object (chapter 4).
Why does the tracer run the worker with PARALLEL=0?
engine/worker.py: _init_worker enters Context(ALLOW_DEVICE_USAGE=0, VIZ=0, TRACK_MATCH_STATS=0). With one kernel tinygrad lowers in-process anyway, but presets like softmax have several.
In the matmul trace, which stage first has no RESHAPE/PERMUTE nodes left?
Rangeify assigns every node an index expression built from RANGEs; remove_movement_op_after_rangeify then deletes the movement ops (it fired 5 times). The kernel AST never sees them.
A pass shows matches 6 but its in→out node counts are equal and the graph looks identical. How can that be?
Every successful rule application is a match, including ones whose result was later rewritten by another rule in the same fixpoint. Graph size alone does not measure change; use the highlighted "new" nodes.
Two kernels in the Fused chain preset are both named r_2_4. Are they the same program?
Check the explorer: each kernel group carries prg_key (the PROGRAM's key). Different ASTs, different programs, same pretty name.

Chapter summary

  • The pipeline is Tensor graph → (Tensor.linear_with_vars: bufferize, callify, rangeify, split) → LINEAR of CALLs → per kernel do_to_program (full_rewrite_to_sink, linearize, render, compile) → run_linear.
  • tinygrad records itself: with TRACK_MATCH_STATS=2, @rewrite_group writes tracked_keys/tracked_ctxs, one TrackedGraphRewrite per graph_rewrite, with every rule match.
  • The tracer adds output graphs (a RewriteContext wrapper), per-call timings (a track_stats wrapper) and the compiled PROGRAMs (to_program_cache), and serializes all of it as one hash-consed node table.
  • Read a trace by its deltas: which pass removed the movement ops, where the graph was cut into CALLs, which OptOps were applied, how REDUCE became an accumulator, and which ops were decomposed for the renderer.
  • Use the explorer, examples/22_trace_cli.py or POST /api/trace on any small program to check claims from the other chapters.
