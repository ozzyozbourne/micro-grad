CHAPTER 08From matmul & conv to primitives

Tensor has well over a hundred methods. The tensor graph they build uses about two dozen kinds of UOp. This chapter opens the box: how sub, div, exp, sigmoid, softmax, layernorm, argmax, gather, cumsum, random numbers, and — the two big ones — matmul and conv2d are built out of movement ops (Chapter 7), a handful of ALU ops, and one REDUCE. Every decomposition below is printed from the real graph, not paraphrased.

8.1Intuition: a small brick box

Analogy: LEGO Technic You can build a crane, a car and a clock from the same small set of bricks. The set is chosen so that each brick is easy to make (render on every backend), easy to reason about (one gradient rule each, Chapter 9) and easy to combine (fusion, Chapter 11). Fancy methods are just instructions for assembling bricks — they live in Python mixins, run once when you call them, and leave nothing behind but a graph of bricks.

The "instructions" live in four mixin files that Tensor (and partly UOp) inherit:

filewhat it decomposes
mixin/elementwise.pyarithmetic, comparisons, activations, transcendental functions
mixin/reduce.pysum, prod, max, any, all → REDUCE
mixin/op.pyindexing, matmul/dot/einsum, softmax, norms, losses, conv/pool, cumsum, sort, scatter/gather…
mixin/rand.pyrand, randn, init schemes, dropout, attention

Inputs → transformation → outputs for this whole chapter: input = a Python call like x.softmax(); transformation = ordinary Python in the mixin, which calls other methods and finally alu(op, …), _mop(op, arg) or _rop(op, axis); output = a new lazy Tensor whose uop is a DAG made only of primitive UOps. Nothing is computed.

8.2The brick box: which Ops the tensor graph uses

The Ops enum () has 75 members, but many only exist late in codegen (RANGE, LOAD, STORE, WMMA, SPECIAL…) or are introduced by later rewrites. The tensor-level vocabulary used by the mixins is:

familyops built by Tensor methodspresent in the enum, but not emitted by the mixins for floats
movementRESHAPE PERMUTE EXPAND PAD SHRINK (+ STACK as data)—
unaryEXP2 LOG2 SIN SQRT RECIP TRUNC CAST BITCASTNEG (-x is x * -1)
binaryADD MUL MAX CMPLT CMPEQ POW, and for ints/bits: TRUNCDIV DIV MOD TRUNCMOD XOR OR AND SHL SHR THREEFRYSUB, FDIV, CMPNE (used by codegen/renderers and symbolic)
ternaryWHEREMULACC (fused later)
reduceREDUCE with arg (ADD|MUL|MAX, n_leading_axes)ALLREDUCE (multi-device)
graph plumbingCONST, BUFFER/ALLOC, COPY, STAGE (contiguous), DETACH, CONTIGUOUS_BACKWARD, AFTER/STORE (assign)
Why so few? Every op in this box needs: a shape rule, a dtype rule, a gradient rule (Chapter 9), a constant-folding rule, a symbolic range rule, and a rendering in C, LLVM, PTX, Metal, WGSL… Each op removed from the box removes a column from that matrix. The price — longer graphs — is paid at graph-build time in Python and then disappears: fusion puts all those elementwise bricks into one kernel, and constant folding cleans up things like MUL(1.0, -1.0).

Each line is a small theorem tinygrad relies on:

\[ a-b = a + (-1)\cdot b \qquad \frac{a}{b} = a\cdot \operatorname{recip}(b) \qquad e^x = 2^{x\log_2 e} \qquad \ln x = \log_2 x \cdot \ln 2 \] \[ \sigma(x) = \frac{1}{1 + 2^{-x\log_2 e}} \qquad \operatorname{relu}(x) = \begin{cases}x & 0 < x\\ 0 & \text{else}\end{cases} \qquad \min(a,b) = -\max(-a,-b) \qquad \cos x = \sin(\tfrac\pi2 - x) \]

Source, line by line: sub is a.alu(Ops.ADD, -b) () and -b is b * (-1) (); div is a.alu(Ops.MUL, b.reciprocal()) (); exp (), log (), sigmoid (), relu (), minimum ().

relu is not maximum(x, 0) — on purpose The source comment: "if you write this as self.maximum(0) the gradient is wrong, passing through half when self is 0". The MAX gradient rule splits ties 50/50 (Chapter 9), and x == 0 is a tie. WHERE(0 < x, x, 0) gives exactly 0 gradient at 0. Decompositions are chosen for their gradients as much as for their values.
Comparisons Only CMPLT and CMPEQ are emitted: x > y is y < x, x >= y is (x < y) == False, and x != y is (x == y) == False. POW survives as a primitive at this level (it has its own gradient rule) and is decomposed later by symbolic (symbolic.py:463, xpow) — see Chapter 15.
How many distinct ALU op kinds does (x - y) / y produce in the tensor graph?
x - y = ADD(x, MUL(y, -1)), then / y = MUL(·, RECIP(y)): kinds ADD, MUL, RECIP (MUL appears twice).

8.4Reductions: one REDUCE that eats leading axes

There is a single reduce op. sum, prod, max pick its arg (Ops.ADD, Ops.MUL, Ops.MAX) via _reduce (), and UOp._rop builds it:

tinygrad/uop/ops.py:624 — UOp._rop
def _rop(self, op:Ops, axis:tuple[int, ...]):
  # NOTE: we don't allow reduce on 1s axis
  axis = tuple(sorted(axis))
  reduce_axis = tuple(x for x in axis if resolve(self.shape[x] != 1))
  if not len(reduce_axis):
    return self.reshape(tuple(s for i,s in enumerate(self.shape) if i not in axis))
  # permute so reduced axes are at the front
  perm = reduce_axis + tuple(i for i in range(len(self.shape)) if i not in reduce_axis)
  ret = UOp(Ops.REDUCE, src=(self.permute(perm),), arg=(op, len(reduce_axis)))
  return ret.reshape(tuple(s for i,s in enumerate(self.shape) if i not in axis)) if axis != reduce_axis else ret

Look at the shape rule we saw in Chapter 7: REDUCE's arg is (op, n) and its output shape is ps[n:] — it removes the first n axes. So reducing axis 2 of a (a,b,c) tensor is PERMUTE(2,0,1) then REDUCE(ADD, 1). This is the mirror image of EXPAND, which adds leading axes. (Hold that thought: in Chapter 9 the gradient of one is the other.) Axes of size 1 are never reduced; they are reshaped away.

=== reductions (tinygrad/mixin/reduce.py, op.py)

8.5matmul = broadcast multiply + sum over the shared axis

\( C_{ij} = \sum_k A_{ik} B_{kj} \). Read it as a three-step recipe on a 3-D grid of size \(M\times N\times K\): put \(A_{ik}\) at every \((i, j, k)\) (copy it along \(j\)), put \(B_{kj}\) at every \((i,j,k)\) (copy it along \(i\)), multiply cellwise, then sum along \(k\). That is exactly dot:

tinygrad/mixin/op.py:390 — dot
x, dx, dw = self, self.ndim, w.ndim
if not (dx > 0 and dw > 0): raise RuntimeError(f"both tensors need to be at least 1D, got {dx}D and {dw}D")
if x.shape[-1] != w.shape[axis_w:=-min(w.ndim,2)]: raise RuntimeError(f"cannot dot {x.shape} and {w.shape}")
x = x.reshape(*x.shape[0:-1], *[1]*min(dx-1, dw-1, 1), x.shape[-1])
w = w.reshape(*w.shape[0:-2], *[1]*min(dx-1, dw-1, 1), *w.shape[axis_w:]).transpose(-1, axis_w)
return (x*w).sum(-1, dtype=dtype).cast(least_upper_dtype(x.dtype, w.dtype) if dtype is None else dtype)

For \(A: (M,K)\), \(B: (K,N)\): x becomes (M, 1, K); w becomes (1, K, N) transposed to (1, N, K); x*w is (M, N, K); .sum(-1) reduces \(K\). The real graph, walked from the top:

There is no EXPAND in a matmul graph The "copy along \(j\)" and "copy along \(i\)" are not ops. The MUL's two sources have shapes (2,1,3) and (1,4,3) and its _shape is simply their broadcast, (2,4,3). During rangeify (Chapter 10) each source gets index 0 on its size-1 axis. And the summed axis \(K\) is moved to the front by a PERMUTE because REDUCE eats leading axes. Nothing here allocates an \(M\times N\times K\) buffer: in the kernel this becomes a loop over \(k\) accumulating into a register.
The matmul broadcast cube
\(A\) (2×3) @ \(B\) (3×4) with the same numbers as the example. Step through: reshape A to a slab, reshape+transpose B to a slab, broadcast both into the \(M\times N\times K\) cube, multiply, PERMUTE \(K\) to the front, REDUCE it away. Hover an output cell of \(C\) to light up the row of \(A\), the column of \(B\) and the line of the cube it sums over.
For a batched matmul (B, M, K) @ (B, K, N), which axis does the final REDUCE remove, and where is it before the REDUCE?
dot builds the broadcast product with \(K\) last and calls sum(-1); _rop permutes \(K\) to position 0 and emits REDUCE(ADD, 1). WMMA (tensor cores) only appears much later as an optimization (Chapter 14).

8.6conv2d = _pool (sliding windows from movement ops) + matmul-style reduce

A 2-D convolution multiplies every \(k_h\times k_w\) window of the input with the kernel and sums. The hard part is making the windows: an im2col-like tensor of shape (…, oh, ow, kh, kw) where each output position owns its own window. tinygrad builds it with nothing but movement ops in _pool:

tinygrad/mixin/movement.py:614 — _pool
def _pool(self, k_: tuple[sint, ...], stride: int | tuple[int, ...] = 1, dilation: int | tuple[int, ...] = 1) -> Self:
  assert len(self.shape) >= len(k_), f"can't pool {self.shape} with {k_}"
  s_, d_ = make_tuple(stride, len(k_)), make_tuple(dilation, len(k_))
  assert len(k_) == len(s_) == len(d_), f"stride/dilation mismatch kernel:{k_} stride:{s_} dilation:{d_}"
  noop, i_ = [None] * (self.ndim - len(k_)), self.shape[-len(k_) :]
  assert all(resolve(d * (k - 1) + 1 <= i) for k, d, i in zip(k_, d_, i_)), "kernel size cannot be greater than actual input size"
  o_ = [ceildiv(i - d * (k - 1), s) for i, d, k, s in zip(i_, d_, k_, s_)]
  # input size scaling factor to make sure shrink for stride is possible
  f_ = [smax(1, ceildiv(o * s - d, i)) for o, s, i, d in zip(o_, s_, i_, d_)]
  # repeats such that we don't need padding
  x = self.repeat([1] * len(noop) + [ceildiv(k * (i * f + d), i) for k, i, d, f in zip(k_, i_, d_, f_)])
  # handle dilation
  x = x.shrink_to(noop + [k * (i * f + d) for k, i, d, f in zip(k_, i_, d_, f_)])
  x = x.reshape(noop + flatten((k, (i * f + d)) for k, i, d, f in zip(k_, i_, d_, f_)))
  # handle stride
  x = x.shrink_to(noop + flatten((k, o * s) for k, o, s in zip(k_, o_, s_))).reshape(noop + flatten((k, o, s) for k, o, s in zip(k_, o_, s_)))
  x = x.shrink_to(noop + flatten((k, o, 1) for k, o in zip(k_, o_))).reshape(noop + flatten((k, o) for k, o in zip(k_, o_)))
  # permute to move reduce to the end
  return x.permute(*range(len(noop)), *[len(noop) + i * 2 + 1 for i in range(len(i_))], *[len(noop) + i * 2 for i in range(len(i_))])

The skew trick, in 1-D

Windows of size \(k=3\) over \([0,1,2,3,4,5]\) (\(i=6\), stride 1): repeat the input \(k\) times and flatten (length 24); cut to \(k(i+1)=21\); reshape to \(k\) rows of \(i+1 = 7\). Because each row is one longer than the data, row \(r\) starts one element later than row \(r-1\): row 0 is \(0,1,2,3,4,5,0\), row 1 is \(1,2,3,4,5,0,1\), row 2 is \(2,3,4,5,0,1,2\). Keep the first \(o = 4\) columns and transpose — column \(c\) of the \(3\times 4\) grid is the window starting at \(c\). Stride and dilation are the same trick with different row lengths (i*f + d) and an extra reshape+shrink to take every \(s\)-th window.

8.7Index-y things: arange, one_hot, gather, argmax, cumsum

There is no "iota", "gather" or "scan" primitive. Everything that smells like indexing is built from comparisons against an arange, and arange itself is a cumulative sum built with _pool:

op.py:218 — arange, op.py:775 — _cumalu
return (cls.full((output_len,), step, dtype=acc_dtype, buffer=False)._cumalu(0, Ops.ADD) + (start - step)).cast(dtype)

def _cumalu(self, axis:int, op:Ops) -> Self:
  assert self.shape[axis] != 0 and op in GroupOp.Reduce
  pads = (None,)*(self.ndim-1) + ((self.shape[axis]-1, 0),)
  pooled = self.transpose(axis,-1)._pad_constant(pads, identity_element(op, self.commit_dtype()))._pool((self.shape[axis],))
  return getattr(pooled, {Ops.ADD: "sum", Ops.MAX: "max", Ops.MUL: "prod"}[op])(-1).transpose(axis, -1)

arange(n) = cumsum of n copies of step, plus start - step. And cumsum is: pad n-1 identity elements on the left, take sliding windows of size n with _pool, reduce each window. A window of size \(n\) ending at position \(j\) contains exactly the elements \(0..j\). After rangeify and symbolic, the sum of a constant over a range folds into a closed form, so the kernel does not really loop.

one_hot is idx == arange(C). gather is "multiply by a one-hot and sum": it compares the index against an arange along a new axis and sums the selected values — a tiny matmul with a 0/1 matrix. Tensor indexing x[idx] uses the same one-hot masks (or a linearized index for consecutive tensor indices), which is why out-of-range tensor indices give 0 instead of an error.

Mark the positions equal to the max, multiply by a descending arange \(n, n-1, \dots, 1\), take the max, and subtract from \(n\): the first maximal position wins ties.

  axis = self._resolve_dim(axis)

  # for now this is a two stage cumsum
  SPLIT = 256

8.8Random numbers: THREEFRY on a counter

Tensor.rand is a pure function of a per-device seed and counter (Tensor._next_counter, ): the counter is a 1-element uint64 tensor that is incremented with an assign each time you draw numbers. The bits come from the THREEFRY op — the Threefry-2x32 block cipher (counter-based PRNG, as in JAX) — applied to arange counters:

tinygrad/mixin/rand.py:12 — _threefry_random_bits, _bits_to_rand
def _threefry_random_bits(key, counts0, counts1):
  x = (counts1.cast(dtypes.uint64) << 32) | counts0.cast(dtypes.uint64)
  x = x.threefry((key[1].cast(dtypes.uint64) << 32) | key[0].cast(dtypes.uint64))
  return x.cast(dtypes.uint32).cat((x >> 32).cast(dtypes.uint32))

def _bits_to_rand(bits, shape:tuple[int, ...], dtype:DType):
  _, nmant = dtypes.finfo(dtype)
  uint_dtype = {1: dtypes.uint8, 2: dtypes.uint16, 4: dtypes.uint32, 8: dtypes.uint64}[dtype.itemsize]
  uint_bits = bits.bitcast(uint_dtype)
  float_one_bits = bitcast(1.0, dtype, uint_dtype)
  return uint_bits.rshift(dtype.bitsize - nmant).bitwise_or(float_one_bits).bitcast(dtype)[:prod(shape)].sub(1).reshape(shape)

_bits_to_rand is a classic trick: put random bits in the mantissa of a float whose exponent says "1.x", which gives a uniform number in \([1,2)\); subtract 1. randn uses Box–Muller (hence SIN and LOG2), so a model input built with Tensor.randn drags THREEFRY, SHL, SHR, OR, BITCAST, SIN into the graph — which is why the op counting script realizes its inputs first. Because the generator is counter-based, the random graph is just more lazy UOps that fuse into whatever consumes them (dropout masks are generated inside the kernel that uses them).

def report(name, model, x, y):
  x = x.realize()   # realize the random input so its THREEFRY/SIN (Box-Muller) graph is not counted as "model"
  for p in get_parameters(model): p.realize()
  with Context(TRAINING=1):
    loss = model(x).sparse_categorical_crossentropy(y) if y.ndim == 1 else model(x).flatten(0, 1).sparse_categorical_crossentropy(y.flatten())
  params = [p for p in get_parameters(model) if p.is_floating_point()]   # BatchNorm also holds an int counter
  fwd = Counter(u.op for u in loss.uop.toposort())
  grads = loss.gradient(*params)
  both = Counter(u.op for u in UOp.sink(loss.uop, *[g.uop for g in grads]).toposort())
  CAPTURE[name] = {"forward": {o.name: n for o, n in fwd.items()}, "forward+backward": {o.name: n for o, n in both.items()}}
  for label, c in [("forward", fwd), ("forward+backward", both)]:
    compute = {o: n for o, n in c.items() if o not in PLUMBING}
    alu = sorted((o.name for o in compute if o not in MOVEMENT and o is not Ops.REDUCE))
    mv = sorted((o.name for o in compute if o in MOVEMENT))
    print(f"{name:16s} {label:17s} {sum(c.values()):5d} UOps | {len(compute):2d} distinct compute ops: "
          f"{len(mv)} movement {mv} + REDUCE + {len(alu)} ALU {alu}")
  return both

8.11Hammer it again: trade-offs and what breaks

  • Graph size vs vocabulary size. tanh is 13 UOps (via sigmoid), Tensor.rand(4) is ~90. That is fine: graph building is a few microseconds per UOp, hash-consing deduplicates shared subtrees (softmax's two exp branches are one node), and the schedule cache (Chapter 12) means it is done once per shape under a JIT.
  • Performance is recovered later. x * recip(y) becomes a division again if the backend prefers; EXP2/LOG2/SIN are either native or decomposed into polynomials (Chapter 15); MUL+ADD become MULACC; matmul-shaped reduces become tensor-core WMMA (Chapter 14).
  • Numerics. \(e^x = 2^{x\log_2 e}\) costs one extra rounding of the product; sigmoid as 1/(1+2^{…}) saturates gracefully to 0/1. The softmax DETACHed max shift keeps exp from overflowing.
  • Integer arithmetic is different. // and % on ints use DIV/MOD (floor semantics) and TRUNCDIV/TRUNCMOD for C semantics; x / y on ints casts to float first. minimum on ints uses an XOR trick instead of negation (no negative of unsigned).
  • conv memory? The pooled tensor is conceptually \(k_h k_w\) times larger than the input, but it is a view: no buffer of that size exists unless the scheduler decides to materialize it.
Which primitive op kinds does Tensor.arange(4) contain?
From the output: Tensor.arange(4) uses ADD, CAST, EXPAND, PAD, PERMUTE, REDUCE, SHRINK. RANGE only appears after rangeify; there is no iota op at the tensor level.
x.gather(1, idx) with x of shape (N, C): which "shape" of computation is it, as decomposed?
See gather: index.unsqueeze(-1)._one_hot_along_dim(C).where(x, 0).sum(-1). Later, rangeify + symbolic can often turn this pattern back into a direct indexed load (the "arange folding" rules), but at the tensor level it is a masked reduce.

Chapter summary

  • Tensor methods are Python recipes in mixin/{elementwise,reduce,op,rand}.py; their output is a DAG of ~two dozen primitive UOp kinds.
  • Elementwise: sub = ADD(a, MUL(b,-1)), div = MUL(a, RECIP(b)), exp = EXP2(x·log₂e), log = LOG2·ln2, sigmoid = RECIP(1+EXP2(−x·log₂e)), relu = WHERE(0<x, x, 0), min = −max(−a,−b).
  • One REDUCE(op, n) that removes the leading n axes (after a PERMUTE). softmax/log_softmax/layernorm are compositions with a DETACHed max shift and rmsnorm.
  • matmul = reshape A to (M,1,K), B to (1,N,K), implicitly broadcast MUL to (M,N,K), PERMUTE K first, REDUCE. No EXPAND, no M×N×K buffer.
  • conv2d = pad + _pool (repeat → flatten → reshape into rows one longer = sliding windows) + broadcast MUL + REDUCE over (cin, kh, kw).
  • arange is a pooled cumsum; one_hot/gather/argmax/tensor-indexing are comparisons with arange + WHERE + REDUCE; rand is THREEFRY on counters.
  • Real models use ~16–17 kinds of compute op; backward adds no new kinds. Next: Chapter 9 — gradients as more of the same bricks.
