CHAPTER 12The schedule: CALLs, LINEAR & memory

Chapter 11 produced a graph of kernels connected by AFTERs. A GPU wants a list. This chapter covers what happens between the kernel graph and kernels actually running: putting the kernels in order (create_schedule), the final form of a schedule (a LINEAR of CALLs), how abstract PARAM/ALLOC slots become real BUFFERs, how the memory planner packs intermediates into one arena, why the second call of a function with new data skips scheduling entirely (the schedule cache), how symbolic Variables pass through as var_vals, and how engine/realize.py compiles and runs the list.

12.1 Intuition: a recipe card with blanks

A schedule is a recipe: "step 1: run kernel r_4_8 on (tray A, input 1); step 2: run kernel E_4_8 on (output, input 1, tray A)". tinygrad first writes the recipe with blanks — "input 1", "a temporary tray" — and only fills in actual memory when you cook. Because the recipe has blanks, it can be reused: the next time you ask for the same computation on different data, it's the same recipe with different things in the blanks. That's the schedule cache. And since a temporary tray is only needed between the step that fills it and the last step that reads it, a planner can put several trays on the same shelf space: the memory planner.

The key ideaThe final schedule is a UOp(Ops.LINEAR, src=(CALL, CALL, …)). Each CALL's src[0] is the kernel body (a SINK AST, later a PROGRAM; or a STORE for a copy) and src[1:] are the buffers it receives, positionally. The schedule is computed once per shape of computation with placeholders (PARAM for inputs, ALLOC for temporaries), cached by the hash of that placeholder graph, and bound to real buffers every time it's used.

12.2 The entry point: create_linear_with_vars

Tensor.realize is three lines:

def realize(self, *lst:Tensor, do_update_stats=True) -> Tensor:
  to_realize = [x for x in (self,)+lst if x.uop.base.needs_storage()]
  if len(to_realize):
    linear, var_vals = Tensor.linear_with_vars(*to_realize)
    run_linear(linear, var_vals, update_stats=do_update_stats)
  return self

linear_with_vars gives each output fresh storage (buf.after(buf.store(compute))), re-points all live Tensors at that storage (so the next realize() is a no-op), and calls create_linear_with_vars:

def create_linear_with_vars(big_sink:UOp) -> tuple[UOp, dict[str, int]]:
  big_sink = transform_to_call(big_sink)
  # big_sink srcs are all the Tensors
  linear_call = graph_rewrite(big_sink, pm_schedule, name="schedule to linear", enter_calls=True)
  # this recursively resolves the linear_call and allocates buffers
  linear = graph_rewrite(linear_call, pm_resolve_linear_call, name="resolve linear call")
  # create copies
  linear = graph_rewrite(linear, pm_copy_from_store, name="lower copy kernels to STORE calls")
  # vars used in the schedule
  used_vars = set().union(*[{v.expr for v in si.src[0].variables()} for si in linear.src])
  var_vals: dict[str, int] = {}
  for b in big_sink.src[1:]:
    if b.is_bound_var:
      nm, val = b.expr, b.arg.val
      if nm not in used_vars: continue
      if var_vals.get(nm, val) != val: raise RuntimeError(f"bind mismatch on {nm}, {var_vals[nm]} != {val}")
      var_vals[nm] = val
  # jit captures this schedule, no need to execute.
  if len(capturing) and CAPTURING:
    capturing[0].add_linear(linear)
    return UOp(Ops.LINEAR, src=()), var_vals
  held_bufs = {b for b in linear_call.src[1:] if b.op is Ops.BUFFER}
  return memory_plan_rewrite(linear, held_bufs), var_vals

12.3 Ordering: create_schedule turns AFTERs into a list

After get_kernel_graph, dependencies are implicit in the graph: a kernel reads a buffer through AFTER(buffer, CALL_that_wrote_it). create_schedule extracts a dependency graph and topologically sorts it (Kahn's algorithm, BFS with a deque):

  • RAW (read-after-write): for every kernel k and every buffer state it reads (_states unwraps views to a BUFFER/PARAM/ALLOC or an AFTER), if that state is an AFTER, each kernel in it must run before k.
  • WAR (write-after-read): for every kernel that reads state S of a buffer, every other write that supersedes S must wait for it. This is what makes b = a*10; a.assign(a+1) correct: the kernel reading the old a runs before the in-place update.
  with cpu_profile(TracingKey("linearize schedule")):
    queue: deque[UOp] = deque(k for k,v in in_degree.items() if v == 0)
    linearized: list[UOp] = []
    while len(queue):
      rk = queue.popleft()
      k = rk.src[0] if rk.op is Ops.END else rk
      buf_uops = tuple(_unwrap_src(s).buf_uop for s in k.src[1:] if not s.is_bound_var)
      linearized.append(k.replace(src=(k.body, *buf_uops)))      # strip the AFTERs: args become plain buffers
      for x in children.get(rk, []):
        in_degree[x] -= 1
        if in_degree[x] == 0: queue.append(x)
    if any(in_degree.values()): raise RuntimeError("cycle detected in assign graph")
  return UOp(Ops.LINEAR, src=tuple(linearized))

Note the k.replace(src=(k.body, *buf_uops)): once a kernel is in the list, its position is its dependency info, so the AFTER wrappers on its arguments are stripped. The second half of the 12_schedule.py output shows the result for (b, a, c): CALL 0 reads the old a (BUFFER#8) into b, CALL 1 updates a in place (one arg), CALL 2 reads the new a into c — and the printed values confirm it: b = 10·old, c = 100·new.

In b = a * 10; a.assign(a + 1); c = a * 100, which dependency forces the kernel computing b to run before the assign?
The scheduler doesn't know your statement order; only the graph. The WAR loop in create_schedule adds the edge b-kernel → assign-kernel.

12.4 Buffers: BUFFER, PARAM, ALLOC — and their numbering

UOpmeaningwhere it comes from
BUFFERbound storage: a real Buffer on a device (arg=ParamArg(slot, dtype, device, buffer=…))UOp.new_buffer; your realized tensors; created by create_new_buffer for temporaries
PARAM (outer)"argument #slot of the enclosing CALL"pm_replace_buf in transform_to_call: each GLOBAL BUFFER in the tensor graph, in order of first appearance; bound Variables too
ALLOC"storage to be allocated", call-local; canonical negative slots inside the cached bodybufferize_to_store (temporaries), stage_to_anon_store (contiguous), copy_to_anon_store (copies); canonicalize_alloc renumbers them
PARAM (kernel)"argument #slot of this kernel"debuf in split_store: the kernel's own buffers numbered 0, 1, 2… in order of discovery

Two levels of PARAM is the thing to keep straight. Inside a kernel AST, PARAM 0 means "this kernel's first argument"; the kernel's CALL lists, positionally, what that argument is in the outer schedule. Positional, slot-numbered placeholders at both levels are what make both the schedule cache and the kernel compile cache hit across different programs.

pm_post_sched_cache fills the blanks, inside resolve_linear_call (pass "params to buffers"):

def create_new_buffer(ctx:tuple[UOp, ...], b:UOp):
  device = b.device if b.device is not None else next(a.device for a in ctx if a.device is not None)
  return UOp.new_buffer(device, b.max_numel(), b.dtype)

pm_post_sched_cache = PatternMatcher([
  # Resolve positional arguments outside kernel bodies; free Variables have slot -1.
  (UPat(Ops.PARAM, name="x"), lambda ctx,x: ctx[x.arg.slot] if x.arg.slot >= 0 else None),
  # bind ALLOCs to fresh BUFFERs for this invocation
  (UPat(Ops.ALLOC, name="b"), create_new_buffer),
])

The walk=True flag on that rewrite means kernel bodies (CALL srcs[0]) aren't entered: kernel-level PARAMs stay put.

12.6 Memory planning: one arena for all temporaries

Every intermediate (h1, h2, h3, logits, row max, row sum) got its own fresh BUFFER from create_new_buffer. But h1 is dead once h2 is computed. memory_plan_rewrite exploits that:

def memory_plan_rewrite(linear:UOp, held_bufs:set[UOp]|None=None) -> UOp:
  if NO_MEMORY_PLANNER: return linear
  # compute lifetimes for all plannable internal buffers
  first_appearance, last_appearance, copy_bufs = {}, {}, set()
  for i, si in enumerate(linear.src):
    si_bufs = [b for src in si.src[1:] for b in _collect_bufs(src) if _can_plan(b, held_bufs)]
    for b in si_bufs:
      if b not in first_appearance: first_appearance[b] = i
      last_appearance[b] = i
    if si.src[0].op is Ops.STORE: copy_bufs.update(si_bufs)
  ...
  # suballocation: build sorted open/close events, then alloc/free in order
  block_size = 256
  nbytes = {b: round_up(b.max_numel() * b.dtype.itemsize, block_size) for b in first_appearance}
  events = sorted([(first_appearance[b], True, b) for b in first_appearance] +
                  [(last_appearance[b] + 1 + buf_hold.get(b, 0), False, b) for b in first_appearance], key=lambda x: (x[0], x[1]))
  ...
  for _, is_open, buf in events:
    if is_open: offsets[buf] = peaks[_key(buf)][1].alloc(nbytes[buf])
    else: peaks[_key(buf)][1].free(offsets[buf])
  ...
  # build replace_map: each buffer becomes a SHRINK/BITCAST into a shared per-device-lane arena
  arenas = {key: UOp.new_buffer(key[0], sz, dtypes.int8) for key, sz in arena_sizes.items()}
  replace_map = {buf_uop:arenas[_key(buf_uop)][offset:offset+buf_uop.nbytes()].bitcast(buf_uop.dtype) for buf_uop, offset in offsets.items()}
  return linear.substitute(replace_map, name="memory plan", walk=True)
  • What is planned: buffers that appear in CALL args and are not in held_bufs (the outer CALL's arguments: your inputs and outputs, which must outlive the schedule) and not on DISK/CL/WEBGPU (no sub-buffer views there).
  • Lifetime: [first CALL index, last CALL index]. Events are sorted by time with frees before allocs at the same index (False < True), so a buffer last used by kernel 1 can be reused by a buffer first written by kernel 2.
  • Allocator: a TLSFAllocator (two-level segregated fit, the same allocator as the runtime's) over a virtual space, 256-byte blocks.
  • Lanes: one arena per (device, copy?) pair. Copy buffers live in a separate lane and are held one extra lifetime so a copy engine and a compute engine never fight over the same bytes.
  • Result: each temporary becomes arena[offset:offset+nbytes].bitcast(dtype) — that's the BITCAST(SHRINK(BUFFER)) you saw as arena#4[0:+16] above. With DEBUG≥1 it prints memory reduced from X MB -> Y MB, n -> m bufs. Disable with NO_MEMORY_PLANNER=1.

12.7 The schedule cache

With DEBUG=1, every schedule of more than one kernel prints a line like

scheduled 2 kernels in 52.82 ms | CACHE MISS eb417c35 | 89 uops in cache | …/12_schedule_cache.py:17

It comes from lower_sink_to_linear, the single pattern of pm_schedule:

schedule_cache: dict[bytes, UOp] = {}
def lower_sink_to_linear(call:UOp) -> UOp|None:
  function = call.body
  if function.op is not Ops.SINK or isinstance(function.arg, KernelInfo) or not call.arg.precompile: return None
  st = time.perf_counter()
  cache_key = function.key
  # SCACHE >= 2 also persists the cache to disk
  sc_ret, disk_hit = schedule_cache.get(cache_key, None) if SCACHE else None, False
  if sc_ret is None and SCACHE >= 2: disk_hit = (sc_ret:=diskcache_get("schedule_cache", {"key": cache_key})) is not None
  if sc_ret is None:
    if SPEC: type_verify(function, spec_tensor)
    linear = create_schedule(get_kernel_graph(prepare_rangeify(function)))
    if SCACHE: schedule_cache[cache_key] = linear
    if SCACHE >= 2: diskcache_put("schedule_cache", {"key": cache_key}, linear)
  else:
    linear = schedule_cache[cache_key] = sc_ret
  ...
  return call.replace(src=(linear,)+call.src[1:])
  • The key is function.key: the structural hash of the CALL body built by transform_to_call. In that body every input/output BUFFER is a PARAM(slot), every ALLOC has a canonical slot, and every bound Variable is a value-free PARAM. So the key captures ops, shapes, dtypes, devices and the pattern of buffer use — not which buffers or which variable values. The 8 hex digits printed are cache_key.hex()[:8].
  • The value is the LINEAR straight out of create_schedule: CALLs whose args are still PARAMs and ALLOCs. Everything expensive (rangeify, remove_bufferize, splitting, ordering) is skipped on a hit; only resolve_linear_call + memory planning run per call.
  • SCACHE=0 disables it (the example scripts in Chapters 10–11 do this so the passes actually run); SCACHE=2 also uses the disk cache.

12.8 Symbolic variables and var_vals

A Variable("bs", 1, 16).bind(3) is a bound variable: a symbol plus a current value. pm_replace_buf turns it into a value-stripped PARAM in the body (so all values share one key: calls 5 and 6 above hit), while the bound UOp itself is passed as a CALL argument. At the end of create_linear_with_vars, the values of variables that are actually used by some kernel are collected into var_vals, e.g. {'bs': 3}, with a check that one name isn't bound to two values. The kernels are compiled once with bs as a runtime argument (kernel names like E_bs_4), and exec_kernel passes var_vals[p.expr] for every ALU PARAM of the program.

Which of these changes produces a schedule-cache hit for f(x) = x / x.sum(1, keepdim=True)?
Shapes, dtypes and devices are in the PARAM-ized body; buffer identity and contents are not. Values of bound Variables aren't either.

12.9 Running it: engine/realize.py

run_linear:

def run_linear(linear:UOp, var_vals:dict[str, int]|None=None, input_uops:Sequence[UOp]=(), update_stats=True, jit=False, wait=False):
  assert linear.op is Ops.LINEAR, f"run_linear calls on {linear.op}"
  if len(linear.src) == 0: return
  inputs = list(input_uops)
  if not jit: linear = link_linear(compile_linear(linear, validate=VALIDATE_WITH_CPU, input_uops=inputs, cache=True), input_uops=inputs)
  ctx = ExecContext(var_vals or {}, tuple(inputs), update_stats, jit, wait or DEBUG>=2)
  for call in linear.src: track_stats(ctx, call.without_after, perf_counter_us(), pm_exec.rewrite(call.without_after, ctx))
  1. compile_linear: optionally wrap calls for CPU validation (VALIDATE_WITH_CPU) or tag them for BEAM search, then lower_and_compile: every CALL(SINK(KernelInfo)) is deduped by to_program_key, compiled with to_program (all of Part IV: optimize, lower, linearize, render, compile) — in parallel worker processes when there are several — cached in to_program_cache, and substituted back as CALL(PROGRAM). Then hcq_compile batches calls into command queues for HCQ devices (AMD, NV, METAL, CUDA…); for CPU it leaves the list alone.
  2. link_linear → hcq_link: resolve addresses / patch command buffers.
  3. pm_exec, a PatternMatcher used as a dispatcher, one call at a time: CALL(STORE) → exec_copy, CALL(PROGRAM) → exec_kernel (allocate buffers lazily with ensure_allocated, look up the runtime, compute launch dims from var_vals, call it), or exec_hcq.

Why does pm_post_sched_cache turn ALLOCs into fresh BUFFERs on every call, even on a cache hit?
Keeping the cached schedule free of memory is what makes it reusable; binding happens per call in resolve_linear_call.
What's the type of the object Tensor.linear_with_vars returns as its first element?
There's no ScheduleItem class in this version. The schedule is IR too: LINEAR of CALLs, with kernel ASTs as CALL bodies.

Chapter summary

  • Input: the SINK of output stores from Tensor.linear_with_vars. Output: LINEAR(CALL(body, *buffers), …) + var_vals.
  • transform_to_call PARAM-izes the graph; its body's hash is the schedule cache key. A hit skips rangeify/splitting/ordering entirely.
  • create_schedule derives RAW and WAR dependencies from AFTERs and topologically sorts the kernels, stripping the AFTERs.
  • resolve_linear_call binds PARAMs to the call's real buffers and ALLOCs to fresh BUFFERs; copy kernels become CALL(STORE).
  • memory_plan_rewrite computes lifetimes over the list and packs temporaries into one arena per device/lane with a TLSF allocator.
  • run_linear: compile_linear (to_program per kernel, cached, parallel) → link_linear → pm_exec per CALL.
