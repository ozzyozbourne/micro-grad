CHAPTER 10 Rangeify: from shapes to loops

A tensor graph talks in shapes: "this is a (4, 3) view of that (3, 4) buffer, plus one, summed over axis 0". A kernel talks in loops: "for r0 in 0..3, for r1 in 0..4, load buf[r0*4+r1]". Rangeify is the translation between those two languages. After this chapter you will know exactly which UOps get their own loops (the realize map), how loop variables (RANGE UOps) are handed from consumers down to producers, how every movement op dissolves into index arithmetic, and what the STAGE (a.k.a. BUFFERIZE) marker means — all against the real code in run_rangeify.

This is the first of three scheduling chapters. 10 (this one): shapes → ranges & materialization candidates. 11: which candidates survive and how the graph is cut into kernels. 12: ordering the kernels into a LINEAR of CALLs, buffers, memory planning, caching. Movement ops themselves are introduced in Chapter 7, the symbolic simplifier in Chapter 6.

10.1 Intuition: every output element asks a question

Take out = (a.permute(1, 0) + 1).sum(0) with a of shape (3, 4). In tensor-land this is a little pipeline of whole arrays. But a kernel never manipulates whole arrays: it runs a loop, and in each iteration it asks "for output element r0, which input element(s) do I need?". Answering that question for every node of the graph is rangeify.

tensor-land (what you wrote)
a   = Tensor.empty(3, 4)   # a buffer of 12 floats
t   = a.permute(1, 0)      # (4, 3)  — a VIEW, no data moves
u   = t + 1                # (4, 3)
out = u.sum(0)             # (3,)    — reduce over the 4
loop-land (what rangeify produces, in pseudo-C)
for (r0 = 0; r0 < 3; r0++) {        // RANGE r0: one per output element
  acc = 0;
  for (r1 = 0; r1 < 4; r1++)         // RANGE r1: created by the REDUCE
    acc += a[r0*4 + r1] + 1;         // permute+reshape became r0*4+r1
  out[r0] = acc;                     // STORE ... END(r0)
}

Read the right-hand side bottom-up and notice what happened to each tensor op:

  • The output (3,) got one loop variable r0 — a RANGE UOp.
  • The sum(0) needed a loop over the reduced axis: it created a fresh range r1.
  • The + 1 just passed the ranges (r1, r0) through — elementwise ops don't care.
  • The permute(1, 0) swapped them: the element at t[r1, r0] is a[r0, r1].
  • The hidden reshape from the flat 12-float buffer to (3, 4) turned the pair into one flat offset r0*4 + r1.

The movement ops are gone. They didn't move data, they only changed which address is read. That is the whole trick: a view is an index function, and composing views is composing index functions.

The key idea Ranges flow from consumers down to producers. Each UOp receives the loop variables of whoever reads it, transforms them (movement ops rewrite them, reduces add new ones), and passes them on to its own sources. When a UOp can't simply take its consumer's ranges — because two consumers want it at different positions, or because a consumer needs it complete before it can broadcast it — it gets fresh ranges and is marked to be materialized into a buffer. That set of UOps is the realize map, and it is the seed of every kernel boundary in Chapter 11.
Analogy Think of a big spreadsheet where every cell of the output has a formula. Rangeify writes the formula for one generic cell out[r0], with r0 as a symbol, by substituting definitions all the way down to raw input cells. A movement op is like a cell reference with arithmetic in it (=A!B(r0*4+r1)). A "realized" intermediate is a helper column you decided to actually fill in, because inlining its formula everywhere would be wrong or too expensive.

def schedule(*tensors:Tensor, run=True):
  """schedule (and optionally run) tensors, returning (log, linear, compiled_linear)"""
  # SCACHE=0: a schedule-cache hit would skip all passes (see chapter 12)
  with Context(SCACHE=0), hooked() as log:
    linear, var_vals = Tensor.linear_with_vars(*tensors)
  compiled = compile_linear(linear)
  if run: run_linear(linear, var_vals)
  return log, linear, compiled

def kernel_sources(compiled:UOp) -> list[tuple[str, str]]:
  """(name, source code) for every CALL in a compiled LINEAR"""
  out = []
  for call in compiled.src:
    body = call.body
    if body.op is Ops.PROGRAM:
      srcs = [u.arg for u in body.toposort() if u.op is Ops.SOURCE]
      out.append((body.src[0].arg.name, srcs[0] if srcs else ""))
    elif body.op is Ops.STORE: out.append(("copy", "// bulk copy: CALL(STORE(dst, src)) -> exec_copy, no kernel is compiled"))
    else: out.append((str(body.op), ""))
  return out

def _arg_label(u:UOp) -> str:
  if u.op in GroupOp.Movement:
    try: return str(u.marg).replace(" ", "")
    except Exception: return ""
  if u.op is Ops.RANGE: return f"r{u.arg[1]} <{u.src[0].render() if u.src[0].op is not Ops.CONST else u.src[0].arg}"
  if u.op in {Ops.PARAM, Ops.BUFFER, Ops.ALLOC}:
    a = u.arg
    kind = {Ops.PARAM: "slot", Ops.BUFFER: "buf", Ops.ALLOC: "slot"}[u.op]
    try: return f"{kind} {a.slot} · {u.max_numel()}×{str(a.dtype).replace('dtypes.', '')}"
    except Exception: return str(a)[:40]
  if u.op is Ops.CONST: return str(u.arg).replace("ConstFloat(", "").rstrip(")") if "ConstFloat" in str(u.arg) else str(u.arg)
  if u.op is Ops.REDUCE: return f"{u.arg[0].name}" + (f", {u.arg[1]} axes" if u.arg[1] else "")
  if u.op is Ops.STAGE: return "" if u.arg is None else ("BUFFERIZE" + ("" if u.arg.removable else " (keep)"))
  if u.op is Ops.SINK and u.arg is not None: return "kernel"

def hidden_srcs(u:UOp) -> set[int]:
  """indices of srcs that are 'shape arguments', not data"""
  if u.op in GroupOp.Movement: return set(range(1, len(u.src)))
  if u.op in {Ops.PARAM, Ops.BUFFER, Ops.ALLOC, Ops.RANGE}: return set(range(len(u.src)))
  return set()

def graph_json(root:UOp, ids:dict|None=None, notes:dict|None=None, max_nodes=260) -> dict:
  ids = {} if ids is None else ids
  keep: list[UOp] = []
  seen = set()
  def visit(u:UOp):
    if u in seen: return
    seen.add(u)
    for i, s in enumerate(u.src):
      if i not in hidden_srcs(u): visit(s)
    keep.append(u)
  visit(root)
  keep = keep[-max_nodes:]
  present = set(keep)
  nodes, edges = [], []
  for u in keep:
    nid = ids.setdefault(u, f"n{len(ids)}")
    try: shape = str(u._shape) if u._shape is not None else ""
    except Exception: shape = ""
    try: dt = str(u.dtype).replace("dtypes.", "")
    except Exception: dt = ""
    n = {"id": nid, "op": u.op.name, "arg": _arg_label(u), "dtype": dt if dt not in ("void",) else "", "shape": shape.replace(" ", "")}
    if notes and u in notes: n["note"] = notes[u]
    nodes.append(n)
    for i, s in enumerate(u.src):
      if i in hidden_srcs(u) or s not in present: continue
      edges.append([ids.setdefault(s, f"n{len(ids)}"), nid, i])
  return {"nodes": nodes, "edges": edges}

def pass_by_name(log, name, nth=0):
  hits = [p for p in log["passes"] if p[0] == name]
  return hits[nth] if nth < len(hits) else None

10.3 The input: what the graph looks like when rangeify starts

By the time run_rangeify sees the graph, three things have already happened to your tensor graph (Chapter 2 showed you its raw form):

  1. Tensor.linear_with_vars gave each output storage: an output that is not already a buffer becomes buf.after(buf.store(compute)), i.e. AFTER(BUFFER, STORE(BUFFER, compute)). "AFTER" means: this buffer, but only after these effects ran (see Ops.AFTER's comment in tinygrad/uop/__init__.py).
  2. transform_to_call collected those stores ("early transform tensor graph") and replaced every real input BUFFER with a positional PARAM(slot) ("replace bufs"), producing CALL(SINK(...), *buffers). The body no longer mentions any concrete memory — that's what makes the schedule cacheable (Chapter 12).
  3. prepare_rangeify ran multi_pm, "inline calls" and "earliest rewrites". The important rewrites for us (earliest_rewrites):
    • .contiguous() (which is an Ops.STAGE on the tensor side, contiguous) becomes a STORE into a fresh call-local ALLOC: stage_to_anon_store.
    • a cross-device COPY becomes a STORE into a fresh ALLOC on the destination device: copy_to_anon_store.
    • big reductions into few outputs are split in two: split_reduceop (Chapter 11).
    • DETACH / CONTIGUOUS_BACKWARD vanish, size-0 tensors become constants.

So the graph that reaches rangeify is: a SINK of AFTER(PARAM, STORE(PARAM-view, compute)), where compute is still in tensor form — shapes, RESHAPE/PERMUTE/EXPAND/PAD/SHRINK, and REDUCE(op, n_axes) whose reduced axes have been permuted to the front (UOp._rop). The output of examples/10_apply_rangeify.py in §10.8 shows such a graph verbatim.

There is no ShapeTracker, no LazyBuffer, no ScheduleItem in this version. Older tinygrad tracked views with a ShapeTracker object and merged views symbolically; today movement ops are ordinary UOps until rangeify turns them into index expressions, and "view merging" is just the symbolic simplifier working on those expressions (see the comment in _apply_reshape: "this is the replacement for the reshape view merging code").

10.5 The realize map: who must be materialized, and why

IndexingContext holds the state of the whole algorithm:

@dataclass
class IndexingContext:
  realize_map: dict[UOp, None|list[int]] = field(default_factory=dict)   # UOp -> which axes get fresh ranges
  non_removable: dict[UOp, None] = field(default_factory=dict)
  range_map: dict[UOp, tuple[tuple[UOp, ...], tuple[UOp, ...]]] = field(default_factory=dict)  # UOp -> (input rngs, output rngs)
  range_idx: Iterator[int] = field(default_factory=itertools.count)
  def new_range(self, s:sint) -> UOp:
    if isinstance(s, UOp) and s.op is Ops.RANGE: return s
    # if a range has a 1 src, it's the same as UOp.const(0)
    return UOp.range(s, next(self.range_idx)) if resolve(s!=1) else UOp.const(0)

Phase 1 — structural: pm_generate_realize_map (pass "get realize")

Phase 2 — dataflow: decided during the walk in run_rangeify

While walking the graph (next section), two situations add a UOp to the realize map:

  • Disagreeing consumers. A UOp with 2+ consumers whose ranges are not identical (e.g. y + y.T: one reader wants y[r0, r1], the other y[r1, r0]). It can't inherit a single set of loop variables, so the axes where they differ get fresh ranges and it is (partially) realized.
  • Ending ranges. When a consumer broadcasts a value (an EXPAND, or a binary op whose input has a size-1 axis where the output doesn't), the ranges it iterates over that axis "end" there: the value must be complete for every position of that axis before it can be reused. If an elementwise op or a REDUCE has pending ending ranges, it is realized. This is why x - x.max(1, keepdim=True) needs the row maximum in a buffer.
Candidates, not kernels The realize map is a list of candidates. Everything except STOREs (and removable=False stages) may still be un-realized by pm_remove_bufferize in Chapter 11 if recomputing is cheaper than storing. E.g. softmax has 4 candidates + 1 STORE, but ends up as 3 kernels.

10.6 The walk: run_rangeify, line by line

run_rangeify visits the graph in reverse topological order — outputs first, buffers last — so that when it reaches a UOp, all of that UOp's consumers have already been assigned ranges. Here's the core (lightly trimmed):

for x in reversed(tsink_toposort):
  if x.op in {Ops.CALL, Ops.AFTER, Ops.MSTACK, Ops.MSELECT}: continue     # no ranges on these
  ending_ranges[x] = sum([ending_ranges.get(u, []) for u in consumer_map[x]], [])
  # ranges the consumers iterate that this node broadcasts over
  ended = [rctx.range_map[c][0][i] for c in consumer_map[x] if c in rctx.range_map and c.op in GroupOp.Broadcastable
           for i in broadcast_axes(x.shape, c.shape)]
  broadcast_ending_ranges = list(UOp.sink(*ended).ranges)
  if x.op is Ops.REDUCE: ending_ranges[x] += broadcast_ending_ranges     # fusion decision: REDUCE before the broadcast

  # *** the ranges on the output are
  #  1. new if this op is realized
  #  2. from the single consumer if this op only has one consumer
  #  3. potentially new if this op has 2+ consumers
  consumer_rngs = [broadcast_rngs(c, x, rctx.range_map[c][0]) for c in consumer_map[x] if c in rctx.range_map]
  if x in rctx.realize_map:
    out_rngs = tuple(rctx.new_range(s) for s in x.shape)                # 1. fresh ranges
    ending_ranges[x] = []
    rctx.realize_map[x] = list(range(len(x.shape)))
  elif len(consumer_rngs) == 0: continue                                  # nobody needs it with ranges
  elif len(consumer_rngs) == 1: out_rngs = consumer_rngs[0]               # 2. inherit
  elif len(consumer_rngs) > 1:                                            # 3. merge or realize
    ...  # if all consumers agree (ignoring validity): OR their valids together
         # otherwise: new range on every axis, and realize_map[x] = those axes

  if len(ending_ranges[x]) and x.op in GroupOp.Elementwise.union({Ops.REDUCE}):
    rctx.realize_map[x] = list(range(len(out_rngs)))                     # ending ranges: realize
    out_rngs = tuple(rctx.new_range(x.shape[i]) for i in range(len(out_rngs)))
    ending_ranges[x] = []
  ending_ranges[x] += broadcast_ending_ranges

  # *** the ranges on the inputs are
  #  1. swizzled for MovementOps   2. newly created for REDUCE   3. passed through for everything else
  rngs = out_rngs
  if x.op in GroupOp.Movement: rngs = apply_movement_op(x.op, x.src[0].shape, x.marg, rngs)
  if x.op is Ops.REDUCE: rngs = tuple(rctx.new_range(s) for s in x.src[0].shape[:x.arg[1]]) + out_rngs
  rctx.range_map[x] = (rngs, out_rngs)

Two numbers per UOp come out of this: out_rngs (the ranges at which the UOp's value is indexed) and rngs (the ranges handed down to its sources). For an elementwise op they are equal; for a movement op rngs is out_rngs transformed by apply_movement_op; for a REDUCE rngs prepends freshly created ranges for the reduced axes. broadcast_rngs drops (replaces with 0) the consumer ranges for axes the source is broadcast along.

# this is the definition of the movement ops
@functools.cache
def apply_movement_op(op:Ops, in_shape:tuple[sint,...], arg:tuple, rngs:tuple[UOp, ...]) -> tuple[UOp, ...]:
  match op:
    case Ops.SHRINK:  rngs = tuple(a if off == 0 else a+off for a,(off,_) in zip(rngs, arg))
    case Ops.PERMUTE: rngs = tuple(rngs[p] for p in argsort(arg))
    case Ops.EXPAND:  rngs = rngs[len(arg):]
    case Ops.PAD:
      rngs = tuple(r if (sz == sh and off == 0) else (r-off).valid(graph_rewrite((r >= off) & (r < (sh+off)),
        symbolic+pm_simplify_valid, name="pad")) for r,sh,(off,sz) in zip(rngs, in_shape, arg))
    case Ops.RESHAPE:
      sink = UOp.sink(*rngs).simplify()
      sub_array = {r:r.replace(arg=(AxisType.PLACEHOLDER, i)) for i,r in enumerate(sink.ranges)}
      rngs = _apply_reshape(in_shape, arg, sink.substitute(sub_array)).substitute({v:k for k,v in sub_array.items()}).src
    case _: raise RuntimeError(f"{op} is not a MovementOp")
  return rngs

Two details are specific to this version. First, EXPAND only prepends axes: numpy-style broadcasting of a size-1 axis
  is built by _broadcast_to as reshape (squeeze the 1s) →
  EXPAND (prepend) → PERMUTE (move them back), so the expanded axis's range simply never reaches the buffer. Second, there is no
  FLIP op: flip is assembled from pads, reshapes, a transpose and shrinks (an anti-diagonal trick in
  mixin/movement.py), and the simplifier collapses the

RESHAPE: the only op that needs real math


@functools.cache
def _apply_reshape(in_shape:tuple[sint,...], out_shape:tuple[sint, ...], urngs:UOp) -> UOp:
  acc:sint = 1
  axes_in:list[UOp] = []
  for s,src in list(zip(out_shape, urngs.src))[::-1]:
    axes_in.append(acc*src)
    acc *= s
  combined_axes = UOp.const(0).usum(axes_in)
  axes_out:list[UOp] = []
  for s in in_shape[::-1]:
    axes_out.append(combined_axes % s)
    combined_axes //= s
  # this simplify is doing a lot of heavy lifting. this is the replacement for the reshape view merging code
  return graph_rewrite(UOp.sink(*axes_out[::-1]), symbolic+pm_simplify_valid+pm_drop_and_clauses, name="reshape")

  
For output index \((i_0,\dots,i_{n-1})\) of shape \((o_0,\dots,o_{n-1})\) the linear position is
  \(L = \sum_k i_k \prod_{j>k} o_j\); the input index along axis \(k\) of shape \((s_0,\dots)\) is
  \(\left\lfloor L / \prod_{j>k} s_j \right\rfloor \bmod s_k\). Without simplification that's a pile of // and
  %; the symbolic rules of Chapter 6 use the ranges' bounds (0 ≤ r < size)
  to fold it, e.g. (r0*4+r1)//4 → r0 and (r0*4+r1)%4 → r1 because r1 < 4. The
  placeholder substitution (AxisType.PLACEHOLDER) renames ranges to canonical ids so that @functools.cache
  hits for every reshape with the same shapes, regardless of which ranges flow in.

10.8 Applying the ranges: pm_apply_rangeify

  
The walk only computes range_map and realize_map. The graph is rewritten afterwards, bottom-up,
  by pm_apply_rangeify (pass "apply rangeify"):


pm_apply_rangeify = PatternMatcher([
  # REDUCE(op, axis) -> REDUCE(op) with ranges
  (UPat(Ops.REDUCE, name="x"), convert_reduce_to_reduce_with_ranges),
  # PAD -> WHERE
  (UPat((Ops.PAD, Ops.INDEX), name="x"), convert_pad_to_where_to_keep_behavior_local),
  # STACK -> WHERE select on the leading range
  (UPat(Ops.STACK, name="x"), convert_stack_to_where),
  # finally, apply_rangeify
  (UPat(GroupOp.All-{Ops.STAGE, Ops.INDEX}, name="x"), create_bufferize_and_index_based_on_ranges),
  # remove movement op
  (UPat(GroupOp.Movement, name="x"), remove_movement_op_after_rangeify),
])

  
The workhorse is create_bufferize_and_index_srcs.
  For every src s of a UOp x:

  
    
    
  • if s is a buffer (PARAM/BUFFER/ALLOC/AFTER/…):
    replace it by s.index(*rngs) — a load at the input ranges of x;
    • 
    
  • if s is in the realize map and is a STORE: replace it by s.end(*closed_ranges);
    • 
    
  • if s is in the realize map otherwise: wrap it as
    STAGE(s, *closed_ranges, arg=BufferizeOpts(device, removable=...)) and index that with x's ranges. The
    STAGE iterates the fresh ranges the walk gave s; the INDEX is where the consumer reads it.
    • 
  

  
Then the leftovers are cleaned: a movement op whose src is now an INDEX is simply removed (its effect already lives in the
  index), PAD → WHERE multiplies in the validity
  (valid.where(x, 0), so padded positions produce 0 without loading), and
  REDUCE is rebuilt as REDUCE(src, *new_ranges,
  arg=(op, 0)) listing exactly the ranges it created. Finally "add device to deviceless" puts a device on STAGEs that had none.

10.9 Hammer it again: three views of the same mechanism

  
View 1 — as substitution

  
Forget graphs. Write the output as a function of its index and keep substituting definitions:

  \[\text{out}[r_0] = \sum_{r_1=0}^{3} u[r_1, r_0],\quad u[i,j] = t[i,j]+1,\quad t[i,j] = a[j,i],\quad a[p,q] = \text{buf}[4p+q]\]
  \[\Rightarrow\ \text{out}[r_0] = \sum_{r_1=0}^{3} \left(\text{buf}[4r_0 + r_1] + 1\right)\]
  
Every "=" sign is one step of run_rangeify. Movement ops are the rows where only the subscript changes. The REDUCE
  is where a new bound variable \(r_1\) appears.


  
View 2 — as "who can share my loop?"

  
A node can be computed inside its consumer's loop iff it is needed exactly once per iteration, at a position the consumer
  can express. One consumer → always (just inherit the ranges). Two consumers at the same position → fine (the merge branch:
  all_all_same, validity OR-ed). Two consumers at different positions, or a consumer that needs all
  values along an axis before it can use any (the broadcast-after-reduce case) → not in the same loop: it needs its own loop
  nest — fresh ranges, a STAGE.

Edge cases worth knowing

  
    
    
  • Size-1 axes never get a RANGE: new_range(1) returns CONST 0. That's why you see
    [r0][0] in the debug table for (4,1) shapes.
    • 
    
  • Reduce to a scalar (x.mean()) has shape (): no output ranges at all, so it has nothing to
    realize along — it is computed inside whatever loop reads it. That's why x - x.mean() is one kernel while
    x - x.mean(1, keepdim=True) is two (Chapter 11 has both side by side).
    • 
    
  • Symbolic shapes (a Variable dimension) make ranges with a symbolic bound; several cleanups skip them
    (cleanup_dead_axes: "skip for symbolic. TODO").
    • 
    
  • STACK (from Tensor.stack/cat on scalars) becomes a WHERE tree selecting on the leading
    range (_stack_select).
    • 
    
  • EXPAND that injects a range (an EXPAND whose new sizes are themselves RANGEs) is not counted as ending ranges. The
    comment in the code admits the heuristic: "this doesn't actually always end a range, but this is why convs are realized".
    • 
  


  
  
10.10 Why it's designed this way

  
    
    
  • One IR all the way down. After rangeify the graph is already almost a kernel AST: STORE(INDEX(buf, expr), value)
    with RANGEs and END. Splitting it into kernels (Chapter 11) is just cutting at STAGE/STORE, and the
    codegen (Chapter 13) starts from exactly this form. There's no separate "lowering from
    views to indices" stage later.
    • 
    
  • Fusion is the default. Nothing is materialized unless a rule says so; the rules are local (consumers of one node).
    Elementwise chains, reduces of elementwise expressions, and arbitrary views all fuse for free.
    • 
    
  • View merging is algebra. Instead of a special data structure that has to know when two views can merge (the old
    ShapeTracker's hard problem), rangeify composes index expressions and lets the general symbolic simplifier fold them. If it can't
    fold, you get // and % in the kernel — correct, just slower.
    • 
    
  • Over-propose, then prune. The walk is conservative (it realizes on any disagreement); a separate cost-based pass decides
    which candidates are worth a buffer. Each piece stays simple.
    • 
  


  

    
In y = x + 1; out = y + y.T, why is y (the ADD) in the realize map?

    
    
    
    
    
The 2+-consumers branch compares the consumers' ranges; they differ, so every axis gets a new range and the ADD is (partially) realized. It's later removed by pm_remove_bufferize (cheap to recompute), giving one kernel.

  


  

    
Which of these makes a REDUCE result a realize candidate?

    
    
    
    
    
REDUCE collects broadcast_ending_ranges from its consumers; pending ending ranges on an elementwise/REDUCE node realize it. (The 32768 threshold is split_reduceop, which splits rather than realizes.)

  


  

    
What does a STAGE(value, r2, r3) node mean right after "apply rangeify"?

    
    
    
    
    
STAGE with BufferizeOpts is the bufferize marker. It may still be removed (recompute) or turned into an ALLOC+STORE (Chapter 11).

  


  

    
x.reshape(2, 6).reshape(4, 3) on a flat 12-element buffer: what is the final index for output [r0, r1]?

    
    
    
    
The intermediate step really is ((r0//2), (r0%2*3+r1)) (see the example output), but the second reshape's flatten (r0//2)*6 + r0%2*3 + r1 simplifies to r0*3 + r1: the two reshapes "merged" through algebra.

  


  
Chapter summary
    
    
  • Input: a tensor-form SINK of AFTER(PARAM, STORE(...)) with shapes and movement ops (after transform_to_call + prepare_rangeify).
    Output: the same computation written with RANGE, INDEX, REDUCE(…ranges), END, and STAGE (BUFFERIZE) wrappers around materialization candidates.
    • 
    
  • run_rangeify walks outputs → inputs. Each UOp's output ranges are fresh (if realized), inherited (one consumer), merged (agreeing consumers) or fresh+realized (disagreeing). Inputs get the ranges transformed by apply_movement_op, or extended with new reduce ranges.
    • 
    
  • Realize map = STOREs, MSELECT/MSTACK srcs, custom-kernel srcs, hazardous store sources (phase 1), plus disagreeing multi-consumer nodes and nodes with ending (broadcast) ranges (phase 2).
    • 
    
  • Movement ops become index math: SHRINK adds, PERMUTE reorders, EXPAND drops, PAD adds a validity condition (→ WHERE), RESHAPE flattens/unflattens with ///% and the symbolic simplifier merges views.
    • 
    
  • Realize-map entries are only candidates; Chapter 11 decides which survive.
