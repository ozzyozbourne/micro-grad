CHAPTER 16Linearizer & renderers

At the end of Chapter 15 the kernel is still a graph: a SINK whose ancestors are scalar (or float4) ALU ops, LOADs, STOREs, and RANGE/END pairs that delimit loops. A CPU or GPU wants a sequence of instructions. This chapter covers the last three steps of codegen: linearize (turn the DAG into a list, with properly nested loops), render (turn each UOp into a line of C, LLVM IR, PTX, WGSL… or into machine instructions with real registers), and compile (turn the text into a binary). The same 4×8 reduction kernel runs through all of it, through ten renderers, and finally through clang into x86 machine code.

16.1Intuition: from a dependency chart to a recipe card

A DAG only says what depends on what. "Load x[r,c] before adding it" is in the graph; "write the three loops in this order and close each one before the next opens" is not. Picture a kitchen dependency chart (sauce needs onions, onions need chopping) versus the recipe card a cook actually reads top to bottom. Linearizing is writing the card: any order that respects the arrows is correct as far as data goes, but some orders are better (load early, store late, keep work out of loops when it doesn't depend on the loop) and, because of loops, some orders that respect every arrow are still nonsense.

AnalogyRANGE and END are parentheses. The DAG tells you which tokens must appear inside each pair of parentheses (everything that depends on the range), but nothing stops a naive toposort from writing ( [ ) ]. In C, } always closes the most recent {, so the linear order must be properly nested. tinygrad gets this by adding a few extra edges to the graph before linearizing (§16.3), so that any toposort is properly nested.

Our running kernel is (x.sum(1) + x.max(1)) for x of shape 4×8, compiled with no optimizations (opts_to_apply=()) so all three loops stay visible: an outer loop over the 4 rows, and two sibling inner loops over the 8 columns, one accumulating the sum and one the max. class CFGContext:
  def __init__(self, sink:UOp):
    # there are 3 relationships between ranges:
    # nested, meaning endrange y is a dependency of endrange x and range x is a dependency of endrange y
    # dependent, meaning endrange y is a dependency of endrange x and range x is not a dependency of endrange y
    # independent, endrange y is not a dependency of endrange x
    # everything is nested inside the sink
    deps: dict[UOp, dict[UOp, None]] = {}
    nesting: dict[UOp, UOp] = {}
    for u in sink.toposort():
      # get the deps from the src
      deps[u] = {}
      for s in u.src_without_body: deps[u] |= deps[s]

      if u.op in (Ops.END, Ops.BACKEDGE, Ops.SINK):
        nesting |= {x:u for x in deps[u] if x.op in (Ops.END, Ops.BACKEDGE) and (u.op is Ops.SINK or u.src[1] in deps[x]) and x not in nesting}
      if u.op in (Ops.RANGE, Ops.END, Ops.BACKEDGE): deps[u][u] = None

    self.edges: dict[UOp, UOp] = {}
    siblings: dict[UOp, list[UOp]] = {}
    for k,vv in nesting.items(): siblings.setdefault(vv, []).append(k)
    for k,v in siblings.items():
      # ranges that have dependencies on other siblings need to be scheduled after them
      order = sorted(v, key=lambda x: len([u for u in v if u in deps[x]]))
      zipped = zip(order, order[1:]) if k.op is Ops.SINK else zip([k.src[1]] + order, order)
      for x,y in zipped:
        # TODO: this can happen! it causes infinite loop in shufflenet
        assert y.src[1] not in x.backward_slice_with_self
        self.edges[y.src[1]] = x

pm_add_control_flow = PatternMatcher([
  # the ordering dep goes on the bound wrapped in AFTER, so a RANGE always has exactly one src
  (UPat(Ops.RANGE, name="x"), lambda ctx,x: x.replace(src=(x.src[0].after(y),)) if (y:=ctx.edges.get(x)) is not None else None),
])

Read it in three moves:

  1. deps: walking the graph in toposort order, deps[u] is the set of RANGE/END UOps that u (transitively) depends on. Every RANGE/END adds itself.
  2. nesting: when we reach an END u (or the SINK), every not-yet-assigned END x in its deps whose own deps contain u's RANGE (u.src[1]) is nested inside u. Anything not nested in a loop ends up nested in the SINK. So nesting maps each END to its immediate parent.
  3. siblings → edges: group ENDs by parent. Sort the siblings by how many of the other siblings they already depend on (data-dependent siblings must come later), then chain them: the first sibling's RANGE must come after the parent's RANGE; each later sibling's RANGE must come after the previous sibling's END. (Under the SINK there is no parent RANGE, so only the sibling chain.)

The edge is materialized in the cheapest possible way: pm_add_control_flow rewrites the RANGE so its bound becomes AFTER(bound, y). A RANGE still has exactly one source; it just can't be scheduled before y. For our kernel:

== 1. CFGContext on the sink entering 'add control flow' ==
  RANGE(axis 0)    must come after RANGE(axis 2)   -> the RANGE's bound gets wrapped: AFTER(bound, RANGE(axis 2))
  RANGE(axis 1)    must come after END(axis 0)   -> the RANGE's bound gets wrapped: AFTER(bound, END(axis 0))
  in the final sink these show up as AFTER uops feeding the RANGE bounds:
    RANGE(axis 2)    src[0] = CAST(CONST)
    RANGE(axis 0)    src[0] = AFTER(CAST, RANGE(axis 2))
    RANGE(axis 1)    src[0] = AFTER(CAST, END(axis 0))
Why a RANGE "floats"A RANGE UOp's only source is its bound (a constant here). Nothing in the plain DAG says the for (c…) loop must start after the for (r…) loop: the body depends on both ranges, but the RANGE itself depends on neither. So a priority toposort is free to open an inner loop before the outer one. With two siblings the priorities happen to save us; with three they don't.

def linearize(sink:UOp) -> list[UOp]:
  # this is a toposort with priority
  lst = list(sink.toposort())
  out_degree:defaultdict[UOp, int] = defaultdict(int)
  priorities:dict[UOp, tuple[int, int, int, Any]] = {}

  # get consumers and assign priorities
  # NOTE: this requires the lst be locally toposorted
  for u in reversed(lst):
    for s in u.src_without_body: out_degree[s] += 1

    # we place UOps with higher run_counts later
    run_count = prod([int(r.vmax)+1 for r in u.ranges])

    # simple priority override. this is all bottom up now, smaller numbers will be closer to the top
    extra = None
    match u.op:
      # the order and placement of these defines is important
      case Ops.PARAM: priority, extra = -20, u.arg.slot
      case Ops.BUFFER | Ops.ALLOC: priority = -17 if u.addrspace == AddrSpace.LOCAL else -18
      case Ops.LOAD: priority = -1    # place loads early
      case Ops.STORE: priority = 1    # place stores late
      case Ops.RANGE: priority = 5    # placing RANGE is good
      case Ops.END | Ops.BACKEDGE: priority = -5     # placing loop exits is bad
      case _: priority = 0            # everything else has priority 0
    priorities[u] = (run_count, len(u.ranges), priority, extra)

  # number the uops in "ideal" order
  nkey = {u:i for i,u in enumerate(sorted(lst, key=lambda x: priorities[x]+(x.tuplize if TUPLE_ORDER else ())))}

  # then force them to be toposorted in as close to the ideal order as possible
  heap = [(-nkey[sink], sink)]
  newlst = []
  while heap:
    newlst.append(u:=heapq.heappop(heap)[1])
    for v in u.src_without_body:
      out_degree[v] -= 1
      if out_degree[v] == 0: heapq.heappush(heap, (-nkey[v],v))
  newlst = newlst[::-1]

  if getenv("DEBUG_LINEARIZE"):
    for i,u in enumerate(newlst):
      print(f"{i:4d} {str(u.op):20s} {multirange_str(u.ranges, color=True, pad=10)} {priorities[u]}")
  return newlst

The algorithm, precisely:

  1. Priority key for each UOp: (run_count, len(u.ranges), op_priority, extra).
    • run_count = ∏ (range.vmax+1) over the ranges the UOp lives in: how many times it executes. Things that run 4 times sort before things that run 32 times. This is what hoists alu0 = Lidx2<<3 out of the inner loops: it only depends on the outer range, so its run count is 4, not 32.
    • len(u.ranges): depth, a tie-breaker.
    • op_priority: PARAM −20 (with the slot as extra, so arguments come in order), BUFFER/ALLOC −18 (−17 for LOCAL), LOAD −1 ("place loads early"), STORE +1 ("place stores late"), RANGE +5, END/BACKEDGE −5 ("placing loop exits is bad"), everything else 0.
  2. Ideal numbering nkey: sort the toposorted list by that key; ties are broken by u.tuplize (a structural key: op, repr(arg), dtype, then the sources' tuplize), because TUPLE_ORDER defaults to 1. That makes the order independent of how the graph happened to be built. If the ideal order were a valid toposort we'd be done; usually it isn't (a STORE with priority +1 must still come after its LOAD, which may have a larger run count).
  3. Repair by a heap toposort from the bottom: start with the SINK; repeatedly pop the ready UOp with the largest nkey and place it (at the end of the program, growing upward); a source becomes ready when all its consumers are placed (out_degree hits 0). Reverse at the end. Because placement is bottom-up, "largest nkey first" means "as late as possible" for things the ideal order wants late, and things that want to be early end up early.

def line_rewrite(lst:list[UOp], pm:PatternMatcher, ctx=None) -> list[UOp]:
  newlst = []
  replaced: dict[UOp, UOp] = {}
  for u in lst:
    nu = u.replace(src=tuple([replaced.get(x, x) for x in u.src]))
    ret: tuple[UOp, list[UOp]] = pm.rewrite(nu, ctx) or (nu, [nu])
    replaced[u] = ret[0]
    newlst.extend(ret[1])
  return newlst
  • pm_linearize_cleanups: a gated STORE STORE(idx, val, gate) (a store guarded by a condition, produced by the "move gates from index" stage of Chapter 15) becomes three lines: IF(gate), the ungated STORE, ENDIF. This is the only producer of IF/ENDIF, and IF/ENDIF already in the graph is an error. (Gated loads stay as LOAD(idx, alt, gate) and render as a ternary.)
  • pm_alloc_to_buf: ALLOC (the accumulator registers of lower_reduce) becomes BUFFER, the op the renderers know (float buf0[1];).

For ISA renderers line_rewrite is used three more times (pre-regalloc, regalloc itself, post-regalloc), see §16.12. It is the list-world analogue of graph_rewrite.

          mults = mults.substitute({x:x.const_like(0) for x in mults.toposort() if x.op is Ops.SPECIAL}) if isinstance(mults, UOp) else mults
      elif u.op in {Ops.END, Ops.BACKEDGE}: mults = mult_stack.pop(-1)
      elif u.op is Ops.SPECIAL: mults *= cast(sint, u.src[0].ssimplify()) # NOTE: we don't push to the mult_stack here, you can't end these
      elif u.op is Ops.LOAD and u.src[0].addrspace != AddrSpace.REG:
        lds += u.max_numel() * u.dtype.itemsize * mults
      elif u.op is Ops.STORE and u.src[0].addrspace != AddrSpace.REG:
        lds += u.max_numel() * u.src[1].dtype.itemsize * mults
      elif u.op in GroupOp.ALU and u not in excluded:
        flops += (mults * (2 if u.op is Ops.MULACC else 1)) * u.max_numel()
      elif u.op is Ops.WMMA and u not in excluded:
        flops += 2 * prod(u.arg[0]) // u.arg[2] * mults
    return Estimates(ssimplify(flops), lds, sum(mem.values()))

It walks the list keeping a multiplier stack: each RANGE multiplies by its trip count, each END pops. ALU ops add mults FLOPs (×2 for MULACC) unless they are pure index arithmetic (ignore_indexing excludes everything feeding an INDEX); LOAD/STORE to non-register memory add bytes; mem counts each PARAM buffer at most once (capped at its size). Check it by hand for our kernel, Estimates(ops=100, lds=272, mem=144):

  • ops: inner sum loop: 1 ADD × 32 = 32. Inner max loop: CMPLT + WHERE = 2 × 32 = 64. Outer: the final ADD × 4 = 4. alu0 = Lidx2<<3 and alu0+Lidx0 are indexing, excluded. Total 100.
  • lds: the two inner loops each LOAD 32 floats from data1 = 2×32×4 = 256 bytes, plus 4 stores of 4 bytes = 16. Loads/stores of the REG accumulators don't count. Total 272.
  • mem: data1 is read twice but capped at its size, 128 bytes; data0 16 bytes. Total 144.

These numbers are what DEBUG=2 prints as GFLOPS and GB/s after a kernel runs, BEAM search (Chapter 14) ranks candidates by timing real runs, and only uses estimates.ops to throw away candidates that need 1000× more compute than the cheapest one (codegen/opt/search.py:138).

If you UPCAST the inner reduce axis by 8 (so the 8 loads become one float4 pair and the 7 adds become a horizontal chain), what happens to Estimates.ops?
Estimates counts work, not loop structure: an ALU op adds mults × u.max_numel(). Unrolling removes the loop multiplier but creates more (or wider) ALU UOps. Measured with Opt(OptOps.SPLIT, axis, (8, AxisType.UPCAST)): 96 when the sum axis is upcast, 92 for the max axis (the 8 lanes need 7 combining ops instead of 8 accumulations), versus 100 without opts: the same arithmetic, minus the accumulator updates.

  • Skipped: CONST (consts are always wrapped in a CAST since "cast consts", and the CAST renders the literal), NOOP, SINK (just records the function name), void AFTER; a non-void AFTER aliases its first source (that's how the control-flow edges of §16.3 vanish from the text).
  • Naming: PARAM → data{slot}_{shape} (data1_32), RANGE → {axis letter}idx{axis} (Lidx0; L for loop, g/l for global/local), SPECIAL → its arg (gidx0), otherwise a prefix + counter: val for LOAD, bidx INDEX, cast CAST/BITCAST/STACK, buf BUFFER, wmma, and alu for everything else (including STORE and END, which is why our kernel jumps from alu0 to alu5).
  • Inline or declare: CAST-of-CONST, INDEX, single-use register LOADs and single-use ALU/CAST/BITCAST/STACK (except WHERE) are inlined: r[u] becomes the expression itself. Anything else gets its own line <type> <name> = <expr>; and the counter advances.
  • Indentation: depth goes up after RANGE/IF and down at END/ENDIF; each line is prefixed with " "*depth. Because the list is properly nested, that is all it takes to get correctly nested braces.

In the reduce kernel, why is there float alu5 but no alu1…alu4?
The prefix table maps anything that isn't WMMA/BUFFER/CAST/INDEX/LOAD to "alu", and c[prefix] += 1 runs for every line appended to kernel, including *(buf1+0) = 0.0f; (alu1), the inner STORE (alu2), the } (alu3), the -inf store (alu4). 16.11Beyond C: LLVM IR, PTX, NIR, and renderer/amd

  • LLVM IR (llvmir.py:162): same skeleton (walk the list, name values %v0, %v1…, a string_rewrite of strings) but the target is SSA with explicit control flow, so a RANGE becomes four basic blocks loop_entry_N / loop_latch_N (a phi for the counter, compare, conditional branch) / loop_body_N, and the END becomes loop_footer_N + the branch back + loop_exit_N. REG buffers become alloca, LOCAL buffers addrspace(3) globals. CPULLVMRenderer compiles in-process with LLVM; AMDLLVMRenderer targets amdgcn.
  • PTX (ptx.py:137): NVIDIA's virtual ISA. asm_for_op maps each op to an instruction template (ex2.approx.f32, fma.rn, setp.lt, selp); registers are typed and declared up front with counts (.reg .f32 %alu_f32_<12>;). It is the only renderer that prints MAX natively (max.f32), and it has its own ptx_matcher (bool CMPLT as XOR+AND, etc.).
  • NIR (nir.py:115): doesn't produce text at all.   1. pre instruction selection (graph, bottom-up): legalize things x86 can't do directly (gated loads/stores, flags).
  2. instruction selection (graph, bottom-up, isel_matcher): every LOAD/STORE/ALU/CONST becomes an Ops.INS UOp whose arg is (X86Ops.VADDSS, dtype, Register("v4", cons=XMM)). The register is virtual: a name and a tuple of allowed real registers (cons). Addresses fold into [base + idx*scale + disp] operands. The graph is still a graph.
  3. linearize, exactly as for C.
  4. pre_regalloc_matcher (list): stack buffers get a lea, RANGE is lowered to mov idx, 0 / LABEL / cmp idx, bound / jge exit, END to add idx, 1 + END; flag-reading instructions are rematerialized next to their compare.
  5. register allocation (LinearScanRegallocContext + pm_regalloc_rewrite): every virtual register gets a real one, with spills/fills if needed.
  6. insert_linearized: save/restore callee-saved registers that were used (rbx, rbp, r12–r15) and reserve the stack frame.
  7. post_regalloc_matcher: RET at the SINK, jmp back + exit LABEL at each END, and two-address fix-up (x86 add a, b overwrites a; if regalloc didn't put the result in the first source's register, a mov is inserted).
  8. do_assemble: asm() encodes each INS to bytes and patches jump offsets (render() returns the hex); X86Compiler.compile is just bytes.fromhex.

class LinearScanRegallocContext:
  # returns the uop that defines the virtual register
  def vdef(self, v:Register) -> UOp: return self.uops[self.live_range[v][0]]
  def __init__(self, ctx:LinearContext, uops:list[UOp], ren:ISARenderer):
    self.uops = uops
    self.ren = ren
    self.idx = itertools.count()

    # compute live ranges
    self.live_range: dict[Register, list[int]] = {}
    lr = self.live_range
    loops: dict[int, int] = {} # the interval of each loop, from its RANGE to the last non pseudo uop that reads that RANGE
    for idx,u in reversed(list(enumerate(uops))):
      if u.op in PSEUDO_OPS: continue
      defs = regs(u)
      for v in defs + tuple(rdef(s) for s in dedup(u.src)):
        if isinstance(v, Register): lr.setdefault(v, []).insert(0, idx)
      for v in defs:
        if (n:=max((e for s,e in loops.items() if s <= lr[v][-1] < e), default=None)): lr[v].append(n)
      if u.op is Ops.RANGE: loops[idx] = max(j for j,x in enumerate(uops) if u in x.src and x.op not in PSEUDO_OPS)

    # allocate registers
    self.spills: dict[Register, Any] = {} # mapping from virtual to arbitrary spill slot
    self.reals: dict[int, dict[Register, Register]] = {} # mapping from virtual to real at each program point
    self.insert_before: dict[int, list[tuple[Register, Register]]] = {} # fills to be inserted at each program point
    live: dict[Register, Register] = {} # mapping from virtual to real that's currently assigned to it
    live_ins: list[dict[Register, Register]] = [] # mapping from virtual to real at loop entry

    def alloc(cons:tuple[Register, ...], i:int) -> Register:
      live_inv = {v:k for k,v in live.items()}
      # allocate the best register. Registers not in live or not used again are free and have priority,
      # otherwise pick the one with the furthest next use. Regs that appear first in cons have priority in case of a tie
      reg,vreg = max(((r,live_inv.get(r)) for r in cons),
                    key=lambda rv: next((j-i for j in ([] if rv[1] is None else lr[rv[1]]) if j >= i), len(uops)))
      return live.pop(vreg) if vreg is not None else reg

    # assign register to spilled virtual and record load to be emitted before current uop, also assign it a stack slot
    def fill(v:Register, i:int, cons:tuple[Register, ...]|None=None) -> Register:
      if v not in self.spills:
        self.spills[v] = ctx.assign_spill_slot(v, self.vdef(v))
      r = alloc(cons if cons is not None else v.cons, i)
      self.insert_before.setdefault(i, []).append((v, r))
      return r

    for i,u in enumerate(uops):
      if u.op in PSEUDO_OPS: continue
      # allocate uses
      for s in u.src:
        if not isinstance(v:=rdef(s), Register): continue
        if v not in live: live[v] = fill(v, i)
        self.reals.setdefault(i, {})[v] = live[v]

      # allocate defs
      if regs(u):
        for j,v in enumerate(regs(u)):
          if v not in live:
            cons = v.cons
            # two address instructions (src is reused by def) can only coalesce reused src.
            # reused src goes first to get priority in case of a tiebreak
            if ren.is_two_address(u) and j == 0:
              uses = tuple(live.get(rdef(s)) for s in u.src)
              cons = ((uses[0],) if uses[0] in cons else ()) + tuple(r for r in cons if r not in uses)
            live[v] = alloc(cons, i+1)
          self.reals.setdefault(i, {})[v] = live[v]

      # loop prologue, avoid loading inside the loop
      if u.op is Ops.RANGE:
        # we move to registers vars used in the loop sorted by next use, vars not used in the loop will not be reloaded in the epilogue
        used_in_loop = [v for v in live.keys() | self.spills.keys() if any(i <= l < loops[i] for l in lr[v])]
        sorted_uses = sorted(used_in_loop, key=lambda k: (next(l-i for l in lr[k] if l >= i), lr[k][0], k.name, k.index))
        live_in: dict[Register, Register] = {}
        for v in sorted_uses:
          # if all the possible registers are already in live_in there's no space for this var
          if set(v.cons).issubset(live_in.values()): continue
          if v not in live: live[v] = fill(v, i)
          live_in[v] = live[v]
        live_ins.append(live_in)

      # loop epilogue at the loop's last reader, reload registers that were live at loop entry
      if i in loops.values():
        # TODO: if a uop is in a different reg in live out vs live in move between registers instead of loading
        # TODO: don't reload if first use in loop is a load
        live_in = live_ins.pop()
        for v,r in live_in.items():
          if v not in live or live[v] != r: live[v] = fill(v, i, (r,))
        # a spilled var that only got a register inside the loop must be forced to reload from spill slot
        for v in list(live.keys()):
          if v in self.spills and v not in live_in: live.pop(v)
  • Live ranges (backwards pass): the list of positions where each virtual register is defined or used. One subtle extension: if a value is defined outside a loop and used inside it, the next iteration reads it again, so its range is extended to the loop's last instruction. (Going backwards, a loop is only in loops once its RANGE has been passed, so a value defined inside the outer loop is only extended to the end of the inner loops that read it.)
  • Allocation (forward pass): at each instruction, sources must be in registers (fill from the spill slot if not), then definitions get a register via alloc: prefer a free register; otherwise evict the one whose next use is furthest away (Belady's heuristic), which becomes a spill.
  • Loops: at a RANGE, values used inside the loop are loaded into registers (prologue); at the loop's last reader they are reloaded into the same registers they had at entry (epilogue), so every iteration starts with the same register assignment.

16.15Hammer it again: the same ideas from other angles

  • The linearizer only orders. It never adds or removes computation, except IF/ENDIF and ALLOC→BUFFER in line_rewrite. Every decision about what to compute was made in Chapters 13–15. If generated code looks wrong, the bug is almost always upstream; DEBUG_LINEARIZE=1 prints the list with ranges and priorities to check.
  • Correct nesting is a graph property. CFGContext puts the loop structure into the graph as AFTER edges, so the linearizer stays a generic priority toposort. The three-sibling example shows that without those edges a perfectly valid toposort is an invalid program.
  • Hoisting comes free from run_count. Anything that depends on fewer ranges executes fewer times and sorts earlier. No separate loop-invariant code motion pass.
  • Renderers are mostly tables. code_for_op, type_map, prefixes, and a string PatternMatcher. The heavy lifting (vectorization, decompositions, launch dims) was done by lowering, parameterized by those tables. That's why tinygrad can support ten backends in a few thousand lines.
  • Same UOps, different contracts. A RANGE is a for in C, four basic blocks and a phi in LLVM, mov/cmp/jge…add/jmp on x86; SPECIAL is get_group_id, blockIdx.x, %ctaid.x or a workgroup builtin. Switch the tabs in §16.12 with that in mind.
You write a new GPU renderer for a C-like language that has exp2 but no sin, and whose work-group id is wg_id(0). What is the minimum you must provide?
Everything else is generic. Leaving SIN out of code_for_op is enough for get_transcendental_patterns to replace it with xsin (Chapter 15). The linearizer and CFGContext don't care about the target language at all.
What is in a fully built PROGRAM UOp for the Clang renderer?
pm_to_program appends one source per step: LINEAR (do_linearize), then estimates are written into the SINK's KernelInfo, then SOURCE (do_render), then BINARY (do_compile). ProgramInfo is computed from the final sink in do_to_program. The CALL that uses the PROGRAM is the schedule's business (Chapters 12 and 17).

Chapter summary

  • add control flow (end of full_rewrite_to_sink): CFGContext finds each END's parent loop and chains sibling loops; pm_add_control_flow wraps a RANGE's bound in AFTER(bound, prev). Now every toposort is properly nested. pm_split_ends makes every END close exactly one RANGE.
  • linearize: priority key (run_count, #ranges, op_priority, extra) → ideal numbering → bottom-up heap toposort that stays as close to ideal as dependencies allow. Hoisting, loads-early, stores-late fall out of the key.
  • pm_to_program grows PROGRAM(SINK) → +LINEAR (do_linearize: line_rewrite with IF/ENDIF and ALLOC→BUFFER; regalloc for ISA) → estimates → +SOURCE (render) → +BINARY (compile), or SOURCE+BINARY at once via do_assemble. ProgramInfo = launch dims + params + outs/ins; Estimates = ops/lds/mem.
  • Renderer = capability tables (code_for_op, extra_matcher, float4, locals, dims, dtypes, tensor cores) + a generator + a compiler. CStyleLanguage: a string PatternMatcher, naming (data0_4, Lidx0, val0, alu0), inline-if-single-use, indentation by RANGE/END depth; six languages are subclasses.
  • LLVM IR (phi loops), PTX (typed virtual registers), NIR (Mesa via ctypes), and the x86 ISA backend: isel to INS with virtual registers → linearize → lower RANGE/END to jumps → linear-scan regalloc (furthest-next-use eviction, loop-aware live ranges) → encode bytes.
